### 8. 用户域数据库表改造方案文档撰写

> 改造方案文档：[2026-08-26-需求-用户域数据库表改造方案.md](../requirements/2026-08-26-需求-用户域数据库表改造方案.md)
> 评审来源：[2026-08-24-数据库表评审-01-用户域.md](../requirements/2026-08-24-数据库表评审-01-用户域.md)

#### 8.1 文档概要

根据用户域 13 张表 + 1 子表的评审结果，拟定改造方案文档，按需求点切分并拟定逐项实现变更顺序。

**文档结构**：
- §一 评审结果总览：9 张表 + 1 子表已决策改造，4 张表已废除
- §二 按需求点切分（14 个需求点）：
  - A. 基础设施前置决策（Redis 序列号生成器）
  - B. 废除表清理（表3/4/12/13）
  - C. 业务主键改造（11 张表编码方案对照表）
  - D. 时间字段统一（命名+维护方式+备注三统一）
  - E. is_deleted 处理（表7 取消豁免）
  - F. CONSTRAINT 外键移除
  - G. extra_json/TEXT 处理（表9B/10/11）
  - H. 字段命名规范化（表源前缀）
  - I. 表拆分（表9 → user_broadcast + user_message）
  - J. 子表新增（user_reminder）
  - K. 索引调整
  - L. COMMENT 补充
  - M. 存量数据迁移
  - N. API 兼容方案
- §三 逐项实现变更顺序（6 个阶段）：
  - 阶段1：基础设施决策 + 废除表清理（并行）
  - 阶段2：核心表 DDL 变更（4 批，按依赖顺序）
  - 阶段3：后端服务改造（编码生成器 → 时间推送 → 引用校验 → 表9拆分服务 → 子表服务 → API 调整）
  - 阶段4：前端改造（小程序 + 管理端并行）
  - 阶段5：存量数据迁移（主键映射 → extra_json → 广播消息）
  - 阶段6：API 兼容过渡与清理
- §四 跨域联动待办（product_code/order_code/processed_by_code/biz_code 字段长度待各域评审确定后同步）
- §五 风险与注意事项（5 项关键风险点）
