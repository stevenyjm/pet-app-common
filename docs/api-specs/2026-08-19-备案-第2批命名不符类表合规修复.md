## 1. 变更范围

第二档「命名不符 + 缺 is_deleted 类」共 **26 张表**，均使用 `create_time` / `update_time` 命名（不符合 `_at` 后缀规范），且缺少 `is_deleted` 字段。

含核心表：`user_account`、`order_main`、`admin_user`、`user_feedback`、`service_conversation`、`refund_record`。

### 1.1 字段统一定义

| 字段 | DDL 定义 |
|------|----------|
| `created_at` | `DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间（北京时间）'` |
| `updated_at` | `DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '最后更新时间（北京时间）'` |
| `is_deleted` | `TINYINT NOT NULL DEFAULT 0 COMMENT '逻辑删除：0-未删除，1-已逻辑删除'` |

## 2. RENAME COLUMN 兼容性说明

所有改名操作使用 `ALTER TABLE ... RENAME COLUMN old TO new`（MySQL 8.0+ 支持）。

数据迁移：
- `created_at` / `updated_at` 直接沿用原 `create_time` / `update_time` 的值，不重写
- `reminder_tag_dict.deleted` → `is_deleted` 直接沿用（`deleted TINYINT NOT NULL DEFAULT 0` → 与目标类型约束完全一致）
- `refund_record.is_hidden` → `is_deleted` 直接沿用（BOOLEAN 隐式转为 TINYINT，true→1/false→0）
- 所有 `is_deleted` 新增字段默认为 0（未删除），不影响存量数据

## 3. 向后兼容性评估

| 变更 | 向后兼容 | 影响 |
|------|---------|------|
| `create_time` → `created_at` | ❌ 不兼容 | 所有后端代码查询 `create_time` 的地方必须同步改名；前端 API 响应如果返回原字段名需排查 |
| `update_time` → `updated_at` | ❌ 不兼容 | 同上 |
| `deleted` → `is_deleted`（reminder_tag_dict） | ❌ 不兼容 | 后端查询 reminder_tag_dict 的 `deleted` 字段需改名 |
| `is_hidden` → `is_deleted`（refund_record） | ❌ 不兼容 | 后端查询 refund_record 的 `is_hidden` 字段需改名；管理端前端类型 `isHidden` → `isDeleted` |
| DROP `is_hidden` / `hidden_at` / `hidden_by`（5 张表） | ❌ 不兼容 | 管理端隐藏功能改造为 DELETE + restore（见 §4） |
| 新增 `is_deleted` 默认 0 | ✅ 兼容 | 不影响存量数据 |

### 4.2 reminder_tag_dict.deleted → is_deleted 改造

后端涉及 `reminder_tag_dict.deleted` 的查询和写入改为 `is_deleted`。通常不涉及独立管理端 API（内嵌于提醒配置页面），需在 service 层搜索使用点并同步。

### 4.3 refund_record.is_hidden → is_deleted 改造

后端涉及 `refund_record.is_hidden` 的查询和写入改为 `is_deleted`；管理端前端类型 `RefundRecord.isHidden` → `isDeleted`。

## 6. 代码引用检查清单（字段改名影响点）

> **注意**：只针对上述 26 张表的字段改名。其它表的 `create_time` / `update_time`（如 user_refresh_token.admin_audit_log 等在第5批处理）本次不改。
