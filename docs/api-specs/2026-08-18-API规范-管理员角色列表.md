# API 规范：管理员角色列表

> **创建日期**：2026-08-18
> **涉及项目**：pet-app-backend（实现）、pet-app-admin-web（消费）
> **关联需求**：管理端「账户管理」页面新建/分配管理员时需要角色下拉选项
> **优先级**：中
> **影响范围**：后端新增只读接口；前端账户管理页消费

## 一、背景

管理端左侧导航缺少「账户管理」菜单，超管无法在页面上对管理员账户做增删改查、启停、重置密码、强制下线等操作。后端 `routes/admin/adminUserRoutes.js` 已实现 8 个管理员管理接口（均 `requireRole('super_admin')` 鉴权），但前端缺失对应页面，且后端缺少「角色列表」只读接口——新建管理员 / 分配角色时需要 `role_id`，必须提供角色下拉来源。

本规范定义新增的只读接口 `GET /admin/admin-roles`，用于支撑前端账户管理页的角色选择下拉框。

## 二、接口定义

### GET /admin/admin-roles

获取管理员角色列表（仅超管可访问）。用于前端账户管理页「新建管理员」「分配角色」对话框的角色下拉选项。

**鉴权**

| 中间件 | 说明 |
|--------|------|
| `adminAuthMiddleware` | JWT 鉴权，解析 `req.admin.adminId` |
| `requireRole('super_admin')` | 仅 `role_code === 'super_admin'` 放行 |

**请求参数**

| 参数 | 类型 | 必填 | 来源 | 说明 |
|------|------|------|------|------|
| Authorization | string | 是 | header | `Bearer <access_token>` |
| is_active | boolean | 否 | query | 是否只返回启用中的角色（`true` 时过滤 `is_active = true`）。默认返回全部 |

**成功响应**（code: 0）

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "list": [
      {
        "role_id": 2,
        "role_name": "仓库管理员",
        "role_code": "warehouse_admin",
        "description": "负责入库、出库、库存盘点等仓库作业",
        "is_active": true,
        "created_at": "2026-07-01T10:00:00+08:00",
        "updated_at": "2026-07-01T10:00:00+08:00"
      },
      {
        "role_id": 3,
        "role_name": "采购员",
        "role_code": "purchaser",
        "description": "负责采购下单与供应商对接",
        "is_active": true,
        "created_at": "2026-07-01T10:00:00+08:00",
        "updated_at": "2026-07-01T10:00:00+08:00"
      }
    ]
  }
}
```

**响应字段说明**

| 字段 | 类型 | 说明 |
|------|------|------|
| list | array | 角色列表 |
| list[].role_id | number | 角色 ID（创建/分配管理员时提交此值） |
| list[].role_name | string | 角色名称（下拉显示） |
| list[].role_code | string | 角色编码（如 `super_admin`/`warehouse_admin`/`purchaser`/`finance`/`operations`） |
| list[].description | string \| null | 角色描述 |
| list[].is_active | boolean | 是否启用 |
| list[].created_at | string | 创建时间（ISO 8601 北京时间） |
| list[].updated_at | string | 更新时间（ISO 8601 北京时间） |

> 前端响应拦截器 `toCamelCase` 会自动转为 camelCase（`roleId`/`roleName`/`roleCode`/`isActive`/`createdAt`/`updatedAt`），前端代码消费 camelCase。

**可能的错误码**

| code | HTTP | 说明 |
|------|------|------|
| 0 | 200 | 成功 |
| 40101 | 401 | 未登录或 Token 失效 |
| 40301 | 403 | 无权访问（非超管角色） |
| 50001 | 500 | 服务器内部错误 |

## 三、数据库表结构

涉及表 `admin_role`（已存在，无需变更）。建表语句如下：

```sql
CREATE TABLE IF NOT EXISTS `admin_role` (
  `role_id` BIGINT NOT NULL AUTO_INCREMENT COMMENT '角色主键',
  `role_name` VARCHAR(64) NOT NULL COMMENT '角色名称',
  `role_code` VARCHAR(32) NOT NULL COMMENT '角色编码（super_admin/warehouse_admin/purchaser/finance/operations）',
  `description` VARCHAR(255) DEFAULT NULL COMMENT '角色描述',
  `is_active` TINYINT(1) NOT NULL DEFAULT 1 COMMENT '是否启用：1-启用 0-禁用',
  `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间（北京时间）',
  `updated_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间（北京时间）',
  PRIMARY KEY (`role_id`),
  UNIQUE KEY `uk_role_code` (`role_code`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='管理员角色表';
```

## 四、字段命名对齐

| 维度 | 规则 | 本接口遵循情况 |
|------|------|----------------|
| 数据库字段 | snake_case | `role_id`/`role_name`/`role_code`/`is_active`/`created_at` |
| API 响应字段 | snake_case | `role_id`/`role_name`/`role_code`/`is_active`/`created_at` |
| 前端消费字段 | camelCase（拦截器转换后） | `roleId`/`roleName`/`roleCode`/`isActive`/`createdAt` |
| 时间字段 | ISO 8601 北京时间 +08:00 | `created_at`/`updated_at` |

## 五、与现有接口的关系

| 接口 | 状态 | 关系 |
|------|------|------|
| `GET /admin/admin-users` | 沿用 | 列表返回每条管理员的 `role_name` 和 `role_code`，但不返回可选角色全集 |
| `POST /admin/admin-users` | 沿用 | 创建管理员需要 `role_id`，依赖本接口提供角色下拉。前端需过滤 `is_active = true` 且 `role_code != 'super_admin'` |
| `PATCH /admin/admin-users/:id/role` | 沿用 | 分配角色需要 `role_id`，依赖本接口提供角色下拉。前端同样需过滤禁用角色 |
| `DELETE /admin/admin-users/:id` | **已下线** | 与「禁用」语义重叠（均为 status=0 逻辑删除），路由不再注册，统一使用 `PATCH /admin/admin-users/:id/status` 替代 |
| `POST /admin/admin-roles` | **新增** | 创建新角色（名称/编码/描述）。参见 [2026-08-19-API规范-角色CRUD管理.md](./2026-08-19-API规范-角色CRUD管理.md) §2.1 |
| `PUT /admin/admin-roles/:role_id` | **新增** | 编辑角色（名称/编码/描述），`super_admin` 不可编辑。参见同上规范 §2.2 |
| `PATCH /admin/admin-roles/:role_id/status` | **新增** | 启用/禁用角色，禁用后下拉自动过滤。参见同上规范 §2.3 |
| `GET /admin/admin-roles/:role_id/permissions` + `PUT /admin/admin-roles/:role_id/permissions` | 沿用 | 权限矩阵接口，与角色字段编辑互不干扰。**新建角色默认权限为空，创建成功后需调用权限矩阵接口配置** |

本接口仅返回角色字典（含 `is_active` 状态），不涉及 `admin_role_permission` 关联表（权限码列表由 `GET /admin/permissions` 单独提供）。

## 六、角色职责与权限分配

> 本节描述 `GET /admin/admin-roles` 返回的 4 个可分配角色（仓库管理员 / 采购专员 / 财务专员 / 运营专员）及超管的职责权能与权限分配，供超管在账户管理页分配角色时参考。超管角色不可被分配（前端下拉已过滤）。

> **重构说明（2026-08-18 更新）**：本节最初仅覆盖进销存 17 个权限码，且按"职能"划分导致部分模块职责重合。已由 [2026-08-18-需求-管理员角色权限矩阵重构.md](../requirements/2026-08-18-需求-管理员角色权限矩阵重构.md) 闭环，权限码扩展至 49 个覆盖管理端全部模块，划分方式从"按职能预设"改为"按模块细分 + 超管可勾选/取消勾选"。下方 6.1–6.4 内容保留作为历史参考与默认勾选状态，**实际权限分配以重构方案矩阵为准**；超管可在前端矩阵 UI 中按需调整任意非超管角色的勾选状态（参见 [2026-08-18-API规范-管理员权限矩阵.md](./2026-08-18-API规范-管理员权限矩阵.md)）。

### 6.1 数据来源

| 信息 | 来源文件 | 说明 |
|------|---------|------|
| 权限码定义 | `pet-app-backend/utils/inventoryPermissions.js`（`INVENTORY_PERMISSIONS`） | 17 个权限码，格式 `模块:操作` |
| 角色 → 权限矩阵（设计） | 同上文件（`ROLE_PERMISSION_MATRIX`） | 超管返回 `ALL_PERMISSIONS`，4 个非超管角色各自的权限码子集 |
| 角色种子数据（role_name / description） | `pet-app-backend/scripts/migrate-schema-v37-audit-ip-and-rbac.js` L68-74 | 5 条预置角色 |
| 权限码 → 前端菜单映射 | `pet-app-admin-web/src/router/index.ts`（`meta.permission`） | 路由守卫按 `meta.permission` 与 `GET /admin/permissions` 返回的权限列表做匹配 |
| 运行时权限返回 | `pet-app-backend/middleware/permissionMiddleware.js`（`getAdminPermissions`） | 超管代码层返回矩阵全集；非超管查 `admin_role_permission` 表 |

### 6.2 角色职责总览

| role_code | role_name（种子） | description（种子） | 职责权能 |
|-----------|---------|------|---------|
| `super_admin` | 超级管理员 | 拥有全部权限 | 系统最高权限，可管理账户、查看全部进销存菜单与操作日志、配置临期预警参数。**不可被分配**（前端下拉过滤 + 后端禁止创建/分配超权角色） |
| `warehouse_admin` | 仓库管理员 | 库存/出入库/调拨/盘点/预警 | 仓库日常作业全流程：入库/出库登记、仓间调拨、库存盘点、仓库与库位维护、批次管理、临期预警查看、追溯查询 |
| `purchaser` | 采购专员 | 采购/供应商/入库 | 采购下单与供应商对接：采购单管理、供应商维护、入库登记、批次/临期/追溯查看 |
| `finance` | 财务专员 | 财务报表/应付应收 | 财务对账与报表查看：财务报表、批次/临期/追溯只读、库存概览与查看 |
| `operations` | 运营专员 | 库存查看/批次/追溯/预警查看 | 日常运营只读监控（权限最少）：库存概览/查看、批次、临期预警、追溯查询 |

### 6.5 当前实现状态与已知缺口

#### 6.5.1 非超管权限尚未落地到数据库（重要）

`getAdminPermissions` 的实际行为：
- **超管**：代码层直接返回 `Object.values(ROLE_PERMISSION_MATRIX.super_admin)`（17 项，含 `admin:manage`），**不查 `admin_role_permission` 表**
- **非超管**：调用 `getRolePermissions(role_id)` 查询 `admin_role_permission` 表

种子脚本 `migrate-schema-v37-audit-ip-and-rbac.js` L95-108 **仅向 `admin_role_permission` 表写入了 super_admin 的 16 条权限记录**（且不含 `admin:manage`，超管的 `admin:manage` 由代码层矩阵提供）。**warehouse_admin / purchaser / finance / operations 四个角色在表中没有权限记录**。

**实际影响**：当前非超管角色登录后 `GET /admin/permissions` 返回空数组，前端 `hasPermission()` 对所有带 `meta.permission` 的进销存菜单返回 `false`，非超管**看不到任何进销存菜单项**。§6.4 的矩阵是**设计意图**，需补充种子脚本将矩阵写入 `admin_role_permission` 表后才能生效。

> 建议后续补一个 `migrate-admin-role-permissions-seed.js` 脚本，按 `ROLE_PERMISSION_MATRIX` 为 4 个非超管角色批量插入权限记录，使矩阵落地。

#### 6.5.2 权限码定义层面的缺口

| 权限码 | 状态 | 影响 |
|--------|------|------|
| `notification:view` | `INVENTORY_PERMISSIONS` 未定义、矩阵未分配给任何角色（含超管） | 顶部铃铛按钮绕过菜单权限检查可直接跳转通知中心；直接访问 `/inventory/notification-center` 路由会被路由守卫拦截至 `/403`。属既有配置不一致，与本角色列表接口无关 |
| `log:view` | 仅超管拥有 | 操作日志仅超管可见，符合最小权限设计 |
| `expiry:config` | 仅超管拥有 | 临期预警配置仅超管可改，符合最小权限设计 |
