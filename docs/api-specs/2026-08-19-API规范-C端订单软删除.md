## 1. 背景

C 端用户对**终态订单**（40 已完成 / 50 已关闭·已取消）发起删除请求，后端执行**逻辑删除**（写入 `user_deleted_at`），**禁止物理 DELETE**。用户侧无任何恢复入口；运营兜底恢复路径在管理端（`PATCH /admin/orders/:id/user-restore`，P1 后续批次）。

## 2. 涉及数据库表

### 2.1 `order_main` 表字段

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| order_id | BIGINT | PK, AUTO_INCREMENT | 订单主键 |
| user_id | BIGINT | NOT NULL | 下单用户 ID |
| out_trade_no | VARCHAR(64) | NULL, UNIQUE | 对外订单号 |
| order_status | TINYINT | NOT NULL, DEFAULT 10 | 订单状态：10-待支付, 20-待发货, 30-待收货, 40-已完成, 50-已关闭/已取消, 60-售后中 |
| user_deleted_at | DATETIME | NULL DEFAULT NULL | C 端用户逻辑删除时间（NULL=未删除）；与管理员 is_hidden 语义隔离 |
| is_deleted | TINYINT | NOT NULL, DEFAULT 0 | 逻辑删除：0-未删除, 1-已逻辑删除（§8 规范字段） |
| created_at | DATETIME | NOT NULL, DEFAULT CURRENT_TIMESTAMP | 创建时间（北京时间） |
| updated_at | DATETIME | NOT NULL, DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP | 最后更新时间 |

### 2.2 `order_main` 建表语句（节选 · 含本期字段）

```sql
CREATE TABLE `order_main` (
  `order_id` BIGINT NOT NULL AUTO_INCREMENT COMMENT '订单主键',
  `user_id` BIGINT NOT NULL COMMENT '下单用户 ID',
  `out_trade_no` VARCHAR(64) DEFAULT NULL COMMENT '对外订单号',
  `order_status` TINYINT NOT NULL DEFAULT 10 COMMENT '订单状态：10-待支付, 20-待发货, 30-待收货, 40-已完成, 50-已关闭/已取消, 60-售后中',
  `user_deleted_at` DATETIME DEFAULT NULL COMMENT 'C端用户逻辑删除时间（NULL=未删除）。与管理员 is_hidden 语义隔离',
  `is_deleted` TINYINT NOT NULL DEFAULT 0 COMMENT '逻辑删除：0-未删除, 1-已逻辑删除',
  `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间（北京时间）',
  `updated_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '最后更新时间',
  PRIMARY KEY (`order_id`),
  UNIQUE KEY `uk_out_trade_no` (`out_trade_no`),
  KEY `idx_user_status_time` (`user_id`, `order_status`, `created_at`),
  KEY `idx_user_deleted_time` (`user_id`, `user_deleted_at`, `created_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='订单主表';
```

> 字段 `user_deleted_at` 已在 `scripts/schema.sql` L225 定义；本期通过迁移脚本 `migrate-schema-v50-order-user-deleted-at.js` 同步至云端 DB。

## 3. 接口定义

### 3.1 DELETE /api/v1/orders/:order_id — 逻辑删除订单（C 端用户）

| 项目 | 说明 |
|------|------|
| 方法 | DELETE |
| 路径 | /api/v1/orders/:order_id |
| 路径参数 | `order_id`（string）：订单主键 ID 或 `out_trade_no`（沿用后端 `buildOrderIdentifierWhere` 解析） |
| 认证 | `authMiddleware`（Bearer User JWT），从 `req.user.userId` 取登录用户 ID |
| 鉴权要求 | 必选；订单 `user_id` 必须等于登录用户 ID |
| 状态门禁 | `order_status ∈ {40, 50}`；否则 42227 `ORDER_CANNOT_DELETE` |
| 归属校验失败 | 404 `ORDER_NOT_FOUND`（40405，不泄露是否存在） |
| 幂等 | `user_deleted_at IS NOT NULL` → 直接返回 `{ deleted: true, already_deleted: true }`，**不抛错** |
| 副作用 | 1) `UPDATE order_main SET user_deleted_at = NOW() WHERE order_id = ? AND user_id = ?`；2) 写 `admin_audit_log`（action=`order_user_delete`，detail 含 `user_id`、`order_id`、`order_status_before`）；**禁止**物理 DELETE |
| 事务 | 使用 sequelize.transaction + `LOCK.UPDATE` 行锁，避免并发重复写入 |
| 响应字段命名 | snake_case（C 端 API 终态规则） |

#### 3.1.1 请求示例

```http
DELETE /api/v1/orders/20260819000123 HTTP/1.1
Authorization: Bearer <user_jwt>
```

无请求体。

#### 3.1.2 成功响应（code=0 · 首次删除）

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "order_id": "20260819000123",
    "deleted": true,
    "already_deleted": false,
    "user_deleted_at": "2026-08-19T15:30:00+08:00"
  }
}
```

#### 3.1.3 成功响应（code=0 · 幂等 · 重复删除）

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "order_id": "20260819000123",
    "deleted": true,
    "already_deleted": true,
    "user_deleted_at": "2026-08-19T15:28:00+08:00"
  }
}
```

#### 3.1.4 响应字段说明

| 字段 | 类型 | 说明 |
|------|------|------|
| order_id | string | 对外订单号（`out_trade_no`），与请求参数对应 |
| deleted | boolean | 是否处于已删除状态（始终 true，幂等） |
| already_deleted | boolean | true=本次为幂等命中（之前已被删除）；false=本次为首次删除 |
| user_deleted_at | string \| null | 用户删除时间（ISO 8601 北京时间 +08:00）；幂等场景返回原删除时间 |

#### 3.1.5 可能的错误码

| code | HTTP | 常量 | 说明 |
|------|------|------|------|
| 40101 | 401 | UNAUTHORIZED | 未登录 / Token 失效 |
| 40405 | 404 | ORDER_NOT_FOUND | 订单不存在或不归当前用户（归属校验失败或主键不存在，统一返回避免泄露） |
| 42227 | 422 | ORDER_CANNOT_DELETE | 当前订单状态不允许删除（status ∉ {40, 50}） |
| 50001 | 500 | INTERNAL_ERROR | 服务器内部错误 |

### 3.2 GET /api/v1/orders — 列表查询过滤变更

在现有 `WHERE user_id = ? AND is_deleted = 0` 的基础上**追加**：

```sql
AND user_deleted_at IS NULL
```

> 该改动**不影响**管理端 `GET /admin/orders`（管理端**不过滤** `user_deleted_at`，全量可见）。

## 4. 不提供的接口（明确范围）

| 接口 | 是否提供 | 原因 |
|------|----------|------|
| `PUT /api/v1/orders/:order_id/restore` | ❌ 不提供 | 用户侧无自助恢复能力 |
| `GET /api/v1/orders/recycle-bin` | ❌ 不提供 | 不提供回收站 |
| `DELETE /api/v1/orders/:order_id/force` | ❌ 不提供 | 禁止物理删除 |

用户删除后唯一恢复路径：联系客服 → 运营在管理端执行 `PATCH /admin/orders/:id/user-restore`（P1 后续批次）。
