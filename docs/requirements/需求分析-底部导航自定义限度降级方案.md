## 一、需求背景与现状

### 1.1 当前底部导航架构（关键事实）

经代码核查，当前小程序底部导航**并非单一实现，而是"原生 custom-tab-bar 框架壳 + 业务画布浮层"的结构**：

| 层 | 文件 | 机制 | 作用 |
|----|------|------|------|
| **原生层（壳）** | [pages.json](file:///c:/Users/22188/Desktop/宠物生鲜电商开发项目/pet-app/src/pages.json#L282-L320) `tabBar.custom: true` + [custom-tab-bar/](file:///c:/Users/22188/Desktop/宠物生鲜电商开发项目/pet-app/src/custom-tab-bar/index.js) | 微信原生自定义 tabBar **框架壳**：[index.wxss](file:///c:/Users/22188/Desktop/宠物生鲜电商开发项目/pet-app/src/custom-tab-bar/index.wxss) 用 `display:none !important` **将 UI 完全隐藏** | 仅注册 5 个 tab 路由，使 `wx.switchTab` 可用；UI 不渲染 |
| **浮层（实际 UI）** | [BottomDock.vue](file:///c:/Users/22188/Desktop/宠物生鲜电商开发项目/pet-app/src/components/bottom-dock/BottomDock.vue) | `position: fixed; bottom: 0` 画布浮层，叠加在隐藏的原生 tabBar 之上 | **承担 100% 的底部导航渲染与点击** |

> ⚠️ **重要事实**（v1.2 修正）：原生 `custom-tab-bar` 的 [index.wxml](file:///c:/Users/22188/Desktop/宠物生鲜电商开发项目/pet-app/src/custom-tab-bar/index.wxml) 虽写了 flex 布局结构与 `prominent` 凸起分支，但 [index.wxss](file:///c:/Users/22188/Desktop/宠物生鲜电商开发项目/pet-app/src/custom-tab-bar/index.wxss) 将 `.tab-bar` 设为 `display:none`，**UI 实际不渲染**。用户看到、点到的底部导航全部来自 `BottomDock.vue` 浮层。`custom-tab-bar/index.js` 的 `switchTab` 方法因 UI 隐藏而不会被触发，实际跳转由 `BottomDock` → `navigatePrimary` → `uni.switchTab` 完成。

**浮层 `BottomDock.vue` 的渲染能力**（[BottomDock.vue:140-175](file:///c:/Users/22188/Desktop/宠物生鲜电商开发项目/pet-app/src/components/bottom-dock/BottomDock.vue#L140-L175)）：

通过 2000px 画布坐标系（`circle.cx/cy/r` 圆心 + `labelAnchor.ax/ay` 文字锚点）精确控制每个图标与文字的像素位置，支撑商户在管理端拖拽调整。

### 1.2 当前可配置项清单

数据模型来自后端 [dockDefaultConfig.js](file:///c:/Users/22188/Desktop/宠物生鲜电商开发项目/pet-app-backend/config/dockDefaultConfig.js#L12-L103)：

| 配置字段 | 含义 | 与本次需求的关系 |
|----------|------|------------------|
| `background` | 底图资源 URL | ✅ **保留** |
| `centerOverflowPx` | 中心凸出高度（pet 上浮像素） | ❌ **废弃**（pet 不再凸起，字段失去意义） |
| `canvas.width / height` | 画布坐标系尺寸（2000×90） | ❌ **废弃**（改用 flex 布局） |
| `slots[].pageId / route / navMode / enabled` | 槽位标识、路由、跳转模式、显隐 | ✅ 保留 |
| `slots[].pageName` | 导航标签文字 | ✅ **保留** |
| `slots[].iconDefault / iconActive` | 默认/选中图标 | ✅ **保留** |
| `slots[].labelStyle` | 文字颜色、字号、加粗 | ✅ 保留 |
| `slots[].circle.cx / cy / r` | 图标圆心坐标与半径 | ❌ **废弃**（位置不再可调；pet 偏大改由 wxss 固定，见 §2.1） |
| `slots[].labelAnchor.ax / ay` | 文字锚点相对偏移 | ❌ **废弃**（位置不再可调） |

### 1.3 问题根因

商户反馈的"流畅性和兼容性不佳"根因在于 **BottomDock 浮层方案本身**，而非原生 tabBar：

1. **浮层重担全压**：原生 custom-tab-bar UI 被 `display:none` 隐藏，底部导航 100% 由 `BottomDock` 用 `position: fixed` 像素定位渲染，失去原生 tabBar 的布局稳定性
2. **坐标系复杂**：2000px 画布 → 真机像素的映射（[dockCoordinate.ts](file:///c:/Users/22188/Desktop/宠物生鲜电商开发项目/pet-app-admin-web/src/utils/dockCoordinate.ts)），不同机型 `rpx/px/safe-area` 换算误差导致错位
3. **图标用 `position: absolute` 像素定位**：而非流式布局，机型适配脆弱
4. **凸起交互**：pet 中心凸起靠 `cy=60` 像素偏移 + `centerOverflowPx` 实现，而非结构性布局；本次决策**移除凸起**，该问题随之消除

## 二、需求整理

### 2.1 商户可配置项（降级后）

| 能力 | 降级前 | 降级后 | 说明 |
|------|--------|--------|------|
| 上传底部导航底图 | ✅ | ✅ **保留** | 整条底图资源，作为 tabBar 背景 |
| 更换导航标签图标 | ✅ | ✅ **保留** | 每个 tab 的默认态/选中态图标 |
| 更改导航标签文字 | ✅ | ✅ **保留** | 每个 tab 的显示文案 |
| 调整图标位置 | ✅（拖拽 cx/cy） | ❌ **去除** | 固定为 flex 等分布局 |
| 调整文字位置 | ✅（拖拽 ax/ay） | ❌ **去除** | 固定在图标下方 |
| **pet 中心凸起视觉** | ✅（`cy=60` + `centerOverflowPx`） | ❌ **去除** | pet 不再上浮凸起，所有 tab 顶部对齐，不超出 tabBar 顶边 |
| **pet 图标偏大尺寸** | ✅（`r=18` vs `r=16`，直径 36 vs 32px） | ✅ **保留**（v1.2 新增） | pet 图标尺寸大于其它 tab（如 60rpx vs 48rpx），**偏大但不凸起**；由 wxss 固定写死，不交商户调；`prominent` 标记保留，语义从"凸起"降级为"仅图标偏大" |
| 电商导航开关（mall/order 显隐） | ✅ | ✅ 保留 | 业务规则不变 |

> **关键概念区分（v1.2）**：
> - **凸起** = pet 整体上浮，图标圆超出 tabBar 顶边 → ❌ 移除
> - **图标偏大** = pet 图标本身尺寸更大，但仍在 tabBar 区域内，不上浮 → ✅ 保留
>
> 两者技术独立。保留偏大不会重新引入机型适配问题。

## 三、合理性分析

### 3.1 需求合理性：**合理，推荐采纳**

| 维度 | 评估 |
|------|------|
| **投入产出比** | 高。去除画布坐标系与凸起逻辑后，三端复杂度大幅下降，而商户损失的仅是"像素级挪动图标"这一低频且易出错的能力；pet 视觉特殊性通过"图标偏大"轻量保留 |
| **商户真实诉求** | 商户关注的是"品牌换肤"（底图、图标、文字），而非"把首页图标往左挪 3px"。坐标调整在生产环境极易产生越界/遮挡事故（现有 `W_min` 校验即为佐证） |
| **稳定性收益** | 消除浮层像素映射，回归微信官方推荐的 custom-tab-bar 方案，机型兼容性显著提升 |
| **行业惯例** | 主流小程序（含微信自身）的底部导航均采用 flex 等分固定布局，"任意位置"无先例；"单 tab 图标偏大"是常见且安全的视觉强调手法 |

### 3.2 现有校验逻辑的反向印证

管理端目前存在大量"防越界"逻辑，恰恰说明自由位置是**负担**而非**能力**：

- [dockCoordinate.ts:81-95](file:///c:/Users/22188/Desktop/宠物生鲜电商开发项目/pet-app-admin-web/src/utils/dockCoordinate.ts#L81-L95) `isSlotWMinViolation`：校验图标圆必须落在 `x∈[840,1160]`（即 320px 安全区）内
- [dockCoordinate.ts:98-110](file:///c:/Users/22188/Desktop/宠物生鲜电商开发项目/pet-app-admin-web/src/utils/dockCoordinate.ts#L98-L110) `getSlotCoordinateHints`：约束 pet 圆心 `cx=0`、非 pet 图标不可超出画布顶边
- [DockCanvasEditor.vue:576-578](file:///c:/Users/22188/Desktop/宠物生鲜电商开发项目/pet-app-admin-web/src/components/DockCanvasEditor.vue#L576-L578) `W_min 未通过` 红色警告

这些约束在 flex 均分布局下天然满足，无需任何运行时校验。

## 四、可行性分析

### 4.1 关键结论：**可行，原生框架已注册但需重写 UI**

> 当前 `pages.json` 已设 `tabBar.custom: true`，`src/custom-tab-bar/` 框架壳已存在并使 `wx.switchTab` 可用。但因其 [index.wxss](file:///c:/Users/22188/Desktop/宠物生鲜电商开发项目/pet-app/src/custom-tab-bar/index.wxss) 为 `display:none` 空壳，**新方案需重新启用并从零编写 custom-tab-bar 的 wxss**（去掉 `display:none`，补全 `.tab-bar/.tab-item/.tab-icon` 等全部样式），本质是"**移除浮层、重写并启用原生层 UI**"。

### 4.2 原生 tabBar 的能力边界（技术调研）

| 能力 | 纯原生 tabBar（`custom: false`） | 原生自定义 tabBar（`custom: true`） | 本次方案选用 |
|------|----------------------------------|--------------------------------------|--------------|
| 自定义底图（背景 image） | ❌ 仅支持纯色背景 | ✅ wxml 可任意布局 image | ✅ |
| 动态切换远程图标 | ❌ 图标须本地静态资源 | ✅ 可读 storage/网络 URL | ✅ |
| 动态切换文字 | ❌ 写死在 pages.json | ✅ 可读配置 | ✅ |
| 位置自由调整 | ❌ | ✅（但本次主动放弃） | ❌ 主动固定 |
| 单 tab 凸起视觉 | ❌ | ✅（但本次主动放弃） | ❌ 主动移除 |
| 单 tab 图标偏大 | ❌ | ✅ | ✅ **保留 pet 偏大**（v1.2） |
| 原生 switchTab 路由 | ✅ | ✅ | ✅ |
| 原生页面栈/预加载 | ✅ | ✅ | ✅ |
| tab 数量限制 | 2~5 | 2~5 | ✅ 当前 5 个 |

**结论**：原生自定义 tabBar（`custom: true`）**完全可以满足降级后的全部需求**，且是微信官方推荐方案。

### 4.3 三大核心关切逐项验证

#### ✅ 关切 1：标签页加载

- 原生 custom-tab-bar 由微信框架托管，随 tabBar 页面自动加载，生命周期稳定（`attached` / `pageLifetimes.show`）
- 现有 [custom-tab-bar/index.js:74-83](file:///c:/Users/22188/Desktop/宠物生鲜电商开发项目/pet-app/src/custom-tab-bar/index.js#L74-L83) 已实现 `attached` + `show` 双时机刷新 `list`
- 降级后**只需把数据源从 `buildVisibleTabList()` 常量改为读取 dock 配置缓存，并启用 UI 渲染**即可

#### ✅ 关切 2：页面路由跳转

- 现有 [custom-tab-bar/index.js:85-110](file:///c:/Users/22188/Desktop/宠物生鲜电商开发项目/pet-app/src/custom-tab-bar/index.js#L85-L110) `switchTab` 方法已使用 `wx.switchTab`（失败 fallback `wx.reLaunch`）
- 启用 UI 后，用户点击 custom-tab-bar 直接触发该 `switchTab`，与原 BottomDock 的 [primaryNav.js:7-14](file:///c:/Users/22188/Desktop/宠物生鲜电商开发项目/pet-app/src/utils/primaryNav.js#L7-L14) `navigateToTabUrl` 走的是**同一条原生 `switchTab` 链路**
- 享受原生页面栈、预加载、返回行为

#### ✅ 关切 3：页面切换动画

- 现有动画机制通过 storage 中转切换方向，目标页 mixin 消费（[custom-tab-bar/index.js:90-102](file:///c:/Users/22188/Desktop/宠物生鲜电商开发项目/pet-app/src/custom-tab-bar/index.js#L90-L102) 与 [primaryNav.js:67-81](file:///c:/Users/22188/Desktop/宠物生鲜电商开发项目/pet-app/src/utils/primaryNav.js#L67-L81) 等价）
- 启用 custom-tab-bar UI 后，`switchTab` 继续写入 `TAB_TRANSITION_KEY`，页面侧 mixin **零改动**
- 详见 [小程序前端需求-主导航标签页切换动画.md](./小程序前端需求-主导航标签页切换动画.md)

### 4.4 方案对比

#### 方案 A（推荐）：移除浮层，重写并启用原生 custom-tab-bar，pet 偏大不凸起

```
保留：pages.json tabBar.custom: true
重写：src/custom-tab-bar/index.wxss（从 display:none 空壳改为完整 flex 布局样式）
增强：src/custom-tab-bar/index.js（读配置）+ index.wxml（渲染底图，pet 用偏大图标类）
移除：src/components/bottom-dock/BottomDock.vue 及其 coordinate.js
简化：管理端 DockCanvasEditor 画布编辑器 → 表单式配置
```

- **优点**：彻底消除浮层像素映射；微信官方方案，兼容性最佳；动画/路由零改动；pet 偏大轻量保留视觉特殊性
- **缺点**：需从零编写 custom-tab-bar wxss；需迁移现有 dock 配置数据结构（去掉坐标字段与 `centerOverflowPx`）

#### 方案 B（备选）：保留浮层，仅锁定坐标与凸起

- **未解决根因**——浮层像素映射、机型错位问题全部保留；只是把"可调"变成"不可调"，流畅性依旧差
- **不推荐**

#### 方案 C（否决）：纯原生 tabBar（`custom: false`）

- 不支持自定义底图、动态图标、动态文字，**无法满足"保留底图/图标/文字可配"的需求**
- 直接排除

## 九、结论与建议

1. **需求合理且可行**，推荐采纳方案 A（移除浮层、重写并启用原生 custom-tab-bar、pet 偏大不凸起）
2. **原生框架已注册但 UI 隐藏**——`custom-tab-bar` 当前是 `display:none` 空壳，新方案需从零编写 wxss 并启用，这是主要新增工作
3. **三大核心关切（加载/路由/动画）均可保证**，且现有动画机制零改动即可保留
4. **pet 视觉处理（v1.2 定案）**：凸起移除、图标偏大保留。偏大只改 `width/height` 不写上浮偏移，不引入机型适配问题；偏大幅度由 wxss 写死，不交商户调
5. **建议**：进入实现阶段前，先在后端做一次"降级版默认配置"的灰度发布，确认小程序读取无误后再推进管理端改造
