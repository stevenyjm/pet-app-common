## 一、需求分析

### 1.1 需求背景

基于已完成的「管理员角色权限矩阵重构」项目，管理端已具备账户管理和角色权限矩阵配置能力。在实际使用场景中，发现以下两个需要调整的点：

1. **账户删除功能存在安全隐患**：当前超权账户可在账户管理页面删除（逻辑删除）管理员账户。考虑到管理员账户属于系统关键资源，删除操作的风险高于禁用操作——删除后账户的审计日志追溯性可能产生歧义（"已删除"与"已禁用"语义重叠），且不存在需要物理/逻辑删除账户的业务场景（用「禁用」即可满足停用需求）。因此决定**移除账户删除功能**。

2. **角色管理能力缺失**：当前系统的 5 个角色（超管、仓库管理员、采购专员、财务专员、运营专员）由种子脚本预置，**不支持在管理端页面上创建新角色、编辑角色信息（名称/编码/描述）、禁用角色**。随着业务扩展，预置角色无法灵活适配多变的组织架构和岗位划分，需要增加角色的完整 CRUD 管理能力（由超权账户操作）。

### 1.2 现状盘点

#### 1.2.1 账户删除功能现状

| 层级 | 实现情况 | 文件 |
|------|---------|------|
| 后端路由 | `DELETE /admin/admin-users/:id` 已存在 | `pet-app-backend/routes/admin/adminUserRoutes.js` |
| 后端控制器 | `deleteAdminUser` 已实现（逻辑删除：`status = 0`） | `pet-app-backend/controllers/adminUserController.js` L138-L166 |
| 前端 API | `deleteAdminUser` 已封装 | `pet-app-admin-web/src/api/adminUser.ts` |
| 前端 UI | 表格操作列「删除」按钮已渲染 | `pet-app-admin-web/src/views/account/List.vue` L414-L419 |

> **注意**：当前删除的实现是「逻辑删除（status 置 0）」，与「禁用」操作的效果完全相同（均为 `update status = 0`）。二者语义重复，删除功能冗余。

#### 1.2.2 角色管理能力现状

|------|------|------|

### 1.3 需求目标

1. **移除账户删除功能**：前后端双端移除/下线「删除管理员」功能，超权账户在账户管理页面不再看到「删除」按钮，后端删除接口同步下线路由（保留函数代码一段时间以防回滚，但路由不注册）。
2. **新增角色 CRUD 管理（C/U/D 中的 C+U）**：
   - 超权账户可在账户管理页面「角色权限配置」表格中**创建新角色**（填写角色名称、角色编码、角色描述）
   - 超权账户可**编辑现有角色**的名称、编码、描述（`super_admin` 角色除外，不可编辑）
   - 超权账户可**禁用/启用**角色（`super_admin` 角色除外，不可禁用），禁用后该角色在「新建管理员」「分配角色」下拉中不再出现
3. **业务规则保护**：
   - `super_admin` 角色不可编辑（名称/编码/描述）、不可禁用
   - 角色编码 `role_code` 全局唯一，新建/编辑时需校验
   - 禁用角色时：若已有管理员分配了该角色，需给出二次确认提示（但不阻塞禁用，管理员仍可登录，只是后续无法再分配此角色）
   - 新建角色默认权限为空（权限矩阵全不勾选），需超管在创建后手动配置

## 二、解决方案

### 2.1 方案一：双端协同调整（推荐）

> 在现有代码基础上做增量修改，不重构已有架构。

#### 2.1.1 账户删除功能移除方案

| 层级 | 操作 | 说明 |
|------|------|------|
| 前端 UI | 删除 `List.vue` 中「删除」按钮列与 `handleDelete` 函数 | 直接移除 DOM 元素与事件处理 |
| 前端 API | 移除 `deleteAdminUser` 导出与调用 | 避免死代码 |
| 后端路由 | 注释/删除 `DELETE /admin/admin-users/:id` 路由注册 | 路由不注册即可使接口失效（保留 controller 函数代码 1 个月以防回滚） |
| 权限层 | 无变更 | 原删除操作无独立权限码（与 `admin:manage` 绑定），无需调整 |

#### 2.1.2 角色 CRUD 管理新增方案

##### 2.1.2.1 后端新增接口（4 个）

在 `adminRoleController.js` 中新增 3 个函数，在 `adminRoleRoutes.js` 中注册 4 条路由：

| HTTP 方法 | 路径 | Controller 方法 | 说明 |
|-----------|------|----------------|------|
| POST | `/admin/admin-roles` | `createAdminRole` | 创建新角色 |
| PUT | `/admin/admin-roles/:role_id` | `updateAdminRole` | 编辑角色（名称/编码/描述） |
| PATCH | `/admin/admin-roles/:role_id/status` | `updateAdminRoleStatus` | 启用/禁用角色 |
| GET | `/admin/admin-roles/:role_id` | `getAdminRoleDetail` | 获取单角色详情（编辑对话框回显用，可选：列表接口已返回全量字段） |

> 所有接口均需 `adminAuthMiddleware + requireRole('super_admin')` 鉴权。

##### 2.1.2.2 创建角色接口：POST /admin/admin-roles

**请求体**：

| 字段 | 类型 | 必填 | 约束 | 说明 |
|------|------|:---:|------|------|
| role_name | string | ✅ | 1-64 字符 | 角色名称（中文/英文/数字） |
| role_code | string | ✅ | 1-32 字符，snake_case，全局唯一 | 角色编码，如 `customer_service` / `marketing` |
| description | string | ❌ | ≤ 255 字符 | 角色描述 |

**成功响应**：返回新创建的角色完整信息（含 `role_id`、`is_active = true`）。

**业务规则**：
- `role_code` 不可为 `super_admin`（保留编码）
- `role_code` 必须唯一（`uk_role_code` 唯一键约束）
- 新角色默认 `is_active = true`，默认权限为空（`admin_role_permission` 不写入任何记录）
- 写审计日志：`action = admin_role_create`

**错误码**：

| code | HTTP | 说明 |
|------|------|------|
| 0 | 200 | 成功 |
| 40001 | 400 | 参数校验失败（必填缺失/长度超限/格式不符） |
| 40002 | 400 | `role_code` 已存在（`ROLE_CODE_DUPLICATE`） |
| 40101 | 401 | 未登录 |
| 40301 | 403 | 非超管 |
| 50001 | 500 | 服务器错误 |

##### 2.1.2.3 编辑角色接口：PUT /admin/admin-roles/:role_id

**请求体**：

| 字段 | 类型 | 必填 | 说明 |
|------|------|:---:|------|
| role_name | string | ✅ | 角色名称 |
| role_code | string | ✅ | 角色编码（snake_case，唯一） |
| description | string | ❌ | 角色描述 |

**成功响应**：返回更新后的角色完整信息。

**业务规则**：
- 不可编辑 `super_admin` 角色（`role_code === 'super_admin'` → 返回 40304 `ROLE_NOT_EDITABLE`）
- 修改 `role_code` 时需校验唯一性（排除自身 role_id）
- 写审计日志：`action = admin_role_update`，`detail_json` 记录变更前后差异

**错误码**：

| code | HTTP | 说明 |
|------|------|------|
| 0 | 200 | 成功 |
| 40001 | 400 | 参数校验失败 |
| 40002 | 400 | `role_code` 已存在（与其他角色冲突） |
| 40101 | 401 | 未登录 |
| 40301 | 403 | 非超管 |
| 40304 | 403 | 角色不可编辑（`super_admin`） |
| 40401 | 404 | 角色不存在 |
| 50001 | 500 | 服务器错误 |

##### 2.1.2.4 切换角色状态接口：PATCH /admin/admin-roles/:role_id/status

**请求体**：

| 字段 | 类型 | 必填 | 说明 |
|------|------|:---:|------|
| is_active | boolean | ✅ | `true` 启用，`false` 禁用 |

**成功响应**：返回 `null`。

**业务规则**：
- 不可禁用 `super_admin` 角色（返回 40304 `ROLE_NOT_EDITABLE`）
- 禁用前检查是否存在使用该角色的管理员（`admin_user` 表中 `role_id` 匹配且 `status = 1` 的记录数），若存在：
  - 后端接口不阻塞禁用，但在响应 `data` 中额外返回 `affected_admin_count` 字段（受影响的管理员数量），供前端弹出二次确认
  - 前端根据此返回值决定是否展示「当前有 N 个管理员使用此角色，确认禁用后新分配将不再出现此角色，已分配的管理员登录不受影响」的提示
- 写审计日志：`action = admin_role_disable` 或 `admin_role_enable`，`detail_json` 记录 `new_status` + `affected_admin_count`（若 > 0）

**错误码**：同编辑接口。

**响应示例（禁用存在关联管理员的角色）**：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "affected_admin_count": 3
  }
}
```

在 `List.vue` 的「角色权限配置」表格中做如下变更：

**1. 表格操作列扩展**：

原「配置权限」按钮右侧新增：「编辑」「禁用/启用」按钮，表格头部新增「新建角色」按钮。

**2. 新建/编辑角色对话框**：

新增 `RoleFormDialog.vue` 组件（或内联在 `List.vue` 中），表单字段：

| 字段 | 组件 | 校验规则 |
|------|------|---------|
| 角色名称 | `el-input` | 必填，1-64 字符 |
| 角色编码 | `el-input` | 必填，1-32 字符，snake_case 正则，唯一（编辑时排除自身） |
| 角色描述 | `el-input`（type="textarea"） | 选填，≤ 255 字符 |

- 新建模式：标题「新建角色」，字段全空
- 编辑模式：标题「编辑角色 - {role_name}」，字段回显当前值，`role_code` 编辑需提示「修改编码可能影响代码层权限判断，请谨慎操作」

**3. 禁用/启用二次确认**：

- 点击「禁用」：
  - 先查询/预估 `affected_admin_count`（可由 PATCH 接口返回，或前端根据当前管理员列表统计）
  - 若 > 0，`ElMessageBox` 显示「当前有 {N} 个管理员正在使用「{role_name}」角色，确认禁用后，该角色将不再出现在新建/分配角色的下拉选项中，但已分配的管理员登录不受影响。是否确认禁用？」
  - 若 = 0，常规确认即可
- 点击「启用」：常规确认

#### 2.1.3 `admin_role` 表补充字段说明（无需变更）

字段已完全覆盖，无需 DDL。

#### 2.1.4 权限码变更

无需新增权限码。角色管理与账户管理同属「系统」分组，统一使用 `admin:manage` 权限码（所有角色接口已 `requireRole('super_admin')`，与权限码约束一致且更强）。

### 2.2 方案二：软删除接口保留（备选）

不推荐。若担心未来需要恢复删除功能，可改为：
- 前端仅隐藏「删除」按钮
- 后端路由保留但 `return res.json({ code: 40305, message: '删除功能已临时关闭，请使用禁用操作' })`

但考虑到「删除 = status=0」与「禁用」完全等价，保留无意义。推荐使用方案一彻底移除。

## 四、业务规则详单（验收用）

### 4.1 账户删除功能

| 规则 | 预期行为 |
|------|---------|
| 前端 UI 无删除按钮 | 账户管理表格操作列不再出现「删除」链接 |

| `deleteAdminUser` 函数保留但标注 deprecated | 代码层保留 1 个月，注释标注不再使用 |

### 4.2 角色创建

| 规则 | 预期行为 |
|------|---------|
| 必填字段校验 | 未填名称/编码时前端表单提示 + 后端返回 40001 |
| `role_code` snake_case 格式 | 前端正则校验 + 后端正则校验（^[a-z][a-z0-9_]*$） |
| `role_code` 唯一 | 输入已存在编码时前端去重校验/后端返回 40002 |
| `role_code` 不可为 `super_admin` | 尝试创建时返回 40001 或 40304 |
| 默认状态 | 新角色 `is_active = true` |
| 默认权限 | 新角色 `admin_role_permission` 无记录（矩阵全不勾选） |
| 审计日志 | `admin_audit_log` 写入 `admin_role_create` |

### 4.3 角色编辑

| 规则 | 预期行为 |
|------|---------|
| `super_admin` 不可编辑 | 按钮 disabled + tooltip；后端直接调用返回 40304 |
| `role_code` 唯一（排除自身） | 修改为其他角色已使用的编码时返回 40002 |
| 名称/描述修改 | 实时生效，列表立即刷新 |
| 审计日志 | `admin_audit_log` 写入 `admin_role_update`，`detail_json` 含 before/after |

### 4.4 角色启用/禁用

| 规则 | 预期行为 |
|------|---------|
| `super_admin` 不可禁用 | 按钮 disabled + tooltip；后端直接调用返回 40304 |
| 禁用无关联管理员角色 | 常规确认弹窗即可 |
| 禁用有关联管理员角色 | 二次确认弹窗提示受影响管理员数量 N |
| 禁用后角色下拉过滤 | 新建管理员/分配角色下拉不再展示已禁用角色 |
| 已分配禁用角色的管理员 | 仍可正常登录、使用已有权限（分配记录不自动清理） |
| 启用 | 恢复展示在下拉中 |
| 审计日志 | `admin_audit_log` 写入 `admin_role_disable` / `admin_role_enable` |

## 五、影响范围与风险

### 5.1 影响范围

| 范围 | 影响 |
|------|------|
| 前端账户管理页 | 删除按钮移除 + 角色表格新增 3 个操作按钮 + 2 个对话框 |
| 后端路由 | 1 条路由下线（删除）+ 3-4 条路由新增（角色 CRUD） |
| 数据库 | 无 DDL 变更（`admin_role` 表字段已完备），仅 DML 写入新增角色记录 |
| 权限中间件 | 无变更（角色接口已 `requireRole('super_admin')`） |
| C 端小程序 | 完全不受影响 |

### 5.2 风险与缓解

| 风险 | 等级 | 缓解措施 |
|------|:---:|---------|
| `role_code` 被修改后代码层硬编码的判断失效（如 `requireRole('warehouse_admin')`） | 高 | 前端编辑对话框对 `role_code` 输入框添加醒目 warning 提示「角色编码被代码层多处引用，若非必要请勿修改」；后端在修改编码时检查 `admin_user` 表是否存在使用此角色的管理员，若存在 warning 日志 |
| 禁用角色后，历史「分配角色」审计日志中 `new_role_name` 对应角色已无法在下拉中找到 | 低 | 历史审计日志只读，不影响功能；角色详情仍可通过 `admin_role` 表查询（`is_active` 不影响 SELECT） |
| 删除功能移除后运营反馈需恢复 | 低 | 后端函数保留 1 个月，注释 deprecated，路由可快速恢复；文档中明确说明「使用禁用替代删除」 |
