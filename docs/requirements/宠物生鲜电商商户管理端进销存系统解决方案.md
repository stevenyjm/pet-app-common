## 1. 需求背景

宠物生鲜电商具有 **高SKU、强效期敏感、批次追溯要求高** 的行业特性。

现有的商品、购物车及订单数据库仅能支撑基础交易，无法满足 **精细化仓储管理、成本核算及合规追溯** 的需求。

因此，需在商户管理端新增一套专业的进销存系统，以实现业务闭环。

---

## 2. 需求目标

| 目标 | 说明 |
|------|------|
| 业财一体化 | 打通采购、销售、库存与财务数据，确保单品毛利、库存成本及应收应付账款的实时准确 |
| 效期与批次管控 | 建立严格的入库批次绑定与出库先进先出（FIFO）策略，杜绝近效期商品误发，降低损耗 |
| 全链路追溯体系 | 实现从生产到销售订单的双向追溯，满足食品安全监管及客诉要求 |
| 库存周转效率 | 通过库存临期预警与安全监控，辅助运营决策，优化资金占用 |

---

## 3. 需求拆解与分析

### 3.1 批次与效期管控（核心关键）

| 环节 | 需求 | 说明 |
|------|------|------|
| 入库环节 | 绑定批号、日期、有效期及质检报告（如有） | 可后续考虑支持同品类不同批次分区存放策略 |
| 出库环节 | 系统自动执行「先进先出（FIFO）」策略 | 校验货品效期是否匹配前端销售链接规则，不合规自动拦截 |

### 3.2 多级临期预警机制

- **自定义预警节点**：支持配置预警天数（如 15 天、30 天、60 天）
- **多端预警推送**：当库存接近临期时，系统自动推送预警至仓库、运营、采购三端
- **预警处理**：便于提前对临期货品进行处理（如促销、调拨等）

### 3.3 全链路双向溯源

| 追溯方向 | 功能 | 说明 |
|----------|------|------|
| 正向追溯 | 通过批号查询所有关联销售订单、流向客户及当前库存状态 | 查询批次流转全路径 |
| 反向追溯 | 通过订单号反向锁定对应的库存批次、入库单据等仓管信息 | 支持一键召回 |

### 3.4 业财联动与成本核算

| 业务场景 | 财务联动 | 说明 |
|----------|----------|------|
| 采购入库 | 自动生成应付账款单据，记录采购成本 | 采购与应付账款关联 |
| 销售出库 | 根据设定的计价方法自动结转主营业务成本，生成应收账款单据 | 确保财务报表与业务数据一致 |

## 4. 与原系统对接方案

### 4.1 对接用户订单表

| 项目 | 说明 |
|------|------|
| 触发机制 | 订单支付成功后，自动触发进销存「销售出库」流程 |
| 校验逻辑 | 系统实时校验库存可用量及批次效期合规性 |
| 成功处理 | 校验通过后扣减库存并生成出库流水 |
| 失败处理 | 若缺货或效期不符，立即拦截订单并触发预警 |

### 4.2 对接商品SKU表

| 项目 | 说明 |
|------|------|
| 主数据同步 | 进销存主数据中心直接读取现有SKU表，实现产品实拍图、规格、成分变更历史等档案的统一维护，避免重复建档 |
| 字段扩展 | 在SKU表中增加进销存专属字段（如批次管理开关、计价方法等），保持基础数据源唯一 |

### 4.3 对接购物车表

| 项目 | 说明 |
|------|------|
| 库存预占 | 在用户提交订单或加入购物车时，实时读取进销存的「可用库存」与「锁定库存」 |
| 防超卖机制 | 基于实时库存数据进行校验，确保前端展示与后端实际库存一致，防止超卖 |

## 5. 核心数据模型设计（含新增与拓展）

基于现有数据库，需进行以下扩展与新增：

### 5.1 商品SKU表扩展

在现有SKU表中增加生鲜强相关字段：

| 字段名 | 类型 | 说明 |
|--------|------|------|
| `barcode` | String | 商品条码 |
| `batch_management_enabled` | Boolean | 批次管理开关 |
| `serial_number_enabled` | Boolean | 序列号管理开关 |
| `shelf_life_days` | Integer | 保质期天数 |
| `costing_method` | String | 计价方法（如：移动加权平均、FIFO） |

### 5.2 新增仓库与库位表

#### 仓库表

| 字段名 | 类型 | 说明 |
|--------|------|------|
| `warehouse_id` | Integer | 仓库唯一ID |
| `name` | String | 仓库名称 |
| `address` | String | 仓库地址 |
| `manager` | String | 负责人 |
| `permission_config` | JSON | 管理权限配置 |

> **说明**：当前可能只有单一仓库，可方便未来规划和拓展。

#### 库位表

| 字段名 | 类型 | 说明 |
|--------|------|------|
| `location_code` | String | 库位编码 |
| `warehouse_id` | Integer | 所属仓库ID |
| `location_type` | String | 库位类型（如：常温区、冷冻区、残次品区） |

### 5.3 新增库存实时表

作为库存状态的聚合视图，必须与流水保持绝对一致：

| 字段名 | 类型 | 说明 |
|--------|------|------|
| `sku_id` | Integer | 商品SKU ID |
| `warehouse_id` | Integer | 仓库ID |
| `available_qty` | Integer | 可用数量 |
| `in_transit_qty` | Integer | 在途数量 |
| `safety_stock_threshold` | Integer | 安全库存阈值 |

### 5.4 新增库存流水表（核心追溯依据）

记录每一次库存变动的明细，用于成本核算与审计：

| 字段名 | 类型 | 说明 |
|--------|------|------|
| `flow_id` | String | 流水唯一ID |
| `related_doc_no` | String | 关联单据号（采购单/出库单/调拨单等） |
| `sku_id` | Integer | 商品SKU ID |
| `warehouse_id` | Integer | 仓库ID |
| `direction` | String | 入/出方向 |
| `quantity` | Integer | 变动数量 |
| `unit_cost` | Decimal | 单价 |
| `batch_no` | String | 批次号 |
| `timestamp` | DateTime | 业务发生时间戳 |

### 5.5 新增交易单据表

#### 采购单/入库单

| 字段名 | 类型 | 说明 |
|--------|------|------|
| `supplier_id` | Integer | 供应商ID |
| `purchase_details` | JSON | 采购明细 |
| `batch_info` | JSON | 批次信息 |
| `production_date` | Date | 生产日期 |
| `status` | String | 入库状态 |
| `inspection_result` | String | 质检结果 |

#### 销售出库单

| 字段名 | 类型 | 说明 |
|--------|------|------|
| `order_id` | Integer | 关联订单ID |
| `delivery_details` | JSON | 实际发货明细 |
| `deduct_batch` | String | 扣减批次 |
| `logistics_info` | JSON | 物流信息 |

#### 其他单据

| 单据类型 | 用途 |
|----------|------|
| 仓间调拨单 | 处理仓库间库存调拨 |
| 盘点单 | 记录库存盘点结果 |
| 库存调整单 | 处理非交易性库存变动 |

## 7. 风险与注意事项（编者补充）

> **说明**：本章节内容为编者根据原始文档需求补充，非原文档内容。

| 风险点 | 说明 | 应对措施 |
|--------|------|----------|
| 数据一致性 | 库存实时表与流水表需保持绝对一致 | 采用事务保证原子性操作 |
| 性能影响 | 高频库存操作可能影响系统性能 | 引入 Redis 缓存库存热点数据 |
| 历史数据迁移 | 现有商品数据需补全批次管理字段 | 制定数据迁移计划，分批处理 |
| 采购三端联动 | 预警机制需协调仓库、运营、采购三端 | 明确各端职责与通知渠道 |
