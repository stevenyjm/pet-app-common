## 二、按需求点切分

### 需求点 A：基础设施前置决策

**涉及表**：表1 user_account、表5 user_login_log、表11 user_feedback

**决策内容**：
- 表1 `user_code`（U + yyyyMMdd + 4 位流水号）、表5 `login_log_code`（LL + yyyyMMdd + 4 位流水号）、表11 `feedback_code`（FB + yyyyMMdd + 4 位流水号）均采用"前缀 + 日期 + 4 位流水号"格式，三表共用同一序列号生成器基础设施。
- 表5 已选方案 C（依赖 Redis 序列号生成器）；表8 `refresh_token_code`、表9 `message_code`、表9A `broadcast_code`、子表 `reminder_code` 选方案 A/B（时间戳+随机，不依赖 Redis）。
- 表1 `user_code` 采用用户自定义 Redis 序列号 + 降级 DB 行锁方案。
- **待决策**：是否引入 Redis 序列号生成器基础设施？若不引入，表5 需改回方案 A 或 B（DB 计数表）。
- **待决策**：Redis 故障降级方案——降级为 DB 计数表 + 行锁，还是拒绝服务？

**依赖关系**：本需求点是表1/5/11 主键改造的前置条件，需最先决策。

### 需求点 B：废除表清理

**涉及表**：表3 user_email_verify、表4 user_email_send_log、表12 user_sms_log、表13 user_notification_setting

**决策内容**：
- 表3/4：绑定邮箱功能下线，前端功能卡片、后端服务接口、Model/Service/Controller、物理表同步清理。
- 表12：短信业务从未实现，Model 完全未被使用，登录已用微信授权，通知已用站内消息+邮件。
- 表13：通知设置业务从未实现，Model 完全未被使用，小程序前端不涉及该表，管理端无通知设置功能。

**配套清理项**（每张废除表均需）：
1. Model 文件删除
2. 数据库物理表 DROP
3. 相关 Service/Controller/Routes 清理
4. 文档同步（schema.sql、verify-db.js 等）

**依赖关系**：无依赖，可最先执行。

### 需求点 C：业务主键改造

**涉及表**：表1、表2、表5、表6、表7、表8、表9A、表9B、表10、子表 user_reminder、表11

**决策内容**：所有表从 `BIGINT AUTO_INCREMENT` 逻辑主键改造为 `VARCHAR(n)` 业务主键。

| 表 | 旧主键 | 新主键 | 编码格式 | 方案依赖 |
|----|--------|--------|----------|----------|
| 表1 user_account | user_id BIGINT | user_code VARCHAR(16) | U + yyyyMMdd + 4位数字 | Redis 序列号 |
| 表2 user_profile | profile_id + user_id | user_code（1:1 直接作主键） | 复用表1 user_code | 无（依赖表1） |
| 表5 user_login_log | log_id BIGINT | login_log_code VARCHAR(32) | LL + yyyyMMdd + 4位流水号 | Redis 序列号（方案C） |
| 表6 user_address | address_id BIGINT | address_code VARCHAR(32) | ADDR + user_code + 3位序号 | DB 行锁（方案A） |
| 表7 user_browse_log | browse_id BIGINT | browse_log_code VARCHAR(32) | BL + 17位毫秒时间戳 + 4位 base36随机 | 无（方案A） |
| 表8 user_refresh_token | id BIGINT | refresh_token_code VARCHAR(32) | RT + 17位毫秒时间戳 + 4位 base36随机 | 无（方案A） |
| 表9A user_broadcast | （新表） | broadcast_code VARCHAR(32) | BC + 14位秒级时间戳 + 4位 base36随机 | 无（方案A） |
| 表9B user_message | message_id BIGINT | message_code VARCHAR(32) | MSG + user_code + 10位秒级时间戳 + 4位 base36随机 | 无（方案B） |
| 表10 user_preferences | preference_id + user_id | user_code（1:1 直接作主键） | 复用表1 user_code | 无（依赖表1） |
| 子表 user_reminder | （新表） | reminder_code VARCHAR(32) | RM + user_code + MMddHHmm + 4位 base36随机 | 无（方案A） |
| 表11 user_feedback | feedback_id + feedback_no | feedback_code VARCHAR(32) | FB + yyyyMMdd + 4位流水号（复用原 feedback_no） | Redis 序列号 |

**依赖关系**：
- 表1 user_account 是基础表，其他所有表的外键引用均依赖 user_code，必须最先改造。
- 表2/表10 依赖表1（user_code 直接作主键，1:1 关系）。
- 表6/表7/表8/表9B/子表/表11 均引用 user_account.user_code，需在表1 改造后同步。
- 表11 的 `order_code` 字段引用 order_main 表，待订单域表评审确定后同步调整字段长度。
- 表11 的 `processed_by_code` 字段引用 admin_user 表，待管理域表评审确定后同步调整字段长度。

### 需求点 E：is_deleted 处理

**涉及表**：表7 user_browse_log（取消豁免）、其他表（保留/保持豁免）

**决策内容**：
- **表7 user_browse_log**：取消原"流水表豁免 is_deleted"主张，补充 `is_deleted TINYINT NOT NULL DEFAULT 0`，与 `message_status` 等业务字段并存（§8.3.3 业务字段共存规则）。
- **表1/2/6/9A/9B/10/子表/11**：保留 `is_deleted`（业务实体表，CRUD 全生命周期）。
- **表5 user_login_log**：保持豁免（流水表，仅追加不删除）。
- **表8 user_refresh_token**：保持豁免（Token 表，通过 `revoke_time` 实现撤销语义，删除走物理清理）。
- **is_deleted 单列索引移除**：既有表若有 `idx_is_deleted` 单列索引，需在迁移期移除（§8.3.7）。
- **查询过滤**：所有读操作默认带 `is_deleted = 0` 过滤；用户消息列表查询同时带 `is_deleted = 0 AND message_status = 1`。

**依赖关系**：与需求点 C/D 同步进行。

**涉及表**：表9B user_message、表10 user_preferences、表11 user_feedback

### 需求点 H：字段命名规范化

### 需求点 I：表拆分（表9 user_message → user_broadcast + user_message）

**涉及表**：表9A user_broadcast（新表）、表9B user_message（改造）

**决策内容**：
- 原 `user_message` 表按消息类型拆分为 2 张表：
  - **表9A user_broadcast**：广播消息主表，面向全体用户，不含 `user_code`，不提供已读/未读状态与删除入口。
  - **表9B user_message**：用户消息表，非广播类消息（订单/宠物/提醒/系统非广播），含 `user_code`，保留已读/删除交互。
- 表9A 字段精简：移除 `biz_type`（广播消息只关联 broadcast_job 一种实体）、`biz_code` 更名为 `broadcast_job_code`、移除 `tags`（分类通过 priority+icon 实现）。
- 表9B `biz_type` 移除 `broadcast_job` 取值（广播消息走 user_broadcast 表），保留 5 个取值 + null。
- 订单消息短期不分表，采用定期归档 + 索引优化 + 消息合并展示替代方案。

**配套服务改造**：
1. `adminBroadcastService`：从批量创建 user_message 记录改为创建 1 条 user_broadcast 记录。
2. `messageService.createMessage`：判断 message_type，若为 system_broadcast → createBroadcast；否则 → createUserMessage。
3. 管理端反查接口：从 `JSON_EXTRACT(extra_json, '$.source_job_id')` 改为 `WHERE broadcast_job_code=?`（走 idx_broadcast_job_code 索引）。
4. 小程序消息中心："系统"Tab 查询改为 UNION user_broadcast + user_message。

**依赖关系**：与需求点 C/D/E/F/G/H 同步（同属表9 DDL 变更），服务改造在后端改造阶段进行。

### 需求点 J：子表新增（user_reminder）

**涉及表**：子表 user_reminder（新表）、表10 user_preferences

**决策内容**：
- 从 `user_preferences.extra_json.reminders` 数组拆分为独立子表 `user_reminder`，15 个字段，3 个索引。
- 主键 `reminder_code`：RM + user_code + MMddHHmm + 4 位 base36 随机。
- 业务规则：单用户提醒上限 5 条（后端业务层校验）。
- 与表9B user_message 对接：定时任务触发提醒后写入 user_message 表（`message_type=user_reminder`，`biz_type='reminder'`，`biz_code=reminder_code`）。

**配套服务改造**：
1. `userPreferenceService`：`persistRemindersExtra` 与 `syncLegacyFieldsFromReminders` 改造为读写 user_reminder 子表。
2. `userReminderCronService`：cron 任务从扫描 `user_preferences.extra_json` 改为扫描 `user_reminder` 子表。

**依赖关系**：与表10 user_preferences 改造（需求点 C/D）同步，服务改造在后端改造阶段进行。

### 需求点 M：存量数据迁移

**涉及表**：所有已决策改造的表

**决策内容**：
- **主键 ID 映射**：各表 `BIGINT AUTO_INCREMENT` 历史数据映射为新的业务主键编码。
  - 表1：按 `user_id` 升序、按注册日期分组生成 `U{yyyyMMdd}{0001/0002/...}` 编码。
  - 表11：`feedback_no` 数据直接作为 `feedback_code`（值不变，仅重命名字段，零迁移成本）。
  - 其他表：按 `id` 升序批量生成新编码，需保留 `idempotency_key` 与原 `id` 的映射关系以兼容历史审计。
- **extra_json 数据迁移**：
  - 表10：`extra_json.reminders` 数组迁移到 `user_reminder` 子表记录。
  - 表9B：`extra_json` 中的 `source_job_id`/`reminder_id`/`cycle`/`icon`/`tags` 迁移到新字段。
- **广播消息历史数据迁移**：现有 user_message 表中 `message_type='system_broadcast'` 的历史数据迁移到 user_broadcast 表。
- **时间字段格式迁移**：ISO8601 格式转换为 `yyyy-MM-dd HH:mm:ss` 格式。

**依赖关系**：在所有 DDL 变更与后端服务改造完成后进行，需配套数据迁移脚本与回填方案。

## 五、风险与注意事项

1. **Redis 序列号生成器可用性**：表1（用户注册）、表5（登录日志）、表11（用户反馈）的主键生成依赖 Redis，Redis 故障将影响这些业务流程，需有降级方案。
2. **表9 拆分的服务改造范围大**：adminBroadcastService、messageService、管理端反查接口、小程序消息中心均需改造，需确保消息发送/展示不中断。
3. **子表 user_reminder 的过渡期双写**：现有 API 层"过渡期双写"逻辑需改造为从子表查询，兼容旧客户端，需评估过渡期长度。
4. **存量数据迁移的映射关系保留**：各表主键 ID 映射需保留映射关系以兼容历史审计，迁移脚本需充分测试。
5. **product_code / order_code / processed_by_code 字段长度待同步**：用户域改造先行，其他域评审确定后需回填调整字段长度。
