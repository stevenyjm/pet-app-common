## 二、规范准则速查（评审依据）

### 2.1 必备字段

| 字段类别 | 字段名（强制） | 类型与约束 | 说明 |
|----------|---------------|------------|------|
| 主键 | `{实体}_code` | `VARCHAR(n) PRIMARY KEY`，禁止 `BIGINT AUTO_INCREMENT` | 业务主键 |
| 创建时间 | `create_time` | `DATETIME NOT NULL`（无 `DEFAULT CURRENT_TIMESTAMP`，后端推送） | 创建时间 |
| 最后修改时间 | `last_modified_time` | `DATETIME NOT NULL`（无 `DEFAULT`/`ON UPDATE`，后端推送） | 最后修改时间 |
| 逻辑删除标记 | `is_deleted` | `TINYINT NOT NULL DEFAULT 0` | 0-未删除，1-已删除 |

### 2.2 业务主键编码规则（用户已决策）

| 实体 | 编码格式 | 字段类型建议 |
|------|----------|--------------|
| 用户 `user_code` | `U00000001`（前缀 `U` + 8 位数字） | `VARCHAR(16)` |
| 宠物 `pet_code` | `UP0001`（前缀 `UP` + 4 位数字） | `VARCHAR(16)` |
| 订单 `order_code` | `yyyyMMdd` + 4 位流水号（如 `202608250001`） | `VARCHAR(20)` |
| 其他实体 | **在实际确定数据库表字段时，由用户询问决策** | 按需预留余量 |

### 2.3 其他已决策规则

| 规则 | 决策结果 |
|------|----------|
| 时间字段维护方式 | 后端主动推送（移除 DB 自动维护） |
| CONSTRAINT 约束 | 全量移除（引用完整性由后端校验） |
| 字段表源前缀 | 仅易混淆字段加前缀（`status`→`{entity}_status`、`name`→`{entity}_name`）；通用字段（`phone`、`email`、`avatar_url`、`create_time`）不加 |
| `is_deleted` 索引 | 移除单列索引；联合索引中 TINYINT 不作首列 |
| COMMENT | 表级与字段级 COMMENT 均不可省略；枚举字段标注取值映射 |
| TEXT/JSON 类型 | 避免使用；短文本用 VARCHAR(n)，数组用子表，结构化对象用扁平字段或子表；若触发分表须先向用户确认 |
| 豁免场景 | Token 表、审计/流水表、会话消息表可豁免 `is_deleted`（仍需主键 + `create_time` + `last_modified_time`） |

### 2.4 豁免表清单（可豁免 `is_deleted`）

| 表类型 | 示例表 | 豁免理由 |
|--------|--------|----------|
| Token 表 | `user_refresh_token`、`admin_refresh_token` | 通过 `revoked_at` 撤销，物理清理 |
| 审计/流水表 | `admin_audit_log`、`inventory_flow`、`payment_log`、`user_login_log`、`user_email_send_log`、`user_browse_log`、`user_sms_log` | 仅追加不删除 |
| 会话消息表 | `service_message`、`user_message` | 通过业务状态或归档机制管理 |

## 五、使用说明

1. **评审流程**：用户依次打开各分册文档 → 阅读第一部分（旧表）与第二部分（建议表结构）→ 在第三部分填写决策
2. **决策粒度**：可逐表决策，也可逐模块批量决策
3. **分表确认**：若某表因避免 TEXT/JSON 触发分表，须在该表第三部分明确分表方案
4. **编码方案**：业务主键编码格式除已决策的 `user_code`/`pet_code`/`order_code` 外，其他实体编码方案在该表第三部分填写
5. **进度更新**：用户完成某表决策后，告知 AI Agent，由 AI Agent 更新本索引文档的进度看板
