## 一、需求描述

### 1.1 总体目标

对项目数据库表结构与数据服务进行大规模整改，统一表项设计规范，提升联表查询可读性、API 响应字段语义清晰度，并将数据完整性约束从数据库层迁移至后端服务层。

### 1.2 数据库表项优化条款

#### 条款 D1：主键使用业务主键，弃用逻辑主键

- 数据表主键尽量不使用逻辑主键（`BIGINT AUTO_INCREMENT`），改用具有明确业务含义的字段作为主键。
- 示例：
  - 用户表主键：`user_code` = `'U001'`
  - 宠物表主键：`pet_code` = `'UP001'`
  - 订单主表主键：`order_code` = `'2026082300001'`（建议格式：`yyyyMMdd` + 4 位流水号）
- 向前端展示时可展示联合结果：`user_code` & `pet_code` = `'U001UP001'`。

#### 条款 D2：字段名需在联表查询时能区分表源与语义

- 数据表下字段名不得使用在联表查询时不能区分表源与含义的名称。
- 示例：宠物表 `pet` 下 `status` → `pet_status`。

#### 条款 D3：时间字段统一命名

- 数据表下需具有创建时间字段 `create_time`，非空，使用统一日期格式 `yyyy-MM-dd HH:mm:ss`。
- 数据表下需具有最后修改时间字段 `last_modified_time`，同上格式。

#### 条款 D4：逻辑删除字段保留

- 数据表下需具有逻辑删除字段 `is_deleted`，`0` 表示"未删除"，`1` 表示"已删除"。

#### 条款 D5：TINYINT 索引策略

- 数据库中通常不对 `TINYINT` 类型字段作索引；如有必要再添加索引（如 `order_date` 等非 TINYINT 字段）。

#### 条款 D6：去除 CONSTRAINT 约束

- 数据表中不进行 `CONSTRAINT` 约束（含外键约束、检查约束等），该约束迁移至后端服务进行实现。

#### 条款 D7：snake_case 命名统一

- 数据表与前后端请求/响应中，统一使用 `snake_case` 命名规范。

### 1.3 参考建表语句（用户提供的样例）

> 用户在需求中给出的参考样例：整合 `pet` 与 `pet_owner` 两张表为 `pet_file` 表。

```sql
-- pet_app.pet_file 表定义 [整合 pet 和 pet_owner 两张表]
CREATE TABLE `pet_file` (
  `pet_code` varchar(20) COMMENT '宠物编码：UPxxxxxx',
  `pet_name` varchar(20) NOT NULL COMMENT '宠物名称',
  `user_code` varchar(16) COMMENT '用户编码：Uxxxxxx',
  `is_main` tinyint NOT NULL COMMENT '主用户标识：0-主用户，1-副用户',
  `pet_avatar_url` varchar(255) DEFAULT NULL COMMENT '宠物头像',
  `pet_breed` varchar(64) DEFAULT NULL COMMENT '品种',
  `pet_gender` tinyint DEFAULT '0' COMMENT '性别：0-未知，1-雄性，2-雌性',
  `pet_birthday` date DEFAULT NULL COMMENT '宠物生日',
  `preferences` varchar(50) DEFAULT NULL COMMENT '喜好',
  `medical_history` varchar(100) DEFAULT NULL COMMENT '药物历史',
  `allergens` varchar(100) DEFAULT NULL COMMENT '过敏源',
  `pet_status` tinyint DEFAULT '0' COMMENT '绑定状态：0-正常绑定 1-已解绑',
  `is_deleted` tinyint DEFAULT '0' COMMENT '删除标识：0-正常，1-逻辑删除',
  `create_time` datetime NOT NULL COMMENT '创建时间：yyyy-MM-dd HH:mm:ss',
  `last_modified_time` datetime NOT NULL COMMENT '最后修改时间：yyyy-MM-dd HH:mm:ss',
  PRIMARY KEY (`pet_code`,`user_code`)
  -- CONSTRAINT `fk_pet_default_owner` FOREIGN KEY (`default_owner_user_id`) REFERENCES `user_account` (`user_id`)
) ENGINE=InnoDB COMMENT='宠物档案表';
```

### 1.4 样例要点提取

| 维度 | 样例做法 | 与现行规范的关系 |
|------|----------|------------------|
| 主键 | 联合主键 `(pet_code, user_code)`，业务主键 | 与现行"单列主键优先"建议不同；现行允许联合主键仅用于纯关联表 |
| 字段前缀 | `pet_name`、`pet_avatar_url`、`pet_breed`、`pet_gender`、`pet_birthday`、`pet_status` | 比现行更激进，要求所有业务字段都带表源前缀 |
| 主用户标识 | `is_main` | 新增业务字段，现行 `pet_owner.ownership_type` 类似 |
| 创建时间 | `create_time` | 与现行 `created_at` 冲突 |
| 最后修改时间 | `last_modified_time` | 与现行 `updated_at` 冲突 |
| 逻辑删除 | `is_deleted` | ✅ 与现行一致 |
| 外键约束 | 注释掉 `CONSTRAINT` | 与现行允许外键约束冲突 |
| 索引 | 样例未定义任何索引 | 隐含遵循 D5（不对 TINYINT 作索引） |
| 字段类型 | 使用 `varchar(20)` / `varchar(16)` 作为主键类型 | 与现行 `BIGINT AUTO_INCREMENT` 主键类型不同 |
| 时间格式 | `yyyy-MM-dd HH:mm:ss` | 与现行 `DATETIME DEFAULT CURRENT_TIMESTAMP` 实现方式不同 |
| `is_deleted` 默认值 | `DEFAULT '0'`（带引号字符串） | 现行 `DEFAULT 0`（数字字面量） |

## 二、合理性与可行性分析

### 2.1 合理性分析

#### 2.1.1 各条款合理性评估

| 条款 | 合理性 | 评估说明 |
|------|--------|----------|
| D1 业务主键 | ⚠️ 部分合理 | 业务主键对用户可见、对审计友好、跨库迁移友好；但生成的业务编码需保证全局唯一、并发安全、防枚举，且对已有 105 张表全量改造影响巨大 |
| D2 字段名带表源前缀 | ✅ 合理 | 联表查询时可读性提升，避免 `status` 在多表 join 时的二义性；现行规范对此要求较弱 |
| D3 `create_time` / `last_modified_time` | ❌ 与现行规范冲突 | 现行规范 `created_at` / `updated_at` 于 2026-08-19 刚完成收敛（69 张表迁移、9 批改造），改回 `create_time` 是反向操作 |
| D4 `is_deleted` | ✅ 合理 | 与现行规范完全一致，无需变更 |
| D5 TINYINT 不作索引 | ✅ 部分合理 | TINYINT 选择性低，单独索引意义不大；但联合索引中包含 TINYINT（如 `(category_id, status)`）有合理性，不应一刀切 |
| D6 移除 CONSTRAINT | ⚠️ 部分合理 | 移除外键约束可降低写入开销、便于分库分表；但需后端服务补充引用完整性校验、级联删除/更新逻辑，工作量与风险并存 |
| D7 snake_case 统一 | ✅ 合理 | 与现行规范完全一致 |

#### 2.1.2 业务主键方案合理性补充

**优势**：
- 用户侧展示更友好（`order_code='2026082300001'` 比 `order_id=12345678` 更易沟通）
- 跨系统/跨库迁移时业务键天然唯一，不依赖自增 ID
- 防止枚举攻击（自增 ID 易被遍历）

**风险**：
- 编码生成需保障并发安全（不能依赖 `AUTO_INCREMENT`）
- 业务编码一旦生成不可变更，否则全链路同步成本极高
- 编码长度需预留扩展位（如商户扩容、年份进位）
- 对已有数据的迁移需提供"老 ID → 新 code"映射表或双写过渡期

#### 2.1.3 时间字段命名冲突的合理性

现行规范 `created_at` / `updated_at` 是 Sequelize/Rails/ Laravel 生态主流命名，符合 `_at` 后缀语义化约定。新需求 `create_time` / `last_modified_time` 更贴近 MySQL DBA 习惯与中文语义，但：
- 现行命名刚于 2026-08-19 完成全量收敛（v44~v48 五批迁移脚本 + 9 批 P0/P1/P2 联调）
- 改回 `create_time` 等于撤销已完成的合规工作
- Sequelize Model 默认 `timestamps` 字段名为 `createdAt`/`updatedAt`，需手动映射 `createdAt: 'create_time'`，增加 Model 维护成本

### 2.2 可行性分析

#### 2.2.1 改造规模估算

| 维度 | 现状 | 全量改造影响 |
|------|------|--------------|
| 数据库表数 | 105 张 | 105 张表全部需重设主键 + 重命名时间字段 + 字段加前缀 + 删除外键 |
| Model 文件数 | 105 个 | 105 个 Sequelize Model 全部需重写主键定义、字段映射、关联关系 |
| Controller/Service | 约 80 个 | 全部需修改查询条件字段名、响应字段名、外键引用 |
| 路由参数 | 约 200 条 | 路径参数从 `:order_id` → `:order_code`，全链路同步 |
| 前端 API 调用 | 小程序 + 管理端各约 30 个文件 | 全部字段名从 snake_case 旧名迁移到新名 |
| 数据迁移 | 0 张已完成业务主键 | 105 张表需提供"老 ID → 新 code"映射与数据回填脚本 |
| 已有 API 规范文档 | 32 份 | 涉及 ID 字段的全部需更新 |
| 第三方依赖 | 微信支付（`out_trade_no`）、订单号生成规则 | 需评估与新 `order_code` 的并存/替换关系 |

#### 2.2.2 可行性结论

- **可分期实施**：建议按"新增表优先采用新规范 + 既有表按业务模块分批迁移"的策略推进。
- **不可一次性全量改造**：105 张表全量改造涉及数据迁移、API 兼容、前端协同，单次发布风险不可控。
- **需先解决规范冲突**：在改造前，必须先在本文档评审阶段决定"`created_at` vs `create_time`"、"主键策略"、"外键策略"的终态规范。
- **可行性评级**：
  - D2/D4/D7：✅ 高可行性，与现行规范兼容或增量
  - D5：✅ 中可行性，需细化"TINYINT 索引允许场景"
  - D1/D6：⚠️ 中可行性，需配套编码生成服务、引用完整性服务
  - D3：❌ 低可行性，与已完成规范收敛反向，建议保留现行 `created_at`/`updated_at`

## 三、现有规范准则摘要

### 3.1 现行数据库基础字段规范（multi-project.md §8）

#### 3.1.1 必备字段（强制）

| 字段类别 | 字段名（强制） | 类型与约束 |
|----------|---------------|------------|
| 主键 | `id` 或 `{实体}_id` | `BIGINT AUTO_INCREMENT PRIMARY KEY` 或业务主键 |
| 创建时间 | `created_at` | `DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP` |
| 最后更新时间 | `updated_at` | `DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP` |
| 逻辑删除标记 | `is_deleted` | `TINYINT NOT NULL DEFAULT 0` |

> 禁止使用 `create_time` / `update_time` / `deleted` / `deleted_at` / `is_hidden`（用于软删语义）等替代命名。

#### 3.1.2 主键规则

- 单列主键优先：`id` 或 `{实体}_id`（如 `order_id`、`user_id`、`sku_id`）
- 联合主键仅用于纯关联表（如 `inventory_real_time`），命名仍遵循 `{实体}_id` 风格
- 禁止无主键表

#### 3.1.3 逻辑删除规则

- 禁止硬删除，所有表删除走 `UPDATE ... SET is_deleted = 1`
- 查询默认带 `is_deleted = 0` 过滤
- `status` 字段不可替代 `is_deleted`

#### 3.1.4 例外场景豁免

仅以下场景可豁免 `is_deleted`（仍需主键 + `created_at` + `updated_at`）：
- Token 表（`user_refresh_token`、`admin_refresh_token`）
- 审计/流水表（`admin_audit_log`、`inventory_flow`、`payment_log`、`user_login_log`、`user_email_send_log`、`user_browse_log`、`user_sms_log`）
- 会话消息表（`service_message`、`user_message`）

### 3.2 现行 API 字段命名规范（naming-conventions-final-state.master.md）

- 后端 API 响应字段全部 `snake_case`，与数据库列名一致
- 前端响应拦截器为唯一转换点（snake_case → camelCase）
- 路由参数 snake_case：`/:order_id`、`/:user_id`、`/:record_date`
- 响应字段示例：`order_id`、`created_at`、`is_new_user`、`access_token`

### 3.3 已完成合规审计结论摘要

依据 `2026-08-19-分析报告-数据库基础字段与逻辑删除规范合规审计.md`：
- 105 张表中，76 张云端已建表，19 张为代码库已定义但云端未 sync 的新表
- v44~v48 五批迁移脚本全部 `errors=0`
- 字段层合规：`FIELD ISSUES=0`（76 张存在的表 0 missing / 0 extra / 0 typeMismatch）
- 软删除业务链路：8 张表（`product`、`after_sales`、`article`、`user_account`、`order_main`、`user_feedback`、`service_conversation`、`refund_record`）已由 `is_hidden` 全量迁移至 `is_deleted`
- 命名收敛：所有 `create_time`/`update_time` 已改名为 `created_at`/`updated_at`

### 4.4 前端 API 调用字段命名（基于 `pet-app/src/api/order.js` 与 `pet-app-admin-web/src/api/order.ts`）

| 端 | 请求风格 | 响应消费风格 | 转换链路 |
|----|----------|--------------|----------|
| 小程序 | camelCase（请求拦截器自动转 snake_case） | camelCase（响应拦截器自动转） | `deepToSnakeCase` ↔ `deepToCamelCase` |
| 管理端 | camelCase（请求拦截器自动转 snake_case） | camelCase（响应拦截器自动转） | `toSnakeCase` ↔ `toCamelCase` |

**关键观察**：前端实际消费的 camelCase 字段（如 `orderId`、`createdAt`）由后端 snake_case 字段（`order_id`、`created_at`）经响应拦截器转换得到。若后端字段改名（如 `order_id` → `order_code`、`created_at` → `create_time`），前端 camelCase 消费侧会自动变为 `orderCode`、`createTime`，仍可工作，但所有页面/组件中显式访问的字段名需同步更新。

### 4.5 现行响应字段命名汇总（按表源前缀视角）

| 类别 | 字段示例 | 表源前缀情况 | 是否符合 D2 |
|------|----------|--------------|-------------|
| 主键/外键 | `order_id`、`user_id`、`product_id`、`sku_id`、`category_id` | 已带表源前缀 | ✅ |
| 业务状态 | `status`、`order_status`、`payment_status`、`refund_status`、`license_status` | 部分带前缀、部分未带 | ⚠️ `status` 不符 |
| 时间字段 | `created_at`、`updated_at`、`pay_time`、`shipped_at`、`expire_at`、`last_login_time` | 多数带业务前缀 | ✅（仅与 D3 时间命名冲突） |

3. **业务语义合理的级联保留**：`ON DELETE CASCADE` 与 `ON DELETE SET NULL` 的外键约束，若业务语义合理，建议保留数据库层保障。

2. **既有表分批**：按业务模块（用户域、商品域、订单域、宠物域、库存域）分批迁移，每批配套数据迁移脚本 + API 兼容方案。
3. **API 双写过渡**：主键改造期间，API 响应同时返回老 ID 与新 code（如 `order_id` + `order_code`），前端逐步切换。
4. **CONSTRAINT 移除需后端补强**：移除外键前，必须先在后端服务补充引用完整性校验、级联删除/更新逻辑。

### 7.3 需要进行评审决策的部分

#### 7.3.1 评审清单

| 评审项 | 现状 | 新需求 | 评审要点 | 建议 |
|--------|------|--------|----------|------|
| **时间字段命名** | `created_at` / `updated_at`（2026-08-19 完成收敛） | `create_time` / `last_modified_time` | 1) 是否撤销已完成的合规收敛？<br>2) Sequelize Model 默认 `createdAt`/`updatedAt` 需手动映射，增加维护成本<br>3) `created_at` 是业界主流命名 | 🟡 建议保留 `created_at`/`updated_at`，新需求 D3 调整为"`created_at`/`updated_at` 为准" |
| **既有 102 张表主键改造** | `BIGINT AUTO_INCREMENT` 逻辑主键 | 业务主键（`user_code`、`pet_code`、`order_code`） | 1) 102 张表全量改造成本与风险<br>2) 业务编码生成服务的并发安全<br>3) 老数据迁移与双写过渡<br>4) 微信支付 `out_trade_no` 与 `order_code` 的关系 | 🟡 建议分期：新增表强制业务主键；既有表按模块分批评估，不强制全量改造 |
| **CONSTRAINT 全量移除** | 50+ 张表使用 80+ 处外键约束 | 全部移除 | 1) 后端服务引用完整性校验工作量<br>2) 级联删除/更新逻辑迁移<br>3) 分库分表预案是否真有需求<br>4) 性能影响评估 | 🟡 建议部分移除：移除普通 `fk_*` 外键；保留 `ON DELETE CASCADE`/`SET NULL` 等业务语义外键 |
| **字段表源前缀全量化** | 业务字段大部分未带前缀 | 全部业务字段带表源前缀 | 1) 60+ 字段改名影响面<br>2) 通用字段（`name`、`phone`、`email`）是否需要前缀<br>3) API 响应字段同步改名影响 | 🟡 建议细化：仅对"易混淆字段"（`status`、`name`）加前缀；通用字段（`phone`、`email`）保留 |
| **联合展示 `user_code` & `pet_code` = `'ZZP001P001'`** | 无 | 新增 | 1) 联合展示的应用场景<br>2) 生成规则与前端解析<br>3) 与单一 `pet_code` 的并存关系 | ⚠️ 建议评审：是否真有此业务场景？若是，需明确生成规则 |
| **`is_deleted` 单列索引去留** | 14+ 张表有 `idx_is_deleted` | D5 不应对 TINYINT 作索引 | 1) 移除后"过滤未删除记录"查询性能影响<br>2) 是否可改为联合索引 `(is_deleted, ...)` | 🟡 建议保留：`is_deleted` 是高频过滤字段，索引必要 |
| **业务主键生成规则** | 自增 ID 自动生成 | 需自定义生成服务 | 1) `user_code`='U001' 的编号规则（年份/月份/流水号）<br>2) 并发安全（分布式锁/序列表/雪花算法）<br>3) 长度预留（`varchar(20)` 是否足够） | ⚠️ 建议评审：先确定编码规则，再启动改造 |
| **既有 `status` 字段加表源前缀** | 60+ 张表使用 `status` | `{entity}_status` | 1) 改名影响所有 controller/service/query<br>2) API 响应字段同步改名<br>3) 是否所有 `status` 都需改？ | 🟡 建议变更：分模块分批改名，优先改 `pet.status`、`order_main.status`（已为 `order_status`，无需改）等高频混淆字段 |
| **时间字段格式 `yyyy-MM-dd HH:mm:ss`** | MySQL `DATETIME DEFAULT CURRENT_TIMESTAMP` 自动维护 | 应用层显式格式化 | 1) 是否需应用层手动写入时间？<br>2) `DEFAULT CURRENT_TIMESTAMP` 与 `ON UPDATE CURRENT_TIMESTAMP` 是否保留？ | 🟡 建议保留 DB 默认值：`DATETIME DEFAULT CURRENT_TIMESTAMP` 仍是合理实现，应用层仅在读取时格式化 |
| **`pet` + `pet_owner` 合并为 `pet_file` 表** | 两张独立表 | 合并为一张 | 1) 合并后 `pet` 与 `user_account` 的多对多关系如何表达？<br>2) 联合主键 `(pet_code, user_code)` 限制了"一宠多主"场景<br>3) 现行 `pet_owner` 表的 `ownership_type`、`status` 等业务字段如何保留？ | 🔴 建议保留两表设计：合并会丢失多对多关系语义，不符合业务实际 |

#### 7.3.2 评审决策原则

1. **已完成合规收敛的条款不轻易反向**：`created_at`/`updated_at` 命名刚完成全量收敛，新需求 D3 改回 `create_time` 需充分评估。
2. **大范围改造需分批评估**：102 张表主键改造、50+ 张表 CONSTRAINT 移除，需按业务模块分批评审，不强制一次性全量。
3. **业务语义合理的设计保留**：`pet` + `pet_owner` 两表设计支持"一宠多主"业务场景，合并为 `pet_file` 会丢失关系语义，建议保留。
4. **性能优先于规范教条**：`is_deleted` 单列索引虽属 TINYINT 索引，但服务于高频过滤，移除会降低性能，建议保留。
5. **新增表严格遵循新规范**：评审通过后，所有新增表必须严格遵循新规范（业务主键 + 字段前缀 + snake_case）。
