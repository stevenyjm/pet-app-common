### 第一部分：当前数据表（旧表）

#### 字段介绍

| 字段 | 类型 | 约束 | 说明 |

#### 建表语句

```sql
CREATE TABLE IF NOT EXISTS `product_category` (
  `category_id` INT NOT NULL AUTO_INCREMENT COMMENT '主键',
  `parent_id` INT NOT NULL DEFAULT 0,
  `category_name` VARCHAR(64) NOT NULL,
  `sort_order` INT DEFAULT 0,
  `slug` VARCHAR(32) DEFAULT NULL,
  `icon` VARCHAR(8) DEFAULT NULL,
  `status` TINYINT NOT NULL DEFAULT 1 COMMENT '业务状态：1-正常（启用）0-停用',
  `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间（北京时间）',
  `updated_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '最后更新时间（北京时间）',

  UNIQUE KEY `uk_slug` (`slug`),
  KEY `idx_parent_id` (`parent_id`)

```

#### 备注说明

- `category_id` 为逻辑主键（`INT AUTO_INCREMENT`），违反 D1 业务主键规则
- `parent_id` 为外键引用（自引用父分类），需改为 `parent_category_code`
- `status` 字段名易混淆（联表查询时与 `product.status`、`product_sku.status` 等无法区分），违反 D2 字段表源前缀规则
- `created_at` / `updated_at` 命名不符 D3 时间字段命名（应为 `create_time` / `last_modified_time`）
- 时间字段使用 `DEFAULT CURRENT_TIMESTAMP` / `ON UPDATE CURRENT_TIMESTAMP`，违反 D3 维护方式规则（应后端推送）
- 无表级 `COMMENT`
- `parent_id` / `category_name` / `sort_order` / `slug` / `icon` 等字段缺失 `COMMENT`
- `icon VARCHAR(8)` 长度较短，若存储图标 key 可能不足，待评审

### 第三部分：用户评审决策

> **填写说明**：请对以下变更项逐项决策。决策列可选：`✅ 采纳` / `❌ 不采纳` / `⚠️ 部分采纳` / `🔄 用户自定义`。若选 `🔄 用户自定义`，请在"最终值"列填写您的方案。

#### 决策对照表

| 变更项 | 旧值 | 建议值 | 决策 | 最终值 |
|--------|------|--------|------|--------|
| 主键 | category_id INT AUTO_INCREMENT | category_code VARCHAR(32) | ✅ 采纳 | category_code VARCHAR(16) |

| 时间字段备注 | （无） | （待补充） | ✅ 采纳 | 北京时间(UTC+8)，格式yyyy-MM-dd HH:mm:ss |
| 字段表源前缀 | status | category_status | ✅ 采纳 | category_status |
| icon 字段长度 | VARCHAR(8) | VARCHAR(64) | ✅ 采纳 | VARCHAR(64) |
| COMMENT 补充 | 部分缺失 | 全部补充 | ✅ 采纳 | 全部补充 |

#### 决策说明

- **主键改造**：`category_id INT AUTO_INCREMENT` → `category_code VARCHAR(16)`，遵循 D1 业务主键规则。
- **category_code 编码方案**：采用 `C` + 4位数字流水（如 `C0001`、`C9999`），最大容量 9999，符合商品分类作为低频字典表的实际量级需求。前缀 `C`（Category）语义清晰，与规范母版 §8.2 示例及用户域已决策表（`user_code` `U`+8位、`pet_code` `UP`+4位）的单字母/短前缀 + 数字风格保持一致。
- **字段长度预留**：`VARCHAR(16)`（当前编码最长 5 字符，预留余量至 16 字节，足以应对未来编码规则扩展）；`parent_category_code` 同步采用 `VARCHAR(16)` 以保持自引用一致性。
- **并发安全方案**：分类为后台低并发写入场景（管理端运营人员创建），采用 Redis 序列号生成器（`INCR category:category_code:seq`），后端取号后格式化为 `C` + 4位零填充；Redis 不可用时降级为数据库序列表方案。无需引入雪花算法等重型方案。
- **时间字段命名与维护方式**：`created_at` / `updated_at` → `create_time` / `last_modified_time`；移除 `DEFAULT CURRENT_TIMESTAMP` 与 `ON UPDATE CURRENT_TIMESTAMP`，由后端业务逻辑主动推送时间值。
- **时间字段备注**：统一标注"北京时间(UTC+8)，格式yyyy-MM-dd HH:mm:ss"，明确时区与格式约定。
- **根节点表示**：`parent_id = 0` → `parent_category_code = NULL`，语义更清晰（NULL 自然表示无父节点），避免 `0` 与有效编码混淆。
- **字段表源前缀**：`status` → `category_status`，因商品域多表联查频繁（`product_category`、`product`、`product_sku` 均有 `status` 字段），加前缀避免歧义。
- **icon 字段长度**：`VARCHAR(8)` → `VARCHAR(64)`，原 8 字节不足以存储图标 key（如 OSS 路径），放宽至 64 字节。
- **COMMENT 补充**：表级 COMMENT 与所有字段 COMMENT 均补充完整，符合 D8 COMMENT 规范。

#### 最终建表语句

```sql
CREATE TABLE IF NOT EXISTS `product_category` (
  `category_code` VARCHAR(16) NOT NULL COMMENT '分类编码（业务主键，格式C+4位流水，如C0001）',
  `parent_category_code` VARCHAR(16) DEFAULT NULL COMMENT '父分类编码（NULL表示根节点，自引用category_code）',
  `category_name` VARCHAR(64) NOT NULL COMMENT '分类名称',

  `is_deleted` TINYINT NOT NULL DEFAULT 0 COMMENT '逻辑删除：0-未删除，1-已删除',
  `create_time` DATETIME NOT NULL COMMENT '创建时间（北京时间(UTC+8)，格式yyyy-MM-dd HH:mm:ss，后端推送）',
```

#### 决策说明

**主键改造**：
- `product_id BIGINT AUTO_INCREMENT` → `product_code VARCHAR(20)`，遵循 D1 业务主键规则。
- **product_code 编码方案**：采用 `P` + 8位数字流水（如 `P00000001`、`P99999999`），最大容量 1 亿，满足中长期扩展需求。前缀 `P`（Product）语义清晰，与用户域已决策表（`user_code` `U`+8位、`pet_code` `UP`+4位）的单字母/短前缀 + 数字风格保持一致。
- **字段长度预留**：`VARCHAR(20)`（当前编码最长 9 字符，预留余量至 20 字节，足以应对未来编码规则扩展）。
- **并发安全方案**：商品为中等写入频率表（管理端运营人员创建），采用 Redis 序列号生成器（`INCR product:product_code:seq`），后端取号后格式化为 `P` + 8位零填充；Redis 不可用时降级为数据库序列表方案。无需引入雪花算法等重型方案。

**时间字段**：
- 命名：`created_at` / `updated_at` → `create_time` / `last_modified_time`，遵循 D3 时间字段命名规则。
- 维护方式：移除 `DEFAULT CURRENT_TIMESTAMP` 与 `ON UPDATE CURRENT_TIMESTAMP`，由后端业务逻辑主动推送时间值。
- 备注：统一标注"北京时间(UTC+8)，格式yyyy-MM-dd HH:mm:ss"，明确时区与格式约定。

**字段表源前缀**：
- `status` → `product_status`：商品域多表联查频繁（`product_category`、`product`、`product_sku` 均有 `status` 字段），加前缀避免歧义。
- `detail_desc` → `product_detail_desc`：描述类易混淆字段加前缀。

**detail_desc 字段替代方案**：
- `detail_desc TEXT` → `product_detail_desc VARCHAR(200)`，遵循 D9 避免 TEXT 类型规则。
- 用户明确业务实际详情描述不超过 200 字，VARCHAR(200) 足以容纳，无需拆分子表。

**original_price / sold_count 字段移除**：
- **移除理由**：价格与销量应归属 SKU 层级管理，商品层冗余存储存在数据不一致与维护成本。
- **original_price 移除影响**：`productHelpers.js` 价格 fallback 逻辑需调整，由 `sku.original_price || product.original_price || sku.price` 改为 `sku.original_price || sku.price`；移除管理端商品原价读写接口。
- **sold_count 移除影响**：商品详情销量展示改为 `SUM(product_sku.sold_count)` 聚合查询（若性能压力大可引入缓存）；移除管理端商品销量读写接口。
- **后续待办**：需补充 SKU 表（表3）`sku_sold_count` 字段决策（用于销量聚合源）。

**cold_chain 字段移除**：
- **移除理由**：业务实际无冷链配送需求，该字段冗余。
- **跨表影响**：
  1. `order_main.cold_chain` 字段需同步移除（用户已确认），影响订单创建逻辑（`orderController.js#L234-L252`）：移除 `coldChain` 判断，配送方式统一为"标准配送"。
  2. `productHelpers.js` 移除冷链标签展示逻辑（`#L136`、`#L196`、`#L246`）。
  3. 前端移除冷链标签 UI 展示。
- **后续待办**：
  - 跨模块影响：`order_main` 表（订单域）的 `cold_chain` 字段移除需在订单域评审中同步处理。
  - 历史订单的 `cold_chain` 数据保留或清理方案需评估。

**status 字段两层并存**：
- **决策**：商品层 `product_status`（1-上架，0-下架）+ SKU 层 `sku_status`（1-正常，0-停售）并存。
- **理由**：两层职责清晰不冗余，是电商行业通用做法：
  - 商品层：控制商品整体可见性与可购性（违规下架、季节性下架、整体停售）。
  - SKU 层：控制具体规格可售性（某规格库存清完、质量问题、暂停销售）。
- **查询过滤逻辑**：C端列表按 `product_status = 1` 过滤可见商品；详情页 SKU 按 `sku_status = 1` 过滤可购规格；下单判定为 `product_status = 1 AND sku_status = 1` 才可购买。
- **库存联动**：SKU 库存为 0 可自动下架该 SKU（`sku_status = 0`），但不影响商品整体展示。

**extra_json 字段（✅ 全部采纳决策完成）**：

- **已决策内容键处理**：
  1. ✅ **移除冗余键**：`img_theme`、`badge` / `badge_text`（与 `product.img_theme`、`product.badge` 字段重复）。
  2. ✅ **扁平化为 product 字段**：`sub_title`、`discount_label`、`intro_highlight`。
  3. ✅ **移除装饰性图标**：`emoji` / `cover_emoji`（装饰性非核心，与 `thumbnail` 冗余，默认值 📦 即可）。
  4. ✅ **移除冗余详情**：`detail_html`（已被 `product_detail_desc VARCHAR(200)` 替代）。
  5. ✅ **保留 JSON 格式不拆表**：`tags`、`gallery`、`intro_points`（简短数组，不拆子表）。
  6. ✅ **扁平化为 3 个 VARCHAR 字段**：`relatedEntry` / `related_entry` → `related_inner_link` VARCHAR(255) + `related_outer_link` VARCHAR(500) + `related_entry_enabled` TINYINT。
  7. ✅ **扁平化为 VARCHAR JSON 文本字段**：
     - `detail_blocks` → `detail_blocks_json VARCHAR(2000)`（对象数组 `[{title, text, theme}]` 的 JSON 文本）
     - `detail_params` → `detail_params_json VARCHAR(1000)`（二元数组 `[[key, value], ...]` 的 JSON 文本）
     - **理由**：避免 TEXT 类型（符合 D9），VARCHAR 长度可控；避免 JSON 原生类型；查询友好，无需 OSS 二次请求；与 `product_detail_desc VARCHAR(200)` 风格一致。
  8. ✅ **拆分子表 product_meal_scan**：
     - `meal_scan` → 独立子表 `product_meal_scan`（一对一关联 SKU，业务主键 `meal_scan_code` 格式 `MS`+8位流水，VARCHAR(16)）
     - **理由**：业务颗粒度为"商品-SKU"，一个 SKU 对应一个二维码、一个营养信息；消除 product.extra_json 嵌套 JSON；消除 nutrition_ref 双份存储与 buildMealScanPatch 反向同步成本；符合 D9 规范；查询简单（按 sku_code 直接查询，无需 5 级 fallback 匹配）。

## 表 2-1：product_meal_scan（商品扫码营养配置子表）

> 该表由表2 `product.extra_json.meal_scan` 拆分而来，与 `product_sku` 一对一关联，承载扫码用餐预填配置。

### 第一部分：背景与业务流程

#### 业务背景

宠物餐食日记录页扫码填写表单场景：用户扫描商品包装上的二维码，小程序自动拉取该商品规格对应的食物名称、参考重量、营养信息摘要，预填到餐食记录表单。

#### 当前架构问题

1. **二维码维度不匹配**：当前按商品维度生成二维码（`GET /products/:product_id/meal-scan-payload`），但业务实际是"商品-SKU"颗粒度扫码。
2. **SKU 匹配逻辑复杂**：需通过 5 级 fallback（skuRef → sku_id → spec.label → default_sku_id → 唯一 SKU）找到对应 SKU。
3. **数据冗余**：`nutrition_ref` 双份存储（SKU.nutrition_json + product.extra_json.meal_scan）。
4. **同步成本**：SKU 营养信息更新时，通过 `buildMealScanPatch` 反向同步到 product.extra_json.meal_scan。
5. **违反 D9**：extra_json 存嵌套 JSON 对象。

#### 重构后业务流程

1. 二维码按 SKU 维度生成（`GET /skus/:sku_code/meal-scan-payload`）。
2. 后端按 `sku_code` 直接查询 `product_meal_scan` 表，返回 food_name、weight_g、nutrition_ref。
3. nutrition_ref 仍由 SKU.nutrition_json 派生（`buildNutritionRefTruncated`），无需反向同步。

### 第二部分：建议数据表结构

#### 字段介绍

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| meal_scan_code | VARCHAR(16) | PK | 扫码配置编码（业务主键，格式 MS+8位流水，如 MS00000001） |
| product_code | VARCHAR(20) | NOT NULL | 商品编码（引用 product.product_code） |
| sku_code | VARCHAR(32) | NOT NULL, UNIQUE | SKU 编码（引用 product_sku.sku_code，一对一） |
| food_name | VARCHAR(128) | NULL | 食物名称（扫码预填，允许与 product_name 不同，如"鸡肉鲜食"） |
| weight_g | DECIMAL(10,2) | NULL | 参考重量（克，扫码预填，允许与规格标签解析值不同） |
| nutrition_ref | VARCHAR(256) | NULL | 营养信息摘要（从 SKU.nutrition_json 派生，trim 后 ≤256 字符） |
| is_deleted | TINYINT | NOT NULL, DEFAULT 0 | 逻辑删除：0-未删除，1-已删除 |
| create_time | DATETIME | NOT NULL | 创建时间（北京时间(UTC+8)，格式yyyy-MM-dd HH:mm:ss，后端推送） |
| last_modified_time | DATETIME | NOT NULL | 最后修改时间（北京时间(UTC+8)，格式yyyy-MM-dd HH:mm:ss，后端推送） |

> 注：
> - `sku_code` 设 UNIQUE 约束，保证一个 SKU 对应一条扫码配置（一对一关系）。
> - `nutrition_ref` 由后端从 SKU.nutrition_json 派生（`buildNutritionRefTruncated`），写入时主动推送。
> - 该表不承载 `default_sku_id`（已废弃）：原 meal_scan.default_sku_id 的语义是"未传 sku_id 时优先使用的 SKU 键"，重构后按 SKU 维度扫码，无需默认值。

### 第三部分：用户评审决策

#### 决策对照表

| 变更项 | 旧设计 | 新设计 | 决策 | 说明 |
|--------|--------|--------|------|------|
| 表来源 | product.extra_json.meal_scan（嵌套 JSON） | 独立子表 product_meal_scan | ✅ 采纳 | 拆分子表，符合 D9 规范 |
| 业务主键 | 无（JSON 键） | meal_scan_code VARCHAR(16) | ✅ 采纳 | 格式 MS+8位流水（如 MS00000001） |
| 业务主键编码 | 无 | MS+8位流水，VARCHAR(16) | ✅ 采纳 | Redis 序列号生成器（`INCR product:meal_scan_code:seq`），降级为数据库序列表 |
| 关联关系 | product.extra_json.meal_scan.skus[key]（JSON 映射） | product_meal_scan.sku_code（一对一 UNIQUE） | ✅ 采纳 | 一对一关联 SKU，消除 5 级 fallback 匹配 |
| 二维码维度 | 按商品维度（`/products/:product_id/meal-scan-payload`） | 按 SKU 维度（`/skus/:sku_code/meal-scan-payload`） | ✅ 采纳 | 业务颗粒度对齐 |
| food_name | extra_json.meal_scan.skus[key].food_name | product_meal_scan.food_name VARCHAR(128) | ✅ 采纳 | 扁平化字段，允许与 product_name 不同 |
| weight_g | extra_json.meal_scan.skus[key].weight_g | product_meal_scan.weight_g DECIMAL(10,2) | ✅ 采纳 | 扁平化字段，允许与规格标签解析值不同 |
| nutrition_ref | extra_json.meal_scan.skus[key].nutrition_ref（双份存储） | product_meal_scan.nutrition_ref VARCHAR(256) | ✅ 采纳 | 由 SKU.nutrition_json 派生，消除双份存储 |
| default_sku_id | extra_json.meal_scan.default_sku_id | 移除 | ✅ 采纳 | 按 SKU 维度扫码后无需默认值 |
| 反向同步 | buildMealScanPatch 同步到 product.extra_json | 移除 | ✅ 采纳 | 消除反向同步成本 |
| 时间字段 | 无 | create_time + last_modified_time | ✅ 采纳 | 北京时间(UTC+8)，格式yyyy-MM-dd HH:mm:ss，后端推送 |
| 逻辑删除 | 无 | is_deleted TINYINT DEFAULT 0 | ✅ 采纳 | 标准逻辑删除 |

#### 决策说明

**业务主键编码**：
- 格式：`MS` + 8位数字流水（如 `MS00000001`），VARCHAR(16)。
- 并发安全方案：Redis 序列号生成器（`INCR product:meal_scan_code:seq`），后端取号后格式化为 `MS` + 8位零填充；Redis 不可用时降级为数据库序列表方案。
- 容量评估：8位流水最大 99999999（约 1 亿），扫码配置随 SKU 数量增长，容量充裕。

**关联关系（一对一）**：
- `sku_code` 设 UNIQUE 约束，保证一个 SKU 对应一条扫码配置。
- 移除原 `default_sku_id`：按 SKU 维度扫码后，二维码本身已携带 sku_code，无需默认值。
- 移除 5 级 fallback 匹配逻辑（`resolveMealScanEntry`）：按 sku_code 直接查询，逻辑简单清晰。

**nutrition_ref 派生机制**：
- 仍由后端从 SKU.nutrition_json 派生（`buildNutritionRefTruncated`），写入 product_meal_scan.nutrition_ref。
- 派生时机：SKU 营养信息创建/更新时，同步更新对应的 product_meal_scan 记录（正向同步，替代原反向同步）。
- 消除双份存储：nutrition_ref 不再冗余存于 product.extra_json，仅存于 product_meal_scan 表。

**扫码 API 调整**：
- 旧：`GET /products/:product_id/meal-scan-payload?skuId=xxx&weightG=xxx`
- 新：`GET /skus/:sku_code/meal-scan-payload?weightG=xxx`
- 后端改造：`mealScanPayloadService.js` 改为按 sku_code 查询 product_meal_scan 表，关联 product_sku 获取 nutrition_json。
- 前端改造：`pet-app/src/api/product.js` 与 `pet-app/src/subpk-pet/services/mealScan.js` 调整 API 路径。

#### 数据迁移方案

**迁移目标**：将 `product.extra_json.meal_scan.skus` 拆解迁移到 `product_meal_scan` 表。

**迁移步骤**：

1. **建表**：执行 product_meal_scan 建表语句。
2. **数据提取**：遍历 product 表，解析 `extra_json.meal_scan.skus` 对象：
   ```javascript

     // key 可能是 sku_id、spec.label 或动态键
     // 通过 mealScanEntryMatchesSku 匹配到具体 SKU
     // 生成 meal_scan_code（MS+8位流水）

   ```
3. **SKU 匹配**：复用 `mealScanEntryMatchesSku` 逻辑，将 meal_scan 键匹配到 product_sku.sku_code。
4. **nutrition_ref 派生**：从 SKU.nutrition_json 重新派生 nutrition_ref（`buildNutritionRefTruncated`），写入新表。
5. **清理 product.extra_json.meal_scan**：迁移完成后，从 product.extra_json 中移除 meal_scan 键。
6. **验证**：对比迁移前后数据一致性（记录数、字段值）。

**迁移脚本**：需配套 `scripts/migrate-meal-scan-to-subtable.js` 脚本。

**回滚方案**：
- 迁移失败时，保留 product.extra_json.meal_scan 原数据不清理，回滚 product_meal_scan 表数据。
- 迁移完成且验证通过后，方可清理 product.extra_json.meal_scan。
