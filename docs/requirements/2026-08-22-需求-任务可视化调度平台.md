## 1. 需求概述

### 1.1 需求来源

商户管理端左侧导航新增「任务可视化调度平台」分组，落地页以模块卡片形式承载多个调度类子模块。本期包含 2 个模块：

| 模块 | 用途 | 可执行操作 |
|------|------|-----------|
| 后端定时任务管理 | 列举后端服务中所有固定定时任务（含 `cron:*`），展示上次执行时间、下次预计执行时间、每次执行结果/状态 | 具权限管理员可对单个任务「直接触发一次」（二次确认） |
| 消息广播定时任务管理 | 管理和定时发布已在「信息注册台」注册的预设广播消息 | 具权限管理员可「新增」「撤销」「提前执行」（撤销与提前执行需二次确认） |

### 1.2 强约束

1. 后端定时任务为**固定服务**，**不提供**新增与撤销入口。
2. 所有**非查询操作**（手动触发、广播新增/撤销/提前执行）必须计入 `admin_audit_log`。
3. 撤销、提前执行、手动触发均需前端二次确认。
4. 遵循 `multi-project.md` §2 跨项目变更顺序契约：先 API 规范 → 后端实现 → 后端自测 → 前端对接 → 联调。

## 2. 现状分析（代码资产盘点）

### 2.1 后端定时任务现状

经核查 `pet-app-backend/package.json` §scripts 与 `scripts/cron-*.js`，当前共 3 个有效 cron 任务（1 个已废弃）：

| 任务编码 | 脚本 | 调度方式 | 执行频率 | 业务含义 | 服务函数 |
|---------|------|---------|---------|---------|---------|
| `cron:order-expiry` | scripts/cron-order-expiry.js | **内部 node-cron**（长驻进程，`cron.schedule`） | `*/5 * * * *` 每 5 分钟 | 扫描并释放过期订单预占库存 | `services/orderExpiryCronService.processExpiredOrders()` |
| `cron:refund-compensation` | scripts/cron-refund-compensation.js | **外部调度**（一次性脚本，由系统 crontab / pm2 触发） | 由部署侧约定（建议 5 分钟） | 退款补偿重试（扫描 refund_record 轮询退款状态） | **内联 main()，未抽服务函数** |
| `cron:user-reminders` | scripts/cron-user-reminders.js | **外部调度**（一次性脚本） | 由部署侧约定（建议每日 1 次） | 用户日常提醒扫描与下发 | `services/userReminderCronService.processUserReminders()` |
| `cron:pet-daily-remind` | scripts/cron-pet-daily-remind.js | 已废弃 | — | 已迁移至 `cron:user-reminders`（脚本仅留桥接提示） | — |

**关键发现**：
- 后端**无任何 cron 任务执行日志表**，无法回溯「上次执行时间/结果」。
- 任务调度分两类：`cron:order-expiry` 在脚本进程内 `node-cron.schedule`；其余两个为一次性脚本依赖外部调度器。
- 主 Express 服务进程（`server.js`）**不持有**任何 cron 任务句柄，无法直接读取运行时状态。
- `cron:refund-compensation` 的核心逻辑内联在脚本中，未抽成 service，不利于管理端复用触发。

## 3. 整体方案设计

### 3.1 设计原则

1. **不改变现有部署模型**：cron 任务仍以独立进程/外部调度方式运行，不将所有任务搬入主 Express 进程，避免耦合 Web 服务生命周期。
2. **服务函数复用**：管理端"直接触发"与 cron 脚本调用**同一个 service 函数**，保证语义一致。
3. **执行可观测**：通过新增执行日志表 + 脚本插桩，记录每次执行（定时调度 / 手动触发）的开始/结束/结果。
4. **下次执行时间计算式**：任务清单为静态清单（cron 表达式），下次执行时间用 `cron-parser` 库从表达式计算，不依赖运行时句柄。
5. **广播调度与即时广播解耦**：新增 `broadcast_schedule` 调度表，到期由 `cron:broadcast-dispatch` 调用既有 `adminBroadcastService` 下发逻辑，不改造即时广播链路。

### 3.2 模块边界

```
任务可视化调度平台（落地页 /task-platform）
├── 后端定时任务管理 (/task-platform/cron-tasks)
│   ├── 数据源：静态任务清单 (utils/cronTaskRegistry.js)
│   ├── 执行记录：cron_task_execution_log 表
│   └── 触发入口：POST /admin/cron-tasks/:taskCode/trigger
└── 消息广播定时任务管理 (/task-platform/broadcast-schedules)
    ├── 数据源：preset_broadcast_message + broadcast_schedule 表
    ├── 调度执行：cron:broadcast-dispatch（扫描 broadcast_schedule 到期项）
    └── 管理入口：POST/DELETE/POST /admin/broadcast-schedules*
```

  const log = await CronTaskExecutionLog.create({
    task_code: taskCode,
    task_name: task.task_name,
    trigger_type: triggerType,
    triggered_by_admin_id: adminId,
    start_time: new Date(),
    status: 0,
  });
  const t0 = Date.now();
  try {
    const result = await fn();
    await log.update({
      end_time: new Date(),
      duration_ms: Date.now() - t0,
      status: 1,
      result_summary: result ?? null,
    });
    return result;
  } catch (err) {
    await log.update({
      end_time: new Date(),
      duration_ms: Date.now() - t0,
      status: 2,
      error_message: String(err.message).slice(0, 1000),
    });
    throw err;
  }
}
module.exports = { runWithLogging };

async function triggerCronTask(req, res) {
  const { taskCode } = req.params;
  const task = registry.findByCode(taskCode);
  if (!task || !task.enabled) throw new AppError('任务不存在或已禁用', codes.NOT_FOUND, 404);

  // 动态加载服务函数（与 cron 脚本同一函数）
  const mod = require(path.resolve(task.service_module));  // 相对项目根
  const fn = mod[task.service_fn];
  if (typeof fn !== 'function') throw new AppError('任务服务函数未实现', codes.SERVER_ERROR, 500);

  const result = await runWithLogging(taskCode, 1, fn, { adminId: req.admin.adminId });

  await writeAdminAudit({
    adminUserId: req.admin.adminId,
    action: 'cron_task_trigger',
    resourceType: 'cron_task',
    resourceId: taskCode,
    detail: { trigger_type: 'manual', result_summary: result ?? null },

  });

> **手动触发同步等待与超时策略**（决策备案见 §12.6）：
> - 同步等待：手动触发为管理端显式操作，需立即返回执行结果用于 UI 反馈
> - 超时上限：**60 秒**，controller 使用 `Promise.race([runWithLogging(...), timeout(60000)])` 实现
> - 超时行为：
>   - controller 立即返回 `{ status: 'timeout', message: '任务已触发，结果稍后查看历史' }`，前端弹窗提示用户稍后在「查看历史」抽屉中查看最终结果
>   - **任务后台继续执行不中断**（Node.js 无法取消 Promise），`runWithLogging` 正常记录 fn 的开始/结束，最终 log.status 为 1（成功）或 2（失败）
> - `status=3`（超时）语义保留给"运行中长时间未完成"的场景：由独立的看门狗扫描（如每 5 分钟扫描 status=0 且 start_time 超过 10 分钟的记录）置为 status=3，本期看门狗可选实现（标记为 BE-TP-11 自测项的扩展，不阻塞主流程）

**提前执行实现**：复用 `adminBroadcastService` 下发逻辑，调用后更新 schedule 状态。

> **target_type 处理约定**：预设广播 `preset_broadcast_message.target_type` 枚举为 `all`（全体用户）与 `users`（指定用户）。`executeScheduleNow` 与 `cron:broadcast-dispatch` 均通过统一的 `buildBroadcastPayload(preset)` 函数构造 `createBroadcast` 入参，覆盖两种枚举：
> - `target_type='all'`：payload 不传 `user_ids`，由 `adminBroadcastService.resolveRecipientUserIds` 扫描全部 status=1 用户
> - `target_type='users'`：payload 传 `user_ids`（来自 `preset.target_value` 逗号分隔串），由 `adminBroadcastService` 校验与解析
>
> 该函数同时被 `executeScheduleNow`（管理员手动触发）与 `cron:broadcast-dispatch`（定时调度）调用，保证两条下发链路 target 解析逻辑一致。

```js
// services/adminBroadcastScheduleService.js

/**
 * 根据预设广播构造 createBroadcast payload
 * 覆盖 target_type 全部枚举：all / users
 * @param {PresetBroadcastMessage} preset
 * @returns {object} createBroadcast payload（含 confirmed: true）
 */
function buildBroadcastPayload(preset) {
  const payload = {
    title: preset.title,
    content: preset.content,
    target_type: preset.target_type,   // 'all' 或 'users'
    confirmed: true,                    // 调度下发无需再次确认
  };
  if (preset.target_type === 'users') {
    // preset.target_value 为逗号分隔的 user_id 字符串
    payload.user_ids = preset.target_value
      ? String(preset.target_value).split(',').map((s) => s.trim()).filter(Boolean)
      : [];
  }
  return payload;
}

/**
 * 提前执行（管理员手动触发）
 */
async function executeScheduleNow(id, admin) {
  const row = await BroadcastSchedule.findOne({ where: { schedule_id: id, is_deleted: 0 } });
  if (!row) throw new AppError('调度不存在', codes.NOT_FOUND, 404);
  if (row.broadcast_status !== 0) throw new AppError('仅待发送状态可提前执行', codes.INVALID_PARAMS, 400);

  await row.update({ broadcast_status: 1 });  // 发送中占位，防止并发重复下发

  try {
    const preset = await PresetBroadcastMessage.findByPk(row.preset_message_id);
    if (!preset) throw new AppError('预设广播消息不存在', codes.NOT_FOUND, 404);

    // 复用即时广播下发（统一 payload 构造，覆盖 all/users）
    const job = await adminBroadcastService.createBroadcast(buildBroadcastPayload(preset), admin);

    await row.update({
      broadcast_status: 2,
      admin_message_job_id: job.job_id,
      sent_at: new Date(),
    });

    await writeAdminAudit({
      adminUserId: admin.adminId,
      action: 'broadcast_schedule_execute_now',
      resourceType: 'broadcast_schedule',
      resourceId: id,
      detail: { preset_message_id: row.preset_message_id, job_id: job.job_id },
    });
    return { schedule_id: id, broadcast_status: 2, job_id: job.job_id };
  } catch (err) {
    // 下发失败回退状态，保留 error_message 供管理端展示
    await row.update({
      broadcast_status: 4,
      error_message: String(err.message).slice(0, 500),
    });
    throw err;
  }
}

/**
 * 定时调度下发（cron:broadcast-dispatch 调用，无 admin 上下文）
 * 系统触发，不写 admin_audit_log，仅写 cron_task_execution_log
 */
async function dispatchSchedule(row) {
  if (row.broadcast_status !== 0) return null;  // 幂等保护

  await row.update({ broadcast_status: 1 });  // 发送中占位

  const preset = await PresetBroadcastMessage.findByPk(row.preset_message_id);
  if (!preset) throw new AppError('预设广播消息不存在', codes.NOT_FOUND, 404);

  // 系统触发使用默认超管上下文（仅用于 created_by 字段）
  const systemAdmin = { adminId: 0 };  // TODO: 解析默认超管 ID，参考 adminAuditHelper.writeAdminAudit
  const job = await adminBroadcastService.createBroadcast(buildBroadcastPayload(preset), systemAdmin);

  await row.update({
    broadcast_status: 2,
    admin_message_job_id: job.job_id,
    sent_at: new Date(),
  });
  return { schedule_id: row.schedule_id, job_id: job.job_id };
}
```

## 10. 风险与对齐检查清单

### 10.1 风险识别

| 风险 | 影响 | 缓解 |
|------|------|------|
| `cron-parser` 计算的"下次执行时间"与部署侧实际调度不一致 | 管理端展示误导 | 在静态清单注释"schedule_cron 为部署约定，需与运维同步"；UI 文案标注"预计" |
| 手动触发长耗时任务阻塞 API 响应 | 用户体验差 | 设 60s 超时；超时记 status=3 但任务后台继续；UI 提示"任务已触发，结果稍后查看历史" |
| 同一 cron 任务并发执行（定时调度 + 手动触发同时进行） | 数据竞争 | **本期不加分布式锁**（决策备案见 §12.3），依赖业务幂等：<br>· order-expiry 扫描已过滤已处理订单（订单状态机推进）<br>· refund-compensation 靠 retry_count + last_retry_time 5min 门槛<br>· user-reminders 靠提醒规则 once/daily/weekly/monthly 的"当日已下发"标记<br>· broadcast-dispatch 靠 broadcast_status=0 过滤 + 下发前置 status=1 占位 |
| `broadcast-dispatch` 与 `execute-now` 并发下发同一 schedule | 重复发送 | execute-now 先置 status=1 占位；dispatch 扫描时 status=0 过滤即跳过 |
| `cron:refund-compensation` 重构抽取 service 可能改变既有行为 | 退款补偿回归 | 抽取时保持 main() 原逻辑等价，仅外壳变更；用既有 verify-refund-mock-flow.js 回归 |
| `node-cron` 未在 package.json dependencies 显式声明（仅 cron-order-expiry.js 引用） | 部署/重装缺失 | 本次一并补声明 `node-cron` 与新增 `cron-parser` 到 dependencies |
| 历史软删记录导致 `uk_preset_scheduled_del` 冲突 | 撤销后无法同 preset 同时刻重建 | 按 Lessons Learned：软删前在同事务内物理清理同业务键历史软删记录 |
| 管理员账号注销导致 `created_by_admin_id` 置 NULL | 创建人信息丢失 | 外键改为 `ON DELETE SET NULL`（决策备案见 §12.5），广播调度不受影响；查询时需处理 NULL 展示为"已注销账号" |

| 决策项 | 决策结果 |
|--------|---------|
