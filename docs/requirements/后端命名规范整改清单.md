## 一、扫描结论总览

| 类别 | 严重程度 | 问题数量 | 跨项目影响 |
|------|----------|----------|------------|
| JS 变量/函数命名不规范 | 🔴 高 | 3 处 | 否 |
| API 响应字段命名（snake_case → camelCase） | 🟡 中 | 30+ 处 | **是（3 端联动）** |
| API 请求参数命名（query/body） | 🟡 中 | 全项目统一 | **是（3 端联动）** |
| 文件名规范不一致 | 🟢 低 | 12+ 处 | 否 |
| 直接访问 req.body/query snake_case 键 | 🟢 低 | 2 处 | 否 |

### 核心判断

当前项目在**内部实现层面**（Model 定义、数据库字段、Service 层）已基本符合 snake_case 规范，JS 变量/函数也基本遵循 camelCase。

**主要差距集中在 API 边界层**：请求参数和响应字段大量使用 snake_case（如 `page_size`、`is_favorited`、`created_at`），而命名规范要求 API 层应转换为 camelCase。但这是一个**三端联动**的大改动，需谨慎评估。

## 三、P1 — API 响应字段命名规范（✅ 后端准备就绪 · 2026-07-27）

### 3.1 问题描述

当前后端 API 响应大量直接返回数据库 snake_case 字段名，不符合"API 层使用 camelCase"的规范。前端（小程序 + 管理端）均已适配 snake_case 响应。

### 3.2 整改方案

**后端实现**：通过 `camelizeResponse` 中间件实现自动转换，支持 `?use_camel_case=true` 查询参数控制转换行为。

**新增文件**：
- `utils/snakeToCamel.js`：递归转换 snake_case → camelCase 的工具函数
- `middleware/camelizeResponse.js`：全局响应中间件，支持 `use_camel_case` 参数

**修改文件**：
- `routes/index.js`：挂载中间件到主路由
- `routes/admin/index.js`：挂载中间件到 admin 路由

**参数说明**：
- `?use_camel_case=true`：返回 camelCase 响应（如 `pageSize`、`createdAt`）
- `?use_camel_case=false` 或不传：保持 snake_case 响应（向后兼容）

### 3.3 运行时验证结果

| 测试场景 | 结果 |
|---------|------|
| 不带参数 | ✅ 返回 snake_case（`page_size: 20`） |
| `?use_camel_case=true` | ✅ 返回 camelCase（`pageSize: 20`） |
| `?use_camel_case=false` | ✅ 返回 snake_case |

### 3.4 三端协同状态

| 项目 | 状态 | 说明 |
|------|------|------|
| **pet-app-backend** | ✅ 已完成 | 提供 `use_camel_case` 参数，前端可渐进式迁移 |
| **pet-app-admin-web** | ✅ 已完成 | 通过 HTTP 拦截器自动转换，无需后端变更 |

### 3.5 改造策略建议

**方案 A：一次性全量改造（推荐）**
- 后端新增统一的响应格式化层，在返回前将 snake_case → camelCase
- 前端同时改造，全部切换到 camelCase
- 优点：彻底解决命名规范问题
- 缺点：改动量大，需三端同步发布

**方案 B：分阶段渐进改造**
- 第 1 阶段：内部变量命名整改（P0 问题，无跨项目影响）
- 第 2 阶段：新增接口默认使用 camelCase，旧接口保持 snake_case 并标注为 deprecated
- 第 3 阶段：前端逐步迁移至 camelCase
- 优点：风险低，可分批次发布
- 缺点：过渡期存在双命名体系，增加维护成本

**方案 C：保持 snake_case 不变**
- 考虑到三端已形成 snake_case 习惯，可更新命名规范文档，将 API 层规范调整为 snake_case 与当前实践一致
- 优点：零改动
- 缺点：规范与实践名义上不一致

## 五、P3 — API 请求参数命名

### 5.1 当前实践

当前项目中，**API 请求的 query/body 参数统一使用 snake_case**（如 `page_size`、`user_id`、`sku_id`）。这与命名规范中"路由参数使用 snake_case"的精神一致，但规范中提到"API 层应转换为 camelCase"。

### 5.2 现状分析

- 后端：Controller 通过 destructuring 将 snake_case 参数映射为 camelCase 变量（`const { page_size: pageSize } = req.query`）✅ 这部分已做好
- 前端（小程序）：所有 API 调用使用 snake_case 参数名
- 前端（管理端）：所有 API 调用使用 snake_case 参数名

### 5.3 建议

考虑到请求参数涉及三端开发者习惯，且当前 destructuring 映射模式已清晰，建议**保持请求参数 snake_case 现状**，但在 API 文档中明确标注。请求参数的命名规范调整可作为长期优化方向。
