## 1. 需求背景

当前商户管理端将"商品管理""资讯管理""CMS 页面管理""店铺配置""小程序配置"分散在不同导航分组中，缺少统一的"发布管理"入口。商品上下架、资讯版面调整、CMS 页面更新、文案配置修改等操作分散在各管理页面内即时生效，**缺乏版本管理、草稿暂存与发布回滚能力**。

同时，与已完成的「信息注册台」（负责"信息注册/数据录入"）形成**注册→发布两阶段架构**：
- **信息注册台**：商品分类/商品/资讯/营养配置等数据的注册（CRUD + 软删）
- **小程序工作台**：从已注册数据中勾选并发布到小程序（草稿→版本→发布→回滚）

新增左侧导航一级菜单**「小程序工作台」**，作为聚合式落地页，内置若干模块卡片，将既有分散的发布功能分离/迁移至此，并统一引入"保存草稿、查询历史记录、提交发布"的版本化发布流程。

### 1.1 与「信息注册台」的联动关系

| 信息注册台模块 | 小程序工作台模块 | 联动关系 |
|---------------|-----------------|----------|
| 商品注册（分类/商品/SKU CRUD） | 商品发布（勾选→上下架→发布） | 注册台软删商品/分类时，若已在工作台发布，需二次确认→同步下架→禁止再次发布 |
| 资讯注册（资讯 CRUD） | 资讯发布（勾选→版面调整→发布） | 注册台软删资讯时，若已在工作台发布，需二次确认→同步下架→禁止再次发布（W7 扩展，与商品一致） |
| 营养配置表/预设广播/营养因子矩阵 | —（不涉及发布） | 无联动 |

### 1.2 关键联动约束

> 用户明确要求：对「信息注册台」下的**商品分类信息**、**商品信息**以及**资讯信息**进行软删除时，如果涉及已在「小程序工作台」中发布的对应项目，需：
> 1. **二次向操作管理员确认**
> 2. 确认后**同步下架**相关商品分类、商品或资讯
> 3. **不允许再次发布**（即使信息注册台恢复该项目，也不可在工作台重新发布）
>
> 上述三类（商品分类、商品、资讯）软删均遵循一致的重复确认逻辑（W7 扩展）。

## 2. 需求范围

### 2.1 In Scope（本次范围）

- **管理端 · 小程序工作台**：新增一级导航 + 落地页（含模块卡片）。
- **管理端 · 商品发布模块**：从原"商品分类管理""商品管理"的上下架/发布功能分离而来；允许管理员勾选已在信息注册台注册的商品分类和商品，进行上下架管理与发布。
- **管理端 · 资讯发布模块**：从原"资讯管理"的版面/发布功能分离而来；允许管理员勾选已在信息注册台注册的资讯信息，进行版面（首页横幅或商城顶部）调整与发布。
- **管理端 · CMS 配置发布模块**：原"CMS 页面管理"功能迁移，增加草稿/版本/发布流程。
- **管理端 · 文案信息配置发布模块**：原"店铺配置"功能与"小程序配置"中的"文本配置"功能合并，增加草稿/版本/发布流程。
- **后端**：新增统一草稿/版本/发布 Model、Service、Controller、Route；实现各模块发布时的实际生效逻辑；接入审计日志；实现与信息注册台的软删联动检查。
- **信息注册台联动调整**（需用户确认后执行）：`softDeleteProduct` / `softDeleteCategory` / `softDeleteArticle` 增加工作台发布状态检查与二次确认流程。

### 2.2 Out of Scope（本次不做）

- 小程序配置中的"主题资产配置"（`/mini-app-config/theme-assets` 的 draft/publish/rollback 流程）保持不变，不迁入工作台。
- 信息注册台的商品注册/资讯注册 CRUD 能力不变（已 Phase 1 完成）。
- C 端商品浏览/资讯浏览/购物流程不变。
- 既有 `mini_app_config` 表的 theme-assets 草稿/发布机制保留不动。
- 小程序端无需改动（工作台为纯管理端功能）。

### 3.4 既有商品软删流程（`adminProductService.softDeleteProduct`）

```javascript
// 当前实现（L-RG-12 已加 is_deleted=0 过滤，但无工作台联动检查）
async function softDeleteProduct(productId, adminId) {
  const product = await Product.findByPk(productId);
  if (!product) throw new AppError('商品不存在', codes.PRODUCT_NOT_FOUND, 404);
  if (product.is_deleted) return { product_id: productId, deleted: true, already_deleted: true };
  await product.update({ is_deleted: 1 });
  await invalidateProductSkusCache(productId);
  return { product_id: productId, deleted: true };
}
```

> **缺口**：无工作台发布状态检查、无二次确认流程、无同步下架、无禁止再次发布标记。

## 5. 解决方案

### 5.1 总体策略

1. **文档先行**：先定需求方案 + API 规范，再后端实现，再管理端对接，最后联调（遵循 `multi-project.md` §2）。
2. **通用版本引擎**：参考 `mini_app_config` 的 draft/published/archived 模式，建通用表 `workbench_draft`，用 `module_type` 区分 4 个子模块，`draft_data` (JSON) 存模块特定草稿内容。
3. **发布时分发**：草稿内容统一存 JSON，"提交发布"时由 Service 解析 JSON 并分发到对应业务表（`product.status`、`article.position`、`cms_page.content_json`、`shop_config`/`mini_app_config`）。
4. **注册台联动**：信息注册台软删商品/分类时，检查工作台发布状态，二次确认后同步下架 + 加入禁止列表。
5. **审计全覆盖**：保存草稿、提交发布、回滚、联动下架均写 `admin_audit_log`。

### 5.2 管理端导航重构（W1）

- 新增一级菜单「小程序工作台」，路由 `/workbench`，落地页 `views/workbench/Index.vue`，权限码 `workbench:view`。
- 落地页以卡片网格展示 4 个模块卡片，点击进入子页面：
  - 商品发布 → `/workbench/product-publish`
  - 资讯发布 → `/workbench/article-publish`
  - CMS 配置发布 → `/workbench/cms-publish`
  - 文案信息配置发布 → `/workbench/content-config`
- 旧菜单项（商品管理/商品分类/资讯管理/CMS 页面/店铺配置/小程序配置文本配置）待信息注册台 + 小程序工作台均上线后删除（W10，联动信息注册台 D2）。

### 5.3 通用草稿/版本/发布引擎（W2/W9）

#### 5.3.1 核心表 `workbench_draft`

统一管理 4 个子模块的草稿、已发布、已归档版本。每次"保存草稿"创建一条 `publish_status=0` 的新记录，`version_no` 在同 `module_type` 内递增。"提交发布"时：
1. 将当前 `publish_status=1` 的旧版本改为 `publish_status=2`（已归档）
2. 将选中草稿改为 `publish_status=1`（已发布）
3. 解析 `draft_data` JSON 并分发到对应业务表

#### 5.3.2 通用 API 设计

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/admin/workbench/:moduleType/draft` | 保存草稿（创建新版本） |
| GET | `/admin/workbench/:moduleType/drafts` | 查询历史记录（分页） |
| GET | `/admin/workbench/:moduleType/published` | 查询当前发布版本 |
| GET | `/admin/workbench/:moduleType/drafts/:draftId` | 查询指定版本详情 |
| POST | `/admin/workbench/:moduleType/drafts/:draftId/publish` | 提交发布 |
| POST | `/admin/workbench/:moduleType/rollback` | 回滚到上一个发布版本 |

> `:moduleType` ∈ `product_publish` / `article_publish` / `cms_publish` / `content_config`

### 5.8 信息注册台联动（W7/W8）

#### 5.8.1 联动检查流程

```
信息注册台 softDeleteProduct(productId) 执行
  ↓
查询 workbench_draft WHERE module_type='product_publish' AND publish_status=1
  ↓
解析 draft_data.items，检查是否包含该 productId
  ↓
  ├─ 未包含 → 正常软删
  └─ 已包含 → 返回 40901 PRODUCT_WORKBENCH_PUBLISHED + { workbench_version, product_name }
        ↓
        前端弹出二次确认弹窗（"该商品已在小程序工作台发布，软删除将同步下架且不可再次发布，是否继续？"）
        ↓
        ├─ 取消 → 不执行
        └─ 确认 → 带 force_workbench_offline=true 重新请求
              ↓
              后端执行：
              1. product.update({ is_deleted: 1, status: 0 })  // 软删 + 下架
              2. workbench_item_blocklist 插入 { module_type, item_type: 'product', item_id: productId, blocked_reason }
              3. writeAdminAudit(action: 'product_workbench_offline')
              4. invalidateProductSkusCache
```

#### 5.8.2 分类软删联动

商品分类软删时，若分类已在工作台发布，需：
1. 返回 40903 `CATEGORY_WORKBENCH_PUBLISHED` + 二次确认
2. 确认后：分类软删 + 分类下所有已发布商品同步下架 + 所有商品加入禁止列表

#### 5.8.3 资讯软删联动（W7 扩展）

资讯软删时，若资讯已在工作台发布（`workbench_draft` 中 `module_type='article_publish'` 且 `publish_status=1` 的版本 `draft_data.items` 包含该 `article_id`），需：
1. 返回 40904 `ARTICLE_WORKBENCH_PUBLISHED` + `{ workbench_version, article_title }` + 二次确认
2. 前端弹出二次确认弹窗（"该资讯已在小程序工作台发布，软删除将同步下架且不可再次发布，是否继续？"）
3. 确认后带 `force_workbench_offline=true` 重新请求，后端执行：
   - `article.update({ is_deleted: 1, status: 0 })`（软删 + 下架）
   - `workbench_item_blocklist` 插入 `{ module_type: 'article_publish', item_type: 'article', item_id: articleId, blocked_reason }`
   - `writeAdminAudit(action: 'article_workbench_offline')`

#### 5.8.4 禁止再次发布

工作台商品/资讯发布时，检查 `workbench_item_blocklist`：
- 若 `product_id` 在禁止列表中，返回 40902 `PRODUCT_WORKBENCH_BLOCKED` + 提示"该商品因信息注册台软删除联动下架，已被禁止再次发布"
- 若 `article_id` 在禁止列表中，返回 40905 `ARTICLE_WORKBENCH_BLOCKED` + 提示"该资讯因信息注册台软删除联动下架，已被禁止再次发布"

CREATE TABLE `workbench_draft` (

## 11. 风险与注意事项

1. **草稿 JSON 查询性能**：联动检查需查询 `workbench_draft` 的 `draft_data` JSON 中是否包含特定 `product_id`。MySQL `JSON_CONTAINS` 或 `JSON_SEARCH` 可用但性能有限；建议在 Service 层先查询 `publish_status=1` 的版本（每个 module_type 仅 1 条），再解析 JSON 比对，避免全表扫描。
2. **发布事务一致性**：提交发布时需在同一事务内完成"旧版本归档 + 新版本发布 + 业务表分发更新"，任一步骤失败需回滚。
3. **回滚安全性**：回滚到上一个发布版本时，需重新执行该版本的 `draft_data` 分发逻辑，确保业务表状态恢复。
4. **分类软删批量下架**：分类下可能有大量商品，同步下架需批量 update + 批量写入禁止列表，注意事务和性能。
5. **禁止列表解除**：若管理员需要解除禁止（如误操作），需提供管理端页面或 API（本期可作为二期增强，本期仅记录不解除）。
6. **与 `mini_app_config` 既有流程的边界**：theme-assets 的草稿/发布/回滚流程保留不动，仅文本配置部分迁入工作台；需确保两者不冲突。
7. **旧菜单项删除时机**：信息注册台 Phase 3（管理端）与小程序工作台 Phase 3（管理端）均上线后，才可安全删除旧菜单项（商品管理/资讯管理/CMS/店铺配置/小程序配置文本配置）。
