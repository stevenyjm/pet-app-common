# 前端请求超时问题分析与解决方案

> **文档日期**: 2026-06-26
> **问题来源**: 小程序前端和Web前端反馈
> **影响范围**: 页面功能使用过程中或页面切换时出现"请求超时"或"服务器内部错误"

---

## 问题描述

前端反馈现象：
- 使用页面功能或页面切换时，偶尔出现"请求超时"或"服务器内部错误"告警
- 出现问题后页面功能无法使用，或页面无法完成加载
- 后端服务仍在运行，线上探活 `GET /api/v1/health` 正常返回
- 重启后端服务后，所有前端恢复正常

---

## 问题根因分析

### 🔴 主因：数据库连接池耗尽

**代码位置**: `config/database.js:21-26`

```javascript
pool: {
  max: 10,      // ⚠️ 连接池上限仅10个
  min: 0,
  acquire: 30000, // 获取连接超时30秒
  idle: 10000,
},
```

**问题传导链**:

1. **认证中间件双重连接消耗** (`middleware/auth.js:26-35`)
   - 每个带认证的请求调用 `checkDatabaseConnection()` (执行 `sequelize.authenticate()`)
   - 接着又调用 `UserAccount.findByPk()`
   - **单个请求消耗约2个数据库连接**

2. **并发场景下的雪崩效应**
   - 假设同时有6个认证请求 → 消耗12个连接，但池只有10个
   - 后续请求进入等待队列，直到 `acquire` 超时(30秒)
   - 前端看到"请求超时"
   - 健康检查 `/health` 是轻量的单一连接请求，恰好能拿到可用连接

3. **事务持锁加剧**
   - 订单操作使用 `transaction` + `LOCK.UPDATE`
   - 事务执行缓慢或异常时，连接被长时间占用

---

### 🟠 次要因素：进程级健壮性缺失

**代码位置**: `server.js`

1. **无 `uncaughtException` / `unhandledRejection` 处理器**
   - 未捕获的Promise拒绝使进程进入不稳定状态
   - 进程运行但事件循环阻塞，无法处理新请求

2. **无HTTP服务器超时配置**
   - 没有设置 `server.timeout`
   - 挂起的连接永远不会被关闭
   - 客户端异常断开后，服务器端连接资源无法释放

---

### 🟡 潜在风险：SSE连接泄漏

**代码位置**: `services/servicePushService.js`

- SSE连接保持打开状态
- cleanup逻辑依赖客户端触发 `close` 事件
- 客户端异常断开时，连接对象可能残留在 `subscribers` Map中

---

### 🟡 潜在风险：Redis静默失败

**代码位置**: `config/redis.js:29`

```javascript
client.on('error', () => {}); // ⚠️ 静默忽略所有Redis错误
```

- Redis断开时不会被发现
- 依赖Redis的功能会静默降级
- 可能导致意外行为

---

## 解决方案

### 方案一：优化数据库连接池（P0 - 立即实施）

**修改文件**: `config/database.js`

```javascript
pool: {
  max: 30,           // 增加连接池上限
  min: 2,            // 保持最小空闲连接
  acquire: 10000,    // 缩短获取连接超时（10秒）
  idle: 30000,       // 空闲连接回收时间
  evict: 60000,      // 连接驱逐检查间隔
},
```

**修改文件**: `middleware/auth.js`

移除冗余的数据库连接检查（启动时已验证，运行时连接池自动重连）：

```javascript
// 移除第26-35行的数据库连接检查
// 直接查询用户
const account = await UserAccount.findByPk(userId);
```

---

### 方案二：添加进程级错误处理器（P0 - 立即实施）

**修改文件**: `server.js`

在 `startServer()` 函数后添加：

```javascript
process.on('uncaughtException', (error) => {
  logger.error('[Fatal] Uncaught exception:', error);
  process.exit(1);
});

process.on('unhandledRejection', (reason, promise) => {
  logger.error('[Fatal] Unhandled rejection:', reason);
  process.exit(1);
});

process.on('SIGTERM', () => {
  logger.info('[Server] SIGTERM received, shutting down gracefully');
  server.close(() => {
    process.exit(0);
  });
});
```

---

### 方案三：添加HTTP服务器超时配置（P1）

**修改文件**: `server.js`

```javascript
server.timeout = 30000;          // 30秒请求超时
server.headersTimeout = 35000;   // 35秒头部超时
```

---

### 方案四：增强Redis错误处理（P2）

**修改文件**: `config/redis.js`

```javascript
client.on('error', (error) => {
  logger.error('[Redis] Connection error:', error.message);
});

client.on('connect', () => {
  logger.info('[Redis] Connected');
});

client.on('close', () => {
  logger.warn('[Redis] Connection closed');
});
```

---

### 方案五：增强SSE连接清理（P3）

**修改文件**: `services/servicePushService.js`

添加连接超时检测：

```javascript
const MAX_CONNECTION_DURATION = 30 * 60 * 1000; // 30分钟

const timeout = setTimeout(() => {
  res.writeHead(204);
  res.end();
}, MAX_CONNECTION_DURATION);

const cleanup = () => {
  clearInterval(heartbeat);
  clearTimeout(timeout);
  set.delete(res);
  if (!set.size) {
    subscribers.delete(String(conversationId));
  }
};
```

## 实施优先级

| 优先级 | 方案 | 预期效果 | 风险 |
|--------|------|----------|------|
| **P0** | 方案一：优化连接池 + 移除认证冗余检查 | 直接解决连接耗尽问题 | 低 |
| **P0** | 方案二：进程级错误处理 | 防止进程僵尸状态 | 低 |
| **P1** | 方案三：HTTP超时配置 | 防止连接资源泄漏 | 低 |
| **P2** | 方案四：Redis错误处理 | 提高可观测性 | 低 |
| **P3** | 方案五：SSE超时 | 清理异常连接 | 低 |
