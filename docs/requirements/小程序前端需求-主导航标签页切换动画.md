## 一、现象与问题分析

### 1.1 现象描述

用户反馈：在主导航 5 个标签页之间切换时——

- **首次**进入某个标签页（如从首页切到商城），会出现短暂但明显的空白等待（约 300ms~1s，受网络状况影响）。
- **后续**再切换到同一标签页时，没有可感知的停顿，切换呈现"瞬时"感。

### 1.2 根因分析

#### 1.2.1 微信小程序 TabBar 页面生命周期差异

当前主导航采用微信原生 `custom-tab-bar`（[src/custom-tab-bar/index.js](../../../pet-app/src/custom-tab-bar/index.js)），通过 `wx.switchTab` 切换页面。5 个 Tab 是相互独立的物理页面（在 [pages.json](../../../pet-app/src/pages.json#L262-L300) `tabBar.list` 中注册）。

| 切换类型 | 触发的生命周期 | 说明 |
|----------|----------------|------|
| **首次进入** | `onLoad` → `onShow` → `onReady` | 页面实例首次创建，需要执行脚本注入、首次渲染、网络请求 |
| **二次切换** | 仅 `onShow` | 页面实例已存在，DOM/数据已就绪，仅触发可见性回调 |

#### 1.2.2 首次进入的耗时构成

以 [mall.vue#L234-L240](../../../pet-app/src/pages/mall/mall.vue#L234-L240) 为例，`onLoad` 中并行发起 3 个网络请求：

```javascript
onLoad() {
  const { navBarHeight } = getWindowMetrics()
  this.navBarHeight = navBarHeight
  this.loadBanners()      // 轮播图接口
  this.loadCategories()   // 分类列表接口
  this.loadProducts()     // 商品列表接口
}
```

耗时构成（典型值）：

```
页面实例化 + 脚本注入      ≈  50~100ms
首屏骨架渲染（空白 view）  ≈  30~50ms
网络请求 RTT + 服务端处理  ≈ 200~800ms（取决于网络/接口）
数据回填 + 二次渲染        ≈  50~100ms
─────────────────────────────────
合计可感知空白            ≈ 300ms~1s
```

#### 1.2.3 Tab 主页面缺少 Loading 占位

经代码核对：

- 仅 [message/index.vue#L57](../../../pet-app/src/pages/message/index.vue#L57) 与 [product/detail.vue#L3](../../../pet-app/src/pages/product/detail.vue#L3) 使用了 `<PageLoading>` 占位组件。
- 5 个 Tab 主页面（index / mall / pet / order / mine）**均未**使用任何 Loading/骨架屏占位，数据返回前页面呈现纯白底色，加重了"空白等待"的主观感受。

#### 1.2.4 二次切换无停顿的原因

二次切换时，`onLoad` 不再触发，已渲染的 DOM 节点保留在内存中，`onShow` 仅执行轻量刷新（如 [order.vue#L247-L256](../../../pet-app/src/pages/order/order.vue#L247-L256) 中的 `refreshCartCount` / `loadOrders`），用户感知为"瞬时切换"。

### 1.3 用户判断的合理性评估

> 用户判断："标签页首次打开时的加载导致的"

**结论：判断正确且准确。**

补充的专业分析：

1. **更精确的归因**：停顿不仅来源于"加载"，而是"加载 + 渲染 + 缺少占位"三者叠加。即便网络瞬时返回，首次 `onLoad` 时的脚本注入与首屏渲染仍会消耗 80~150ms，这段时间也是空白。
2. **二次切换无停顿的本质**：是页面实例复用 + DOM 复用，并非"数据被缓存"——`onShow` 中仍会重新拉取数据（如 `loadOrders`），但因为旧数据已渲染在屏幕上，新数据回来只是局部更新，用户无感知。
3. **可改善方向**：
   - 加方向性的"滑入动画"，将停顿时间转化为动画时间，主观感受会显著改善；
   - 配合骨架屏/Loading 占位，消除"纯白"视觉；
   - 配合分包预加载（`preloadRule`）+ 数据预取，缩短首次实际耗时。

## 二、需求分析

### 2.1 业务需求

提升主导航的视觉流畅度与操作反馈感，让用户在 Tab 之间切换时能感知"方向性"，强化"空间方位"心智模型，降低多次切换时的认知负担。

### 2.2 功能性需求

| 编号 | 需求 | 说明 |
|------|------|------|
| FR-01 | **方向感知** | 切换动画方向由目标 Tab 与当前 Tab 的相对位置决定 |
| FR-02 | **左切右滑** | 目标 Tab 位于当前 Tab **左侧**时，新页面从左侧**滑入**（视觉上等于当前页向右滑出） |
| FR-03 | **右切左滑** | 目标 Tab 位于当前 Tab **右侧**时，新页面从右侧**滑入**（视觉上等于当前页向左滑出） |
| FR-04 | **方向回退** | 用户从系统返回手势/物理返回键触发时（理论上 Tab 页不应被返回到上一 Tab，但需兜底处理），使用默认无动画或与最近一次切换相反方向 |
| FR-05 | **首次切换特殊处理** | 应用启动后第一次切换 Tab 时，目标页面仍在加载中，动画期间需保证不出现"动画结束 + 空白"的视觉断层 |
| FR-06 | **可关闭** | 提供"关闭切换动画"的开关（设置页或调试开关），尊重无障碍/减少动效偏好 |
| FR-07 | **降级** | 在低端机型或动画掉帧严重时自动降级为无动画 |

### 2.3 非功能性需求

| 维度 | 要求 |
|------|------|
| **性能** | 动画时长 ≤ 250ms，60fps，不阻塞 `onLoad`/`onShow` 中的数据请求 |
| **兼容** | 兼容 iOS/Android/PC 微信开发者工具；在 H5 调试模式下视觉一致 |
| **可维护** | 动画逻辑封装为 mixin 或独立模块，不侵入各 Tab 页面业务代码 |
| **无障碍** | 遵循系统"减少动效"偏好（微信小程序暂无官方 API，可通过运行环境检测降级） |
| **不打断** | 动画期间用户可继续点击其他 Tab，新点击应中断当前动画直接切换 |

### 2.4 约束条件

1. **不得改造为单页面 SPA**：5 个 Tab 必须保留为独立物理页面（受微信小程序 `tabBar` 机制约束，且 `wx.switchTab` 是唯一合法切换 API）。
2. **不得使用 `wx.navigateTo` 等 Tab 切换以外的 API** 模拟滑动。
3. **`wx.switchTab` 本身不提供过渡动画 hook**，所有动画需在页面层或全局遮罩层自实现。
4. **`custom-tab-bar` 是 Component 而非 Page**，无法直接覆盖页面内容做全屏遮罩；若需全局遮罩，需在每个 Tab 页面内放置 overlay。
5. **5 个 Tab 顺序固定**：首页 → 商城 → 宠物 → 订单 → 我的（来自 [custom-tab-bar/index.js#L1-L35](../../../pet-app/src/custom-tab-bar/index.js#L1-L35)），方向判定基于此顺序的索引差。
6. **电商 Tab 可被远程配置隐藏**（`isEcommerceNavEnabledFromStorage`），动画方向判定需基于**当前可见 Tab 列表**的索引，而非固定索引。
7. **遵守项目命名规范**：mixin 文件 camelCase（如 `tabSwitchTransition.js`），常量 UPPER_SNAKE_CASE，CSS 类名 BEM + kebab-case。

## 三、技术方案

### 3.1 方案对比

#### 方案 A：单页面 SPA + 自实现 Tab 容器

将 5 个 Tab 页面改造成组件，在单一容器页面内通过 `swiper` 或自定义滑动容器承载，由容器控制切换动画。

| 维度 | 评价 |
|------|------|
| 动画效果 | ⭐⭐⭐⭐⭐ 最自然，可做完整进出动画 |
| 改动量 | ❌ 极大，需重写 5 个 Tab 页面 + 路由结构 |
| 风险 | ❌ 破坏现有 `onLoad`/`onShow` 生命周期、分包预加载、`custom-tab-bar` 机制；可能违反微信审核规范（TabBar 必须使用原生配置） |
| 结论 | **不采用** |

#### 方案 B：拦截 `switchTab` + 全局遮罩层动画

在 `custom-tab-bar` 拦截点击，先在全屏遮罩上播放"滑出"动画，动画中途调用 `wx.switchTab`，新页面 `onShow` 时播放"滑入"动画。

| 维度 | 评价 |
|------|------|
| 动画效果 | ⭐⭐⭐⭐ 较完整，可做出连续滑动感 |
| 改动量 | ⚠️ 中等，需在每个 Tab 页面放置 overlay 容器 + 全局方向状态 |
| 风险 | ⚠️ `custom-tab-bar` 是 Component，遮罩需放在每个页面内；遮罩状态需全局同步 |
| 结论 | **备选** |

#### 方案 C：页面级 enter 动画（推荐）

每个 Tab 页面根节点包裹一个动画容器，在 `onShow` 时根据"上次离开的 Tab 索引"与"当前 Tab 索引"判定方向，播放对应的"从左/右滑入"动画。**不做离开动画**，依赖 `wx.switchTab` 的瞬时切换。

| 维度 | 评价 |
|------|------|
| 动画效果 | ⭐⭐⭐ 半边动画，但配合 250ms 时长已足够形成方向感 |
| 改动量 | ✅ 小，封装为 mixin + 1 个全局 store，各 Tab 页面仅引入 mixin + 包一层 view |
| 风险 | ✅ 低，不破坏现有生命周期，可灰度开关 |
| 缺点 | 离开动画缺失，"滑出"靠系统瞬时切换掩盖 |
| 结论 | **采用** |

#### 方案 D：方案 C 增强版——加"滑出"遮罩

在方案 C 基础上，于每个 Tab 页面顶部叠加一个 `position: fixed; inset: 0` 的"离开遮罩"，切换时：

1. 当前页 `onHide` 触发，遮罩从中心向目标方向滑出覆盖（150ms）；
2. `wx.switchTab` 已在覆盖前调用，新页 `onShow` 时遮罩从相反方向滑出消失（150ms）。

| 维度 | 评价 |
|------|------|
| 动画效果 | ⭐⭐⭐⭐ 完整进出动画 |
| 改动量 | ⚠️ 中等偏大，需精确控制遮罩时机，跨页面状态同步复杂 |
| 风险 | ⚠️ `onHide` 与 `onShow` 时序不严格保证，可能闪屏 |
| 结论 | **二期增强，本期不实现** |

### 3.2 选型与理由

**本期采用方案 C（页面级 enter 动画）**，理由：

1. 改动量小，可快速验证效果；
2. 不破坏现有页面结构与生命周期；
3. 通过 mixin 封装，5 个 Tab 页面接入成本均等；
4. 动画失败/降级时不影响功能；
5. 后续如需增强，可在方案 C 基础上叠加方案 D 的离开遮罩，向前兼容。

#### 3.3.2 方向判定算法

```javascript
// src/constants/tabTransition.js
export const TRANSITION_DIRECTION = {
  NONE: 'none',       // 无方向（首次进入、降级、回退兜底）
  FROM_LEFT: 'left',  // 新页从左侧滑入（目标在当前左侧）
  FROM_RIGHT: 'right' // 新页从右侧滑入（目标在当前右侧）
}

export const TRANSITION_DURATION_MS = 250
```

```javascript
// src/stores/tabTransition.js
import { defineStore } from 'pinia'
import { TRANSITION_DIRECTION } from '@/constants/tabTransition'

export const useTabTransitionStore = defineStore('tabTransition', () => {
  const lastVisibleTabIndex = ref(-1) // 上一次激活的可见 Tab 索引
  const pendingDirection = ref(TRANSITION_DIRECTION.NONE) // 待消费的方向

  function recordSwitch(fromVisibleIndex, toVisibleIndex) {
    if (fromVisibleIndex < 0 || toVisibleIndex < 0) {
      pendingDirection.value = TRANSITION_DIRECTION.NONE
    } else if (toVisibleIndex < fromVisibleIndex) {
      pendingDirection.value = TRANSITION_DIRECTION.FROM_LEFT
    } else if (toVisibleIndex > fromVisibleIndex) {
      pendingDirection.value = TRANSITION_DIRECTION.FROM_RIGHT
    } else {
      pendingDirection.value = TRANSITION_DIRECTION.NONE
    }
    lastVisibleTabIndex.value = toVisibleIndex
  }

  function consumeDirection() {
    const dir = pendingDirection.value
    pendingDirection.value = TRANSITION_DIRECTION.NONE
    return dir
  }

  return { lastVisibleTabIndex, pendingDirection, recordSwitch, consumeDirection }
})
```

#### 3.3.3 custom-tab-bar 改造

`custom-tab-bar` 是微信原生 Component，**不经 Vite 编译**，无法直接 `import` Pinia store。改用 `wx.setStorageSync` 中转：

```javascript
// src/custom-tab-bar/index.js（修改 switchTab 方法）
const TAB_TRANSITION_KEY = 'tab_transition_pending'

methods: {
  switchTab(e) {
    const index = e.currentTarget.dataset.index
    const item = this.data.list[index]
    const fromIndex = this.data.selected

    // 写入方向信息供目标页面 onShow 消费
    let direction = 'none'
    if (index < fromIndex) direction = 'left'
    else if (index > fromIndex) direction = 'right'
    try {
      wx.setStorageSync(TAB_TRANSITION_KEY, { direction, ts: Date.now() })
    } catch (_) {}

    wx.switchTab({
      url: item.pagePath,
      fail: () => { wx.reLaunch({ url: item.pagePath }) },
    })
  },
}
```

#### 3.3.4 Tab 页面 mixin

```javascript
// src/mixins/tabSwitchTransition.js
import { TRANSITION_DIRECTION, TRANSITION_DURATION_MS } from '@/constants/tabTransition'

const TAB_TRANSITION_KEY = 'tab_transition_pending'
const STALE_MS = 1000 // 超过 1s 视为陈旧方向，丢弃

export default {
  data() {
    return {
      tabEnterDirection: TRANSITION_DIRECTION.NONE,
      tabEnterActive: false,
    }
  },
  onShow() {
    this._applyTabEnterDirection()
  },
  methods: {
    _applyTabEnterDirection() {
      let direction = TRANSITION_DIRECTION.NONE
      try {
        const raw = wx.getStorageSync(TAB_TRANSITION_KEY)
        if (raw && typeof raw === 'object') {
          if (Date.now() - raw.ts < STALE_MS) direction = raw.direction
          wx.removeStorageSync(TAB_TRANSITION_KEY)
        }
      } catch (_) {}

      if (direction === TRANSITION_DIRECTION.NONE) return
      this.tabEnterDirection = direction
      this.tabEnterActive = true
      setTimeout(() => {
        this.tabEnterActive = false
      }, TRANSITION_DURATION_MS)
    },
  },
}
```

#### 3.3.5 页面模板接入

每个 Tab 页面根节点包裹动画容器：

```vue
<template>
  <view
    class="page"
    :class="tabEnterActive ? ('page--enter-' + tabEnterDirection) : ''"
  >
    <!-- 原页面内容 -->
  </view>
</template>

<script>
import tabSwitchTransition from '@/mixins/tabSwitchTransition'

export default {
  mixins: [tabSwitchTransition],
  // ...
}
</script>

<style lang="scss" scoped>
.page--enter-left {
  animation: tab-enter-from-left 250ms ease-out both;
}
.page--enter-right {
  animation: tab-enter-from-right 250ms ease-out both;
}

@keyframes tab-enter-from-left {
  from { transform: translateX(-12%); opacity: 0.6; }
  to   { transform: translateX(0);    opacity: 1; }
}
@keyframes tab-enter-from-right {
  from { transform: translateX(12%);  opacity: 0.6; }
  to   { transform: translateX(0);    opacity: 1; }
}
</style>
```

> 说明：位移幅度取 12% 而非 100%，避免出现"完整页面从屏外推入"的过长视觉；配合 250ms 时长，形成轻量的方向暗示。

#### 3.3.6 关闭开关与降级

- 在 [src/stores/dockConfig.js](../../../pet-app/src/stores/dockConfig.js) 或 miniAppConfig 远程配置中增加 `tabSwitchTransition: 'on' | 'off'`，默认 `on`。
- mixin 在 `_applyTabEnterDirection` 中读取该配置，若为 `off` 则直接 return。
- 降级：暂无运行时 fps 检测，先依赖用户手动关闭；二期可加 `wx.getPerformance` 监听掉帧自动降级。

## 五、对首次加载停顿的缓解评估

### 5.1 缓解程度：**部分缓解，不根治**

| 维度 | 评估 |
|------|------|
| 主观感受 | ✅ 显著改善——动画 250ms 期间用户注意力被引导，停顿感降低约 30~50% |
| 实际耗时 | ❌ 不变——网络请求 RTT、服务端处理、首屏渲染时间不被动画压缩 |
| 视觉断层 | ⚠️ 可能加剧——若动画结束（250ms）后数据仍未返回，从"滑入完成"到"内容出现"的空白会更突兀 |

### 5.2 推荐配套措施（与切换动画解耦，建议同步推进）

为彻底缓解首次加载停顿，建议在切换动画之外**并行**实施以下措施：

#### 5.2.1 骨架屏占位（强烈推荐）

为 5 个 Tab 主页面增加骨架屏，在数据未返回前展示结构化的灰块占位：

- 复用现有 [PageLoading](../../../pet-app/src/components/page-loading/PageLoading.vue) 组件，或新建 `TabSkeleton.vue`；
- 在 `loading === true && !data.length` 时展示骨架；
- 数据返回后淡入真实内容。

预期效果：彻底消除"纯白"视觉，主观停顿感降低 60~80%。

#### 5.2.2 分包预加载 `preloadRule`

在 `pages.json` 中配置 `preloadRule`，使用户进入首页时预加载其他 Tab 所在分包（虽 5 个 Tab 均在主包，但可预加载相关子包资源）：

```json
{
  "preloadRule": {
    "pages/index/index": {
      "network": "all",
      "packages": ["__APP__"]
    }
  }
}
```

#### 5.2.3 数据预取

在 `custom-tab-bar` 点击时（动画启动的同时）预先发起目标页面的关键请求：

- 需要将各 Tab 的 `loadBanners`/`loadCategories`/`loadOrders` 等抽离为 service 函数；
- `custom-tab-bar` 无法直接调用 service（不经 Vite 编译），可通过 `wx.setStorageSync` 写入"预取触发标记"，目标页面 `onLoad` 时检测标记并复用预取结果；
- 改动较大，建议二期实施。

#### 5.2.4 接口聚合与缓存

- 后端可考虑为每个 Tab 提供聚合接口（一次返回 banner + category + product），减少并发请求数；
- 前端可对"轮播图""分类"等低频变动数据做内存级缓存（5 分钟 TTL），二次进入直接命中缓存，`onLoad` 中再异步刷新。

### 5.3 综合结论

| 措施 | 对首次停顿的缓解 | 实施成本 | 建议 |
|------|------------------|----------|------|
| 切换动画（本需求） | 30~50%（主观） | 低 | 本期实施 |
| 骨架屏占位 | 60~80%（主观） | 中 | **强烈建议同期实施** |
| 分包预加载 | 5~10% | 低 | 本期实施 |
| 数据预取 | 20~30%（客观） | 高 | 二期 |
| 接口聚合 + 缓存 | 30~50%（客观） | 高（跨端） | 二期 |

> **建议**：本期切换动画 + 骨架屏 + 分包预加载三管齐下，可将首次停顿从"明显可感"降至"几乎无感"。

## 六、风险与注意事项

### 6.1 技术风险

| 风险 | 等级 | 缓解措施 |
|------|------|----------|
| `custom-tab-bar` 与目标页 `onShow` 时序不严格，storage 中转可能丢失 | 中 | 加 `ts` 时间戳，超时丢弃；mixin 中 `try/catch` 兜底 |
| 5 个 Tab 混入 mixin 后样式冲突 | 低 | SCSS 作用域 `scoped` + BEM 命名隔离 |
| 电商 Tab 隐藏后索引变化导致方向反向 | 中 | `custom-tab-bar` 内 `this.data.selected` 已是可见列表索引，直接使用即可 |
| 动画期间用户连续点击 Tab | 中 | `tabEnterActive` 期间允许中断，新方向覆盖旧方向 |
| iOS 与 Android 动画曲线感知差异 | 低 | 使用 `ease-out` 通用曲线；如差异明显再分平台适配 |

### 6.2 兼容性注意

- 微信基础库 ≥ 2.10.4 支持 `custom-tab-bar`，本项目已使用，无需额外兼容。
- CSS `@keyframes` 在微信小程序中支持良好，无需降级。
- Pinia store 在小程序运行时无法被 `custom-tab-bar` 直接访问（已用 storage 中转规避）。

### 6.3 验收边界

- 本需求**不**包含骨架屏、数据预取、接口聚合的实施，仅评估其作为配套措施的可行性。
- 本需求**不**修改 5 个 Tab 页面的业务逻辑，仅在根节点加动画 class 与引入 mixin。

### 9.2 与方案的偏差说明

| 偏差点 | 原方案 | 实际实现 | 原因 |
|--------|--------|----------|------|
| Store 实现 | Pinia（`defineStore`） | reactive state 模式 | 项目 `src/stores/` 现有两个 store（`dockConfig.js`/`themeAssets.js`）均采用 reactive state 模式，未引入 Pinia；为保持代码风格一致，采用相同模式 |
| 动画样式位置 | 各 Tab 页面 `<style scoped>` 内重复定义 | `src/App.vue` 全局 `<style>` 块统一定义 | 避免在 5 个页面重复定义 `@keyframes`，便于统一维护；class 选择器 `.tab-enter--left`/`.tab-enter--right` 不会污染其他元素 |
| 方向信息中转字段 | 仅 `{ direction, ts }` | `{ direction, fromIndex, toIndex, ts }` | 增加 `fromIndex`/`toIndex` 便于 H5 调试时通过 `getLastTabSwitch()` 查看完整切换信息 |
| mixin 中 API | 文档示例使用 `wx.xxx` | 实际使用 `uni.xxx` | 项目规范要求"使用 uni.xxx 而非 wx.xxx（便于 H5 兼容）"；mixin 经 Vite 编译，支持 uni API；`custom-tab-bar/index.js` 仍是原生 Component 不经编译，继续用 `wx.xxx` |
