## 一、需求关键点回顾

商户对"底部导航配置"功能的需求可以归纳为两条：

1. **发布频率跟随版本更新**
   商户希望有渠道发布底部导航配置，但发布频率可以仅跟随小程序版本更新，**不需要随时更新，也不要求即时同步至所有 C 端用户**。

2. **可配置项覆盖 3 类**
   - 5 个导航图标（含选中态与非选中态）
   - 5 个导航图标的**尺寸**
   - 5 个导航图标的**文案**（或不使用文案）

## 二、当前实现概览（三端架构）

### 2.1 后端（pet-app-backend）

- **Schema**：[config/schemas/dock.v2.json](../../pet-app-backend/config/schemas/dock.v2.json)
  - 固定 5 个 slot（`minItems: 5, maxItems: 5`）
  - 每个 slot 必填字段：`pageId / pageName / route / navMode / enabled / labelStyle / iconDefault / iconActive`
  - `labelStyle` 含 `color / activeColor / fontSize(10-20) / isBold`
  - **没有"图标尺寸"字段**
  - **没有"是否显示文案"开关**，且 `pageName` 强制正则 `^[\u4e00-\u9fa5]{2}$`（必须 2 个汉字）

- **接口**（[routes/admin/miniAppConfigRoutes.js](../../pet-app-backend/routes/admin/miniAppConfigRoutes.js)）：
  - `GET /admin/mini-app-config/dock` 获取配置详情
  - `PUT /admin/mini-app-config/dock/draft` 保存草稿
  - `POST /admin/mini-app-config/dock/publish` 发布
  - `POST /admin/mini-app-config/dock/publish/rollback` 回滚到上一版本
  - `POST /admin/mini-app-config/dock/validate` 校验
  - C 端：`GET /mini-app-config`（带 version / etag）

- **机制**：草稿/发布分离、版本号自增、发布历史、回滚、Redis 缓存 + DB fallback 已具备 ✅

### 2.2 管理端（pet-app-admin-web）

- **类型**：[src/types/miniAppConfig.ts](../../pet-app-admin-web/src/types/miniAppConfig.ts) `DockSlot` 完整对齐后端 schema
- **页面**：[src/views/mini-app-config/Dock.vue](../../pet-app-admin-web/src/views/mini-app-config/Dock.vue) 已支持图标、文案、显隐、尺寸（fontSize 文字尺寸）、电商开关（mall/order 同开同关）
- **机制**：草稿编辑、发布、回滚、发布历史、预览面板 ✅

### 2.3 小程序前端（pet-app）

- **custom-tab-bar 单例组件**：[src/custom-tab-bar/index.js](../../pet-app/src/custom-tab-bar/index.js)
  - 由微信框架托管，全小程序 1 个实例，5 个 Tab 页面共享
  - `lifetimes.attached` 首次创建时 setData 一次
  - `pageLifetimes.show` 每次 Tab 页 onShow 时 setData 刷新

- **配置读取**：[src/utils/tabBarConfig.js](../../pet-app/src/utils/tabBarConfig.js)
  - `buildVisibleTabList()` 与 `getBackgroundFromStorage()` **直接从 storage 读取** `mini_app_config_dock`
  - storage 为空时直接 `return DEFAULT_TAB_LIST`（硬编码 `/static/tabbar/*.png`），**没有内存兜底**

- **配置同步**：[src/utils/tabPageGuard.js](../../pet-app/src/utils/tabPageGuard.js)
  - `syncTabBarSelected(idx)` 在每个 Tab 页 onShow 中调用，通过 `getTabBar().setData()` 显式同步 selected / list / background

- **配置拉取与缓存**：[src/stores/dockConfig.js](../../pet-app/src/stores/dockConfig.js)
  - `bootstrapDockConfig()`：启动时同步读缓存 + 异步拉远程
  - `refreshDockConfigFromRemote()`：在 App.onShow 中**每次回前台都调用**
  - 三级兜底：remote → cache → bundled default
  - **关键缺陷**：custom-tab-bar 完全绕过 Pinia store，自己直读 storage，未享受三级兜底

- **DEFAULT_TAB_LIST vs bundled default**：两份独立硬编码
  - `tabBarConfig.js` 模块内 `DEFAULT_TAB_LIST`（指向 `/static/tabbar/*.png`）
  - [src/config/dock.theme.default.json](../../pet-app/src/config/dock.theme.default.json) bundled default
  - 两者**未对齐**，未来调整 bundled default 时 `DEFAULT_TAB_LIST` 不会同步

## 三、需求 vs 当前实现 对照分析

| 需求项 | 当前实现 | 状态 | 说明 |
|---|---|---|---|
| 1. 发布跟随版本，不要求即时同步 | 后端已有 draft/publish/rollback + version 机制 | ✅ 后端支持 | 后端架构完全对齐 |
| 1. 发布跟随版本，不要求即时同步 | C 端 App.onShow 每次 `refreshDockConfigFromRemote()` | ❌ 过度活跃 | 与"跟随版本"诉求不符，每次回前台都拉远程 |
| 2.1 配置 5 个图标双态（选中/非选中） | `iconDefault` / `iconActive` | ✅ 已支持 | Schema + 管理端 UI 完整 |
| 2.2 配置图标尺寸 | 仅 `labelStyle.fontSize`（文字尺寸 10-20） | ❌ 缺失 | **Schema 无图标尺寸字段**，无法满足 |
| 2.3 配置文案 / 或不使用文案 | `pageName` 必填正则 `^[\u4e00-\u9fa5]{2}$` | ❌ 不支持 | **强制 2 个汉字，不能为空、不能关闭** |

### 3.1 关键问题诊断

**问题 1：Schema 缺"图标尺寸"字段**
- 当前仅有 `labelStyle.fontSize`（10-20 范围），是文字大小
- 图标 `<image class="tab-icon">` 的尺寸由 [src/custom-tab-bar/index.wxss](../../pet-app/src/custom-tab-bar/index.wxss) 硬编码，且 `prominent` 仅 pet 一个 boolean 开关（"图标偏大"二态），无法精细配置每个 tab 的图标尺寸

**问题 2：Schema 不支持"不使用文案"**
- `pageName` 必填且正则限定 2 个汉字，导致管理端无法配置"无文案"样式
- 实际视觉上 5 个 tab 全部带文字，缺少"纯图标"模式

**问题 3：C 端拉取策略过度活跃**
- [src/App.vue#L22-L26](../../pet-app/src/App.vue#L22-L26) 在 `onShow` 中无条件 `refreshDockConfigFromRemote()`
- 与"跟随版本更新，不要求即时同步"诉求冲突
- 配合 storage TTL 过期清理 → 用户回前台时容易出现短暂的"图标回退默认"现象

**问题 4：custom-tab-bar 绕过 Pinia store 三级兜底**
- `tabBarConfig.js` 直读 storage，不读 `getEffectiveDockConfig()`
- storage 被 `clearDockCache()`（商户撤回 / TTL 过期 / 写入失败）清空时立即回退 `DEFAULT_TAB_LIST`
- 单例 `data.list` 中保存的旧值被代码主动覆盖，未利用

**问题 5：两套"默认值"未对齐**
- `tabBarConfig.js` 内的 `DEFAULT_TAB_LIST` 与 `dock.theme.default.json` 独立硬编码
- 商户撤回发布时，store 走 bundled default，custom-tab-bar 走 DEFAULT_TAB_LIST，可能出现样式不一致

## 四、是否需要调整：**是，建议调整**

调整范围聚焦三个层面：

1. **Schema 层**：补齐"图标尺寸"和"是否显示文案"两个字段
2. **C 端拉取策略**：从"每次回前台拉远程"改为"启动时拉一次 + 版本号比对 + 手动刷新入口"
3. **C 端 custom-tab-bar 兜底链路**：从"直读 storage"改为"读 Pinia store effectiveConfig + 模块级内存缓存"

**不调整的部分**：
- 后端草稿/发布/回滚/版本号机制：已对齐需求，保留
- 管理端 UI 主结构：保留，仅新增 2 个控件
- custom-tab-bar 单例本质：保留，不重写

## 五、建议调整方案

### 5.1 后端 Schema 扩展（dock.v3.json）

**新增字段**：

| 字段路径 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| `slots[].iconSize` | integer | 否 | minimum 40, maximum 120, 单位 rpx | 图标尺寸（不传时使用 wxss 默认值） |
| `slots[].showLabel` | boolean | 是 | - | 是否显示文案，false 时 pageName 可为空字符串 |

**字段调整**：

| 字段 | 当前约束 | 调整后约束 | 原因 |
|---|---|---|---|
| `slots[].pageName` | 必填，正则 `^[\u4e00-\u9fa5]{2}$` | 必填，但当 `showLabel=false` 时允许空字符串 | 支持"不使用文案" |

**Schema 版本策略**：
- 升级到 `dock.v3.json`，保留 `dock.v2.json` 用于历史兼容回滚
- `dockDefaultConfig.js` 同步升级到 v3 结构（增加 `iconSize` 默认值、`showLabel: true`）
- 后端 validator 增加对 v3 的校验，已发布 v2 配置仍能被读取（按 version 选择 schema）

### 5.2 管理端调整（pet-app-admin-web）

#### 5.2.1 类型定义扩展

[src/types/miniAppConfig.ts](../../pet-app-admin-web/src/types/miniAppConfig.ts) `DockSlot` 增加字段：

```typescript
export interface DockSlot {
  pageId: string
  pageName: string

  navMode?: string
  enabled?: boolean
  labelStyle: DockLabelStyle
  iconDefault: string
  iconActive: string

  showLabel: boolean        // 新增：是否显示文案

```

#### 5.2.2 Dock.vue 新增控件

[src/views/mini-app-config/Dock.vue](../../pet-app-admin-web/src/views/mini-app-config/Dock.vue) 每个 slot 配置区增加：

- **图标尺寸**：`<el-input-number v-model="tab.iconSize" :min="40" :max="120" :step="4" />`（单位 rpx）
- **显示文案**：`<el-switch v-model="tab.showLabel" />`
  - 当 `showLabel=false` 时，禁用"文案"输入框并清空 `pageName`
- **预览面板** [src/components/DockPreviewPanel.vue](../../pet-app-admin-web/src/components/DockPreviewPanel.vue) 同步：
  - `<img :style="{ width: tab.iconSize + 'rpx', height: tab.iconSize + 'rpx' }" />`
  - `<span v-if="tab.showLabel">{{ tab.text }}</span>`

### 5.3 C 端调整（pet-app）

#### 5.3.1 拉取策略：从"每次回前台拉远程"改为"启动时拉 + 版本号比对"

**当前**（[src/App.vue#L22-L26](../../pet-app/src/App.vue#L22-L26)）：

```javascript
onShow() {
  refreshDockConfigFromRemote().catch(() => {})   // 每次回前台都拉
}
```

**调整为**：

```javascript
onShow() {
  // 仅当离开超过 N 分钟（如 30 分钟）才主动拉取，避免频繁打扰
  maybeRefreshDockConfigIfStale().catch(() => {})
}
```

**新增工具函数**（`src/stores/dockConfig.js`）：

```javascript
const STALE_THRESHOLD_MS = 30 * 60 * 1000  // 30 分钟

export function maybeRefreshDockConfigIfStale() {
  const lastFetchedAt = state.lastFetchedAt || 0
  if (Date.now() - lastFetchedAt < STALE_THRESHOLD_MS) {
    return Promise.resolve({ updated: false, source: state.source })
  }
  return refreshDockConfigFromRemote()
}
```

**保留启动时拉取**：`bootstrapDockConfig()` 不变，启动时仍同步读缓存 + 异步拉远程。

#### 5.3.2 手动刷新入口

在"我的"页（[src/pages/mine/mine.vue](../../pet-app/src/pages/mine/mine.vue)）「设置」入口附近增加：

- "检查底部导航更新" 按钮（仅在设置子包或开发者面板中显示）
- 调用 `refreshDockConfigFromRemote()` 后 `uni.showToast({ title: '已是最新' })`
- 满足需求 1 中"商户不要求即时同步，但保留人工触发渠道"的诉求

#### 5.3.3 custom-tab-bar 兜底链路重构

**目标**：让 custom-tab-bar 享受 Pinia store 的三级兜底，storage 被清也不回退默认。

**方案 A（推荐）**：`tabBarConfig.js` 改读 Pinia store

```javascript
// src/utils/tabBarConfig.js
import { getEffectiveDockConfig } from '@/stores/dockConfig'

export function buildVisibleTabList() {
  const effective = getEffectiveDockConfig()   // 永远不会为 null（模块顶层 bundled default 兜底）
  return transformDockToTabList(effective)
}

function transformDockToTabList(dockConfig) {
  // dock 格式（slots + iconDefault/iconActive/labelStyle）→ tab-bar list 格式
  // 增加 iconSize / showLabel 字段透传
}
```

**方案 B（最小改动）**：保留直读 storage，但加模块级内存缓存

```javascript
// src/utils/tabBarConfig.js
let lastSuccessList = null
let lastSuccessBackground = null

export function buildVisibleTabList() {
  const dockConfig = getDockConfigFromStorage()
  if (!dockConfig || !Array.isArray(dockConfig.slots)) {
    return lastSuccessList ?? DEFAULT_TAB_LIST   // ← 优先用上次成功的内存值
  }
  const list = computeList(dockConfig)
  lastSuccessList = list
  return list
}
```

**推荐方案 A**，因为：
- 复用 store 已有的三级兜底逻辑，避免重复造轮子
- 商户撤回时 `state.effectiveConfig` 自动 fallback 到 bundled default，与 store 行为一致
- 模块级内存缓存在方案 A 中由 Pinia reactive state 天然提供

#### 5.3.4 DEFAULT_TAB_LIST 与 bundled default 对齐

- **短期**：保留 `DEFAULT_TAB_LIST` 作为最后兜底，但确保其字段与 `dock.theme.default.json` 完全一致（可由 `getBundledDefaultDockConfig()` 动态生成）
- **长期**：方案 A 落地后，`DEFAULT_TAB_LIST` 退化为"store 未初始化时的引导值"，仅在 `attached` 触发前使用

#### 5.3.5 custom-tab-bar index.wxml 适配新字段

[src/custom-tab-bar/index.wxml](../../pet-app/src/custom-tab-bar/index.wxml) 增加 iconSize / showLabel 渲染：

```xml
<image
  class="tab-icon {{item.prominent ? 'tab-icon--pet' : ''}}"
  src="{{selected === index ? item.selectedIconPath : item.iconPath}}"
  mode="aspectFit"
  style="width: {{item.iconSize || 48}}rpx; height: {{item.iconSize || 48}}rpx;"
/>
<text
  wx:if="{{item.showLabel !== false}}"
  class="tab-label {{item.prominent ? 'tab-label--pet' : ''}}"
  style="..."
>{{item.text}}</text>
```

## 六、改进点与风险点对比

### 6.1 改进点

| 改进点 | 当前痛点 | 调整后收益 |
|---|---|---|
| Schema 增加 iconSize / showLabel | 商户无法配置图标尺寸、无法关闭文案 | 完整对齐需求 2.2 / 2.3 |
| C 端拉取策略改为"启动 + stale 阈值" | 每次回前台拉远程，资源浪费、出现图标回退 | 对齐需求 1"跟随版本"，减少网络请求 |
| custom-tab-bar 读 Pinia store | 直读 storage，三级兜底失效 | 享受 remote → cache → bundled default 三级兜底，图标回退问题根除 |
| 模块级内存缓存兜底 | 单例 data.list 被无条件覆盖 | 单例旧值被利用，storage 临时为空也不闪烁 |
| DEFAULT_TAB_LIST 与 bundled default 对齐 | 两套硬编码，未来不同步风险 | 单一数据源，维护成本下降 |
| 手动刷新入口 | 商户更新后用户无法主动触发 | 兼顾"不即时同步"与"用户可主动更新" |

### 6.2 风险点

| 风险点 | 影响 | 缓解措施 |
|---|---|---|
| Schema v2 → v3 升级 | 已发布 v2 配置读取兼容性 | 保留 v2 schema 文件，按 version 选择；新增字段为可选/默认值 |
| 管理端历史草稿格式不兼容 | 老草稿打开报错 | 加载草稿时 `mergeDockConfig(defaultV3, draftV2)` 兼容合并，缺省字段补默认值 |
| C 端 stale 阈值导致商户更新延迟生效 | 商户发布后用户最长 30 分钟才看到 | 提供"我的"页手动刷新入口；并在 `refreshDockConfigFromRemote` 成功后通过 `subscribeDockConfig` listener 触发 custom-tab-bar 主动 setData |
| Pinia store 在 custom-tab-bar attached 时尚未初始化 | 首次渲染读 store 返回 bundled default | 模块顶层 `const bundledDefault = getBundledDefaultDockConfig()` 已是兜底，attached 时即使 store 未初始化也能拿到合理值 |
| `showLabel=false` 导致 tab 高度过低 | 视觉破坏 | wxss 中 `.tab-item` 设置 min-height，无文案时仍保持触控区 |
| 图标尺寸过大破坏布局 | 视觉破坏 | Schema 限制 `iconSize` 40-120 rpx；管理端预览面板实时预览；wxss `.tab-bar` 使用 flex 均分 + overflow hidden |
| 三端协同成本 | 后端 Schema 改动需三端同步 | 严格按 multi-project.md §2.1 流程：先规范文档 → 后端实现 → 后端自测 → 前端对接 → 联调 |

### 6.3 不调整的风险

如果不调整，将持续存在以下问题：

1. 商户需求 2.2 / 2.3 无法满足（功能缺口）
2. C 端每次回前台拉远程，与"跟随版本"诉求不符
3. 图标回退静态资源的现象无法根治（已在前序对话中确认根因）

## 八、版本与回滚预案

### 8.1 实施版本

- 后端：`v1.0.x`（具体版本号见 `docs/项目开发说明-后端.md` §版本号规则）
- 管理端：`v0.x.0`
- 小程序前端：`v0.x.0`

### 8.2 回滚策略

| 故障范围 | 回滚动作 |
|---|---|
| 仅 v3 Schema 校验有问题 | 后端临时把 `dock.v2.json` 设为活跃 schema，v3 配置降级为 v2 读取（丢失 iconSize/showLabel，但能正常显示） |
| C 端 custom-tab-bar 改造有问题 | 回退 `tabBarConfig.js` 到直读 storage 版本（即当前实现），保持 v2 兼容 |
| C 端拉取策略有问题 | App.onShow 恢复为 `refreshDockConfigFromRemote()` |
| 管理端 UI 改造有问题 | 隐藏新增控件，复用 v2 字段提交 |

### 8.3 灰度策略（可选）

如果需要更稳妥的灰度：

1. 后端先发布 v3 schema 但 `dockDefaultConfig` 不变（保留 v2 默认值）
2. 管理端先支持 v3 字段编辑，但默认值与 v2 一致
3. C 端先支持 v3 字段读取，但渲染时 `iconSize || 48` 兜底
4. 一周内无问题后，商户可开始尝试配置 iconSize / showLabel

## 九、结论

当前实现**部分满足**商户需求：

- ✅ 需求 1（发布跟随版本）：后端架构已支持，但 C 端拉取策略过度活跃，与"不要求即时同步"诉求不符
- ✅ 需求 2.1（5 图标双态）：完整支持
- ❌ 需求 2.2（图标尺寸）：Schema 缺字段，需扩展 v3
- ❌ 需求 2.3（文案或不使用文案）：Schema 强制 pageName 为 2 字汉字，需扩展 v3

同时存在一个已确认的隐性缺陷：**custom-tab-bar 绕过 Pinia store 直读 storage**，导致商户撤回 / TTL 过期 / 写入失败时图标回退静态资源。

**建议按 §五 方案调整**，预计涉及后端 Schema 升级、管理端 2 个控件新增、C 端拉取策略与兜底链路重构。改动可控，回滚预案明确，与现有 draft/publish/rollback 机制完全兼容。
