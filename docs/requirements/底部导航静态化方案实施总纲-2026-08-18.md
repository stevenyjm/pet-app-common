## 一、决策记录

### 1.1 决策背景

商户对"底部导航配置"功能的核心诉求：
1. 发布频率跟随版本更新，不要求即时同步至所有 C 端用户
2. 可配置 5 个导航图标双态（选中/非选中）、图标尺寸、文案（或不使用文案）

经可行性分析（详见 [可行性分析文档](./底部导航静态化方案可行性分析-2026-08-18.md)），确认：
- 静态化方案**完全满足**需求 1（跟随版本更新）
- 静态化方案**技术上满足**需求 2.1/2.2/2.3（由开发硬编码实现）
- 静态化方案**彻底根除**隐性缺陷（custom-tab-bar 绕过 Pinia store 直读 storage）

### 1.2 决策结论

**采用静态化方案**：彻底移除"底部导航配置"动态功能，底部导航样式由开发人员硬编码控制，随小程序版本迭代一同更新。原动态配置方案归档备案，详见 [备案文档](./底部导航动态配置方案-备案-2026-08-18.md)。

### 1.3 决策理由

| 维度 | 静态化方案 | 动态配置方案（原方案） |
|------|-----------|----------------------|
| 满足需求 1（跟随版本） | ✅ 完全满足，天然对齐 | ✅ 满足，但 C 端拉取策略过度活跃，需额外优化 |
| 满足需求 2（图标/尺寸/文案） | ✅ 技术上由开发实现 | ✅ 商户自助配置 |
| 根除隐性缺陷 | ✅ 彻底根除，无动态数据依赖 | ⚠️ 需重构 custom-tab-bar 兜底链路 |
| 实施成本 | 低（删除动态链路，保留静态壳） | 中（Schema 升级 + 管理端新增控件 + C 端重构） |
| 维护成本 | 低（变更走发版流程） | 中（三端协同维护） |
| 运营灵活性 | 低（每次变更需发版） | 高（商户自助配置） |

**选择静态化的关键考量**：商户已明确表态"发布频率可跟随版本更新，不需要随时更新"，运营灵活性非核心诉求，优先选择更低实施成本和更低维护风险的方案。

## 四、架构变更对比

### 4.1 变更前（动态配置）

```
商户管理端 Dock.vue
  ↓ PUT /admin/mini-app-config/dock/draft
后端 miniAppConfigService.js
  ↓ 存入 mini_app_config 表
后端 GET /mini-app-config/public
  ↓ C 端拉取
pet-app stores/dockConfig.js（三级兜底：remote → cache → bundled default）
  ↓ 写入 storage
pet-app utils/tabBarConfig.js（直读 storage ← 缺陷根因）
  ↓ buildVisibleTabList()
pet-app custom-tab-bar/index.js（setData 渲染）
```

### 4.2 变更后（静态化）

```
开发人员修改 src/utils/tabBarConfig.js 中的 DEFAULT_TAB_LIST
  ↓（随版本编译打包）
pet-app custom-tab-bar/index.js（直接使用 DEFAULT_TAB_LIST 渲染）
```

**链路从 7 层缩减为 1 层**，无运行时动态数据依赖。

## 五、风险与缓解

| 风险点 | 影响 | 缓解措施 |
|--------|------|---------|
| 电商导航开关丢失 | 静态化后 mall/order 不再支持隐藏 | 当前业务场景下 5 个 Tab 恒启用；如未来需隐藏，由开发修改 `DEFAULT_TAB_LIST` 并发版 |
| 动画开关丢失 | `tabSwitchTransition` 配置不再可用 | 动画开关改为代码内静态常量（默认开启或关闭由开发决定） |
| 后端 dock 数据残留 | `mini_app_config` 表中已有 dock 发布记录 | 保留数据不删除（不影响功能），仅在 registry 中取消注册 |
| themeAssets 受波及 | 移除 dock 逻辑时误删 themeAssets 代码 | 严格按任务清单逐项操作，每个步骤自测 themeAssets 接口 |
| 商户未来需要恢复动态配置 | 需要重新实现 | 参见 [备案文档](./底部导航动态配置方案-备案-2026-08-18.md)，完整记录了原架构 |
| 管理端侧边栏菜单残留 | 配置总览页仍有 dock 入口 | 阶段 3 任务 3.8 明确移除入口卡片 |
