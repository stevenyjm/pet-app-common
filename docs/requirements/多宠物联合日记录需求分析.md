# 多宠物联合日记录需求分析

## 一、需求概述

### 1.1 需求背景

当前日记录系统中，每条记录仅关联一个宠物。但实际使用场景中，存在多个宠物共同参与同一活动的情况：

| 场景 | 说明 |
|------|------|
| 共同进食 | 多只宠物一起用餐，用户无法细分每只宠物的食量 |
| 共同运动 | 多只宠物一起外出玩耍，记录内容高度相似 |
| 群体活动 | 如多只宠物一起洗澡、美容等 |

### 1.2 核心问题

1. **展示问题**：联合记录如何在各宠物的日记录列表中展示？如何标识关联宠物？
2. **创建/编辑问题**：如何选择关联宠物？如何处理宠物移除后的降级逻辑？
3. **存储问题**：数据库如何设计以支持联合记录？

### 1.3 需求合理性评估

| 评估维度 | 分析 | 结论 |
|----------|------|------|
| **用户价值** | 减少重复录入，提升记录效率 | ✅ 高价值 |
| **使用频率** | 多宠物用户日常操作 | ✅ 高频场景 |
| **技术可行性** | 需要调整数据模型和API | ⚠️ 中等复杂度 |
| **向后兼容** | 不影响现有单宠物记录 | ✅ 可兼容 |

## 二、现有数据模型分析

### 2.1 当前表结构（后端实际模型）

#### `pet_daily_record` — 日记录主表

| 字段 | 类型 | 说明 |
|------|------|------|

| `pet_id` | BIGINT | 宠物ID（单宠物，不可为空） |

| `daily_mood` | VARCHAR(32) | 心情 |

| `daily_stool_health` | VARCHAR(32) | 排便状态 |
| `create_time` | DATE | 创建时间 |
| `update_time` | DATE | 更新时间 |

#### `pet_meal_session` — 餐食记录

| 字段 | 类型 | 说明 |
|------|------|------|
| `session_id` | BIGINT | 主键（自增） |
| `daily_record_id` | BIGINT | 关联日记录ID（不可为空） |
| `period` | VARCHAR(16) | 餐段（不可为空） |
| `meal_time` | TIME | 用餐时间 |
| `post_meal_status` | VARCHAR(32) | 餐后状态 |
| `nutrition_reference` | TEXT | 营养参考 |
| `remark` | VARCHAR(500) | 备注 |
| `sort_order` | TINYINT | 排序（默认0） |
| `create_time` | DATE | 创建时间 |

#### `pet_exercise_session` — 运动记录

| 字段 | 类型 | 说明 |
|------|------|------|
| `session_id` | BIGINT | 主键（自增） |
| `daily_record_id` | BIGINT | 关联日记录ID（不可为空） |
| `pet_id` | BIGINT | 宠物ID（不可为空） |
| `record_date` | DATEONLY | 记录日期（不可为空） |
| `location` | VARCHAR(32) | 运动地点（不可为空） |
| `start_time` | TIME | 开始时间（不可为空） |
| `duration_minutes` | SMALLINT | 运动时长（不可为空） |
| `assessment` | VARCHAR(32) | 运动评估 |
| `ext_json` | JSON | 扩展字段 |
| `create_time` | DATE | 创建时间 |
| `update_time` | DATE | 更新时间 |

### 2.2 当前问题

1. **单宠物限制**：`pet_id` 字段为单值，无法支持多宠物
2. **数据冗余**：共同活动需为每只宠物创建相同记录
3. **一致性风险**：修改一条记录时，其他宠物的相同记录不同步
4. **职责混淆**：`pet_daily_record` 同时承担"日期容器"和"宠物状态存储"两个职责

### 2.3 关键发现

`PetExerciseSession` 已经同时拥有 `record_date` 和 `pet_id` 字段，说明后端已经预见到了"直接存储日期"的需求。

## 三、联合记录范围定义

### 3.1 联合范围决策

| 记录类型 | 是否支持联合 | 原因 |
|----------|-------------|------|
| **每日状态（mood/weight/stool）** | ❌ 不支持 | 状态属性具有个体性，每只宠物状态不同 |
| **餐食记录（meal_session）** | ✅ 支持 | 多宠物可共同进食，食物内容相同 |
| **运动记录（exercise_session）** | ✅ 支持 | 多宠物可共同运动，地点时间相同 |

### 3.2 设计原则

1. **每日状态仍按单宠物存储**：`pet_daily_record` 重命名为 `pet_daily_status`，每宠物每日一条
2. **餐食/运动记录支持多宠物关联**：通过关联表实现多宠物共享同一条记录
3. **结构统一**：单宠物记录和联合记录使用相同的数据结构，无特殊标记
4. **直接存储日期**：`pet_meal_session` 和 `pet_exercise_session` 直接存储 `record_date`，去除对 `daily_record_id` 的依赖

| 条件 | 勾选选项状态 | 说明 |

宠物数量以当前宠物列表（`pets.length`）为准；禁用态下勾选框不可点击，可附 `toast` 提示「至少需要 2 只宠物」。

| 区域 | 变化 |

| **顶栏左上角** | ⚙ 设置按钮隐藏 |

#### 4.3.4 联合记录点击校验

当「进行联合记录」被勾选时，点击「餐食」或「运动」的响应规则：

| 已勾选宠物数量 | 点击「餐食」/「运动」行为 |
|---------------|--------------------------|
| ≥ 1 | 进入对应录入页（携带已勾选宠物列表） |
| 0 | **不响应跳转**，提示「请勾选至少一个宠物」 |

- 再次点击「进行联合记录」勾选框 → 取消勾选
- 恢复常规交互：宠物选项恢复右侧选中标记、点击切换宠物/进入信息页、顶栏 ⚙ 恢复显示、底部文案恢复「记录」
- 已勾选的宠物状态清空

## 六、后端存储方案设计

### 6.1 方案对比

| 方案 | 实现方式 | 优点 | 缺点 | 推荐度 |
|------|----------|------|------|--------|
| **方案A：扩展字段** | 添加 `pet_ids` JSON 数组字段 | 改动小 | 查询性能差，双数据源 | ★★★☆☆ |
| **方案B：关联表（推荐）** | 新建 `pet_record_pet` 关联表 | 数据规范化，查询高效 | 需要新增表和API | ★★★★★ |
| **方案C：独立表** | 新建联合记录表 | 逻辑清晰 | 改动大，兼容性差 | ★★★☆☆ |

### 6.2 推荐方案：关联表

#### 6.2.1 表结构调整

##### 1. `pet_daily_record` → `pet_daily_status`（重命名）

| 字段 | 类型 | 变更 | 说明 |
|------|------|------|------|
| `daily_record_id` | BIGINT | → `status_id` | 主键重命名 |
| `pet_id` | BIGINT | 不变 | 宠物ID |
| `record_date` | DATEONLY | 不变 | 记录日期 |
| `daily_mood` | VARCHAR(32) | 不变 | 心情 |
| `daily_weight_kg` | DECIMAL(6,2) | 不变 | 体重 |
| `daily_stool_health` | VARCHAR(32) | 不变 | 排便状态 |
| **复合唯一键** | — | ✅ 新增 | `(pet_id, record_date)` |

##### 2. `pet_meal_session` 调整

| 字段 | 类型 | 变更 | 说明 |
|------|------|------|------|
| `daily_record_id` | BIGINT | ✅ 移除 | 不再关联日记录 |
| `record_date` | DATE | ✅ 新增 | 直接存储日期 |
| `period` | VARCHAR(16) | 不变 | 餐段 |
| `meal_time` | TIME | 不变 | 用餐时间 |

##### 3. `pet_exercise_session` 调整

| 字段 | 类型 | 变更 | 说明 |
|------|------|------|------|
| `daily_record_id` | BIGINT | ✅ 移除 | 不再关联日记录 |
| `pet_id` | BIGINT | ✅ 移除 | 不再存储单宠物ID |

##### 4. 新建 `pet_record_pet` — 记录-宠物关联表

```sql
CREATE TABLE pet_record_pet (
  id              BIGINT       NOT NULL AUTO_INCREMENT PRIMARY KEY,
  session_id      BIGINT       NOT NULL COMMENT '餐食/运动会话ID',
  session_type    VARCHAR(16)  NOT NULL COMMENT 'meal/exercise',
  pet_id          BIGINT       NOT NULL COMMENT '宠物ID',
  create_time     DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_session_pet (session_id, session_type, pet_id),
  KEY idx_pet (pet_id),
  KEY idx_session (session_id)
);
```

#### 6.2.2 数据写入逻辑

**创建单宠物餐食记录**：

```sql
-- 1. 创建每日状态
INSERT INTO pet_daily_status (pet_id, record_date, daily_mood, ...)
VALUES (1, '2026-07-07', '开心', ...);

-- 2. 创建餐食会话（直接存储日期）
INSERT INTO pet_meal_session (record_date, period, meal_time, ...)
VALUES ('2026-07-07', '早餐', '07:30:00', ...);

-- 3. 建立关联（单宠物）
INSERT INTO pet_record_pet (session_id, session_type, pet_id)
VALUES (456, 'meal', 1);
```

**创建联合餐食记录**：

```sql
-- 1. 创建每日状态（每只宠物单独创建）
INSERT INTO pet_daily_status (pet_id, record_date, daily_mood, ...)
VALUES (1, '2026-07-07', '开心', ...),
       (2, '2026-07-07', '一般', ...),
       (3, '2026-07-07', '兴奋', ...);

-- 2. 创建餐食会话（直接存储日期，无 pet_id）
INSERT INTO pet_meal_session (record_date, period, meal_time, ...)
VALUES ('2026-07-07', '早餐', '07:30:00', ...);

-- 3. 建立关联（多宠物）
INSERT INTO pet_record_pet (session_id, session_type, pet_id)
VALUES (456, 'meal', 1),
       (456, 'meal', 2),
       (456, 'meal', 3);
```

#### 6.2.3 查询逻辑

**查询宠物1的所有餐食记录（含联合记录）**：

```sql
SELECT ms.*, prp.pet_id
FROM pet_meal_session ms
JOIN pet_record_pet prp ON ms.session_id = prp.session_id AND prp.session_type = 'meal'
WHERE prp.pet_id = 1
  AND ms.record_date = '2026-07-07';
```

**查询餐食记录456的所有参与宠物**：

```sql
SELECT p.*
FROM pet_record_pet prp
JOIN pet p ON prp.pet_id = p.pet_id
WHERE prp.session_id = 456
  AND prp.session_type = 'meal';
```

**判断是否为联合记录**：

```sql
SELECT COUNT(*) as pet_count
FROM pet_record_pet
WHERE session_id = 456
  AND session_type = 'meal';
-- pet_count > 1 即为联合记录
```

### 7.1 创建联合记录后的状态

```

    ↓

    ↓
```

```javascript
togglePetSelection(petId) {
  const idx = this.selectedPetIds.indexOf(petId)
  if (idx >= 0) {
    if (this.selectedPetIds.length > 1) {
      this.selectedPetIds.splice(idx, 1)
    }
  } else {
    this.selectedPetIds.push(petId)
  }
  this.isJointMode = this.selectedPetIds.length >= 2
}
```

```javascript
isJointRecord(record) {
  return record.participants && record.participants.length > 1

getParticipantNames(record) {

    return []
  }
  return record.participants.map(p => p.name)
}
```

### 9.3 Phase 2 详细任务

```sql
CREATE TABLE pet_record_pet (
  id              BIGINT       NOT NULL AUTO_INCREMENT PRIMARY KEY,
  session_id      BIGINT       NOT NULL COMMENT '餐食/运动会话ID',
  session_type    VARCHAR(16)  NOT NULL COMMENT 'meal/exercise',
  pet_id          BIGINT       NOT NULL COMMENT '宠物ID',
  create_time     DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_session_pet (session_id, session_type, pet_id),
  KEY idx_pet (pet_id),
  KEY idx_session (session_id)
);
```

#### Phase 2.2：数据迁移 — 餐食记录

```sql
INSERT INTO pet_record_pet (session_id, session_type, pet_id)

JOIN pet_daily_record dr ON ms.daily_record_id = dr.daily_record_id;
```
