## 1. 需求背景与目标

### 1.1 用户原始诉求

进销存系统当前功能复杂且冗余，参考商户管理端左侧导航中的页面模块，考虑进行大幅度删减：

- **仅保留**：库存管理、入库管理、出库管理 三个页面及其功能。
- **仓库/仓位简化**：所有入库单/出库单中的"仓库信息"和"仓位信息"统一使用"主仓库"和"默认仓位"填充。
- **批次简化**：所需关联批次单独占据一个批次号（即每次入库对应一个独立批次号）。
- **可行性评估**：结合原有实现，分析这种情况下是否能够完成最基本的出入库操作；若不可行，提供可行解决方案；有需要确认和决策的内容一并列举。

### 1.2 本文档目标

| 目标 | 说明 |
|------|------|
| 现状梳理 | 完整盘点管理端进销存模块的页面、后端 Model/Service/Route、关键业务链路 |
| 可行性评估 | 逐链路分析降级方案是否能完成最基本的出入库操作 |
| 矛盾识别 | 指出降级方案与现有实现的冲突点（特别是销售出库对批次的强依赖） |
| 解决方案 | 提供可行的降级实施路径（不破坏订单交易链路） |
| 决策清单 | 列出所有需要用户确认与决策的事项 |

> **重要声明**：本文档仅做需求分析与可行性评估，**不进行任何代码变更**。决策点已确认（见 §7），待进入实施阶段。

### 2.3 关键业务链路

#### 2.3.1 订单交易链路（C 端 → 后端，必须保留）

```
用户下单 ──► orderController.js#placeOrder
            └─► inventoryService.reserveStock(skuId, qty, WH=1, LOC=1)
                └─► InventoryRealTime: available_qty -= qty, locked_qty += qty
                └─► InventoryFlow: direction='LOCK'

订单支付成功 ──► paymentService.js#completePayment（事务提交后）
                └─► outboundService.createOutbound(orderId)
                    └─► inventoryService.deductStockWithFIFO(skuId, qty, WH=1, LOC=1)
                        ├─► 查询 BatchInfo WHERE sku_id, warehouse_id=1, location_id=1, status='active', quantity>0
                        │   ORDER BY production_date ASC
                        ├─► ❗ 若 batches.length === 0 → throw 'NO_AVAILABLE_BATCH'（400）
                        ├─► FIFO 分配批次：batch.quantity -= allocateQty
                        └─► InventoryRealTime: locked_qty -= qty

订单取消 ──► orderService.js#cancelOrder
            └─► inventoryService.releaseStock → locked_qty -= qty, available_qty += qty

订单过期 ──► orderExpiryCronService.js（定时任务）
            └─► inventoryService.releaseStock
```

## 4. 可行性分析

### 4.1 入库流程可行性

| 维度 | 评估 | 说明 |
|------|------|------|
| 仓库/仓位固定 | ✅ 可行 | `addStock` 默认参数 `WH=1, LOC=1`，前端无需选择 |
| 创建独立批次号 | ❌ **不可行（当前）** | `addStock` **不创建 BatchInfo**，与用户"关联批次单独占据一个批次号"的要求不符 |
| 不依赖采购单 | 🟡 需改造 | 采购管理页面删除后，入库无法走 `receivePurchase`；需新建简化入库 API |
| 不依赖供应商 | ✅ 可行 | `BatchInfo.supplier_id` 已 `allowNull: true` |

**矛盾核心**：用户要求"关联批次单独占据一个批次号"，但当前 `inventoryService.addStock` 不创建批次。若不改造，销售出库链路会断裂（见 4.3）。

**解决方案**：改造入库 API，在 `addStock` 基础上**额外创建一条 BatchInfo**（batch_no 自动生成，warehouse_id=1, location_id=1），并使 InventoryFlow.batch_id 关联新批次。详见 §5.2。

### 4.2 出库流程可行性

| 维度 | 评估 | 说明 |
|------|------|------|
| 仓库/仓位固定 | ✅ 可行 | 默认参数已支持 |
| 手动出库扣减批次 | ❌ **不可行（当前）** | 现有 `POST /admin/inventory/outbound` 用 `addStock(-qty)` 实现，**不扣 BatchInfo**，导致批次数量与实时库存不一致 |
| 销售出库单管理 | ✅ 可行 | `outboundService.listOutbounds/confirmOutbound/cancelOutbound` 可保留 |

**矛盾核心**：手动出库若不扣批次，长期会导致 `BatchInfo.quantity` 累计虚高，FIFO 失效，销售出库（订单触发）会按错误批次扣减。

**解决方案**：手动出库改为调用 `deductStockWithFIFO`（与销售出库一致），扣 `BatchInfo.quantity` + `InventoryRealTime.available_qty` + 写 InventoryFlow(direction='OUT')。详见 §5.3。

### 4.3 销售出库（订单触发）链路可行性

| 维度 | 评估 | 说明 |
|------|------|------|
| 触发链路保留 | ✅ 必须保留 | `paymentService.completePayment → outboundService.createOutbound` 是订单交易闭环 |
| `deductStockWithFIFO` 对批次的强依赖 | ❌ **阻断点** | 若入库未创建批次，`deductStockWithFIFO` 会抛 `NO_AVAILABLE_BATCH`（400），订单支付后出库失败 |
| 仓库/仓位 | ✅ 已固定 | `outboundService` 已使用 `DEFAULT_WAREHOUSE_ID/DEFAULT_LOCATION_ID` |

**关键结论**：销售出库链路**强依赖批次数据**。降级方案若要可行，**必须保证每次入库都创建批次**，否则订单交易链路会断裂。这是降级方案能否成立的决定性约束。

### 4.4 仓库/仓位表保留可行性

| 维度 | 评估 | 说明 |
|------|------|------|
| `Warehouse` / `Location` 表保留 | ✅ 可行 | 表结构不变，保留主仓库 + 默认仓位的初始数据 |
| `InventoryRealTime` 联合主键 | ✅ 可行 | (sku_id, warehouse_id=1, location_id=1) 三列主键不变，业务层固定使用 1 |
| 前端下拉移除 | ✅ 可行 | 三个保留页面移除仓库/库位下拉选择 |

> **不推荐方案**：完全删除 `Warehouse`/`Location` 表并重写 `InventoryRealTime` 主键。影响面极大（涉及所有库存读写），风险高，违背"降级"而非"重写"的初衷。

## 5. 推荐解决方案（方案 A：保留数据模型 + 简化 API + 删除冗余模块）

### 5.1 总体原则

| 原则 | 说明 |
|------|------|
| 数据模型不动 | `warehouse`/`location`/`inventory_real_time`/`inventory_flow`/`batch_info`/`sales_outbound` 表结构全部保留 |
| 主仓库/默认仓位固化 | 业务层固定 `warehouse_id=1, location_id=1` |
| 入库自动创建批次 | 每次入库对应一个独立批次号（自动生成） |
| 出库走 FIFO 批次扣减 | 手动出库与销售出库一致，扣 `BatchInfo.quantity` |
| 订单交易链路不动 | `reserveStock` / `releaseStock` / `paymentService→outboundService` 完全保留 |
| 删除冗余页面/路由/服务/定时任务 | 见 §5.6 删除清单 |

### 5.2 入库 API 改造（关键）

#### 5.2.1 现状

```
POST /admin/inventory/inbound
  body: { sku_id, quantity, warehouse_id?, location_id?, unit_cost?, related_doc_no? }
  → inventoryService.addStock(...)
  → InventoryRealTime.available_qty += qty
  → InventoryFlow(direction='IN', batch_id=NULL)
```

#### 5.2.2 改造后

```
POST /admin/inventory/inbound
  body: {
    sku_id,           // 必填
    quantity,         // 必填，正整数
    unit_cost?,       // 可选，单位成本
    production_date?, // 可选，生产日期（用于 FIFO 排序与临期）
    expiry_date?,     // 可选，过期日期（若不填且 SKU 有 shelf_life_days 则自动推算）
    related_doc_no?,  // 可选，关联单号
    reason?           // 可选，备注
  }
  → 新建简化入库 Service 方法（如 inventoryService.inboundWithBatch）
    1. 自动生成 batch_no（如 INB_{timestamp}_{random}）
    2. 创建 BatchInfo（warehouse_id=1, location_id=1, status='active'）
    3. InventoryRealTime.available_qty += qty（或自动创建）
    4. InventoryFlow(direction='IN', batch_id=新批次, unit_cost, reason)
  → 返回 { flow_id, batch_id, batch_no, ... }
```

> 改造点：移除前端表单的 `warehouseId` / `locationId` / `purchaseId` 字段；保留 `productionDate` / `expiryDate` / `unitCost` 字段（用于 FIFO 与成本）。

### 5.3 出库 API 改造（关键）

#### 5.3.1 现状

```
POST /admin/inventory/outbound（手动出库）
  body: { sku_id, quantity, warehouse_id?, location_id?, reason? }
  → inventoryService.addStock(sku_id, -quantity, ...)  ❌ 不扣批次，direction='IN'
```

#### 5.3.2 改造后

```
POST /admin/inventory/outbound（手动出库）
  body: {
    sku_id,           // 必填
    quantity,         // 必填，正整数
    reason?           // 可选，出库原因
    related_doc_no?   // 可选，关联单号
  }
  → 新建简化出库 Service 方法（如 inventoryService.outboundWithFIFO）
    1. 校验 InventoryRealTime.available_qty >= quantity
    2. 调用 deductStockWithFIFO(sku_id, qty, WH=1, LOC=1)
       - 查询 BatchInfo WHERE status='active', quantity>0, ORDER BY production_date ASC
       - FIFO 分配批次：batch.quantity -= allocateQty
       - InventoryRealTime.available_qty -= qty
       - InventoryFlow(direction='OUT', batch_id=分配批次)
    3. 返回 { flow_id, allocations: [...] }
```

> 改造点：移除前端表单的 `warehouseId` / `locationId` 字段；出库不再依赖 `locked_qty`，直接扣 `available_qty`（手动出库不需先预占）。
>
> **注意**：`deductStockWithFIFO` 当前会校验 `locked_qty < quantity` 并抛 `INVENTORY_LOCK_INSUFFICIENT`（L600-L602），这是为销售出库设计的（先预占后扣减）。**手动出库未预占，需绕过此校验**。
>
> **决策确认（D-2 ✅）**：采用新增 `deductStockDirectWithFIFO` 方法（直接扣 `available_qty` + FIFO 扣批次，不校验 `locked_qty`，不要求先预占）。语义清晰，适合手动出库。

### 5.4 销售出库（订单触发）链路保持不变

`paymentService.completePayment → outboundService.createOutbound → deductStockWithFIFO` 完全保留。改造后入库会创建批次，因此销售出库能正常找到批次并完成 FIFO 扣减。

## 6. 关键矛盾点与风险

### 6.1 已识别矛盾

| 编号 | 矛盾 | 影响 | 解决 |
|------|------|------|------|
| C-1 | 手动入库不创建批次，但销售出库强依赖批次 | 订单支付后出库失败 | §5.2 入库 API 改造 |
| C-2 | 手动出库不扣批次，导致批次数量虚高 | FIFO 失效，库存不一致 | §5.3 出库 API 改造 |

### 6.2 风险

| 风险点 | 等级 | 应对 |
|--------|------|------|
| 历史批次数据未清理，FIFO 仍按旧批次扣减 | 中 | 建议提供"归档旧批次"脚本（将历史批次 status 置 empty） |
| 删除定时任务后，临期/低库存不再预警 | 中 | 在 D-3 决策；若保留定时任务，需保留通知写入逻辑 |

| 删除追溯模块后，批次流向无法查询 | 低 | 表数据保留，未来可恢复页面 |
| 入库时未填生产日期，FIFO 退化为按 batch_id 顺序 | 低 | 可接受；或强制要求生产日期 |
| 手动出库与销售出库共用 `deductStockWithFIFO`，并发冲突 | 中 | 沿用现有乐观锁 + 事务，已支持 |

#### D-1：入库完全脱离采购单与供应商（已确认：完全脱离）
