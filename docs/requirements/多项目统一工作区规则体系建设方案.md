> **创建日期**：2026-08-13
> **创建人**：yjm
> **涉及项目**：pet-app-backend、pet-app、pet-app-admin-web、pet-app-common
> **优先级**：高
> **状态**：待实施（依赖 Trae CN 父级规则加载验证）

---

## 一、背景与需求

### 1.1 现状痛点

本产品包含四个目录：

```
宠物生鲜电商开发项目/
├── pet-app-backend/      # 后端服务（Node.js / Express / Sequelize / MySQL）
├── pet-app/              # 微信小程序前端（uni-app + Vue3）
├── pet-app-admin-web/    # Web 管理端（Vue3 + Element Plus）
└── pet-app-common/       # 公共资源目录（独立 git 管理）
```

**当前问题**：

| 编号 | 痛点 | 影响 |
|------|------|------|
| P1 | 三端 `cross-project.md` 各维护一份副本，靠人工同步，已出现内容漂移 | AI 助手在不同工作区获取的跨项目信息不一致 |
| P2 | 三端 `naming-conventions.md` 已分化（字节数不同），公共规范与项目专属规范混杂 | 新成员无法快速区分哪些规范是跨端统一的 |
| P3 | 多端协同变更（如新增 API 需后端实现 + 前端对接 + 管理端配置）无统一流程指引 | 每次协同变更需人工重新规划顺序，易遗漏步骤 |
| P4 | 在单项目工作区打开时，AI 助手只能看到当前项目规则，缺少全局视图 | 接口字段对齐、错误码同步等高频协同任务效率低 |
| P5 | `pet-app-common` 只有 README，无 `.trae/rules` 规则 | 公共文档的写规范模糊，容易与项目文档边界不清 |

### 1.2 需求目标

在父级目录建立 **多项目统一工作区**，实现：

1. **跨项目契约统一**：变更顺序、协同流程、三端对齐清单等跨项目规则由单一事实源承载
2. **项目专属规范自治**：各项目命名、文档、技术栈约束保留在项目内 `.trae/rules/`，不被全局规则覆盖
3. **AI 全局视图**：在父级工作区打开时，AI 能同时看到三端的项目结构和约束，自动按流程协同
4. **可落地**：提供可直接复制使用的规则文件，无需从零搭建

## 二、目标架构

### 2.1 规则分层模型

```
┌─────────────────────────────────────────────────────────┐
│  父级 .trae/rules/                                       │
│  ├── multi-project.md    ← 跨项目契约层（本方案核心）    │
│  └── test-parent-rules.md ← 验证用临时文件（测试后删除） │
├─────────────────────────────────────────────────────────┤
│  pet-app-common/docs/shared-rules/                       │
│  └── cross-project.master.md ← 公共规范母版（单一事实源）│
├─────────────────────────────────────────────────────────┤
│  各项目 .trae/rules/                                     │
│  ├── cross-project.md     ← 引用母版 + 项目特定权限      │
│  ├── naming-conventions.md ← 项目专属命名规范           │
│  └── docs-conventions.md  ← 项目专属文档规范           │
└─────────────────────────────────────────────────────────┘
```

### 2.2 各层职责边界

| 层级 | 承载位置 | 内容类型 | 变更频率 |
|------|----------|----------|----------|
| **跨项目契约层** | 父级 `.trae/rules/multi-project.md` | 变更顺序契约、协同流程、三端对齐检查清单、跨项目目录映射 | 低（流程稳定后极少变更） |
| **公共规范母版** | `pet-app-common/docs/shared-rules/cross-project.master.md` | 三端共有的项目结构说明、公共目录操作规范、Git 管理规则 | 中（新项目/新成员加入时更新） |
| **项目专属规范** | 各项目 `.trae/rules/` | 命名规范、文档范式、技术栈约束、项目特定的目录权限 | 高（随项目演进频繁更新） |

### 2.3 核心原则

> **跨项目契约上提，项目规范下沉，公共规范母版化**

1. **父级规则只写"项目间"的事**：变更顺序、协同流程、对齐清单——任何只涉及单个项目的规则都不上提
2. **项目规则保持自治**：命名规范、文档范式、技术栈约束仍在各项目 `.trae/rules/`，不被父级规则覆盖
3. **公共规范单一事实源**：三端 `cross-project.md` 的共有部分（项目结构、公共目录操作）从 `cross-project.master.md` 复制，改动先改母版再同步

## 三、变更路径

### 3.1 前置验证（必须先完成）

在执行任何变更前，**必须先验证 Trae CN 的规则加载行为**：

1. 用 Trae CN 打开父级目录 `宠物生鲜电商开发项目` 作为工作区
2. 向 AI 提问："你能看到父级的 multi-project-test 规则吗？请引用 test-parent-rules.md 的内容。"
3. 观察 AI 回答，确认以下三点：
   - [ ] 父级 `.trae/rules/test-parent-rules.md` 的内容被 AI 感知
   - [ ] 子项目的 `.trae/rules/` 规则（如 backend 的 naming-conventions.md）仍然被加载
   - [ ] 两者可以同时生效，无互相覆盖

**验证通过前，不执行后续步骤。** 若验证失败（如父级规则不被加载或子级规则被覆盖），需调整方案（如改用在父级建 `.trae-cn/rules/` 而非 `.trae/rules/`）。

### 3.2 实施步骤

| 步骤 | 操作 | 涉及路径 | 风险等级 |
|------|------|----------|----------|
| **Step 1** | 创建父级跨项目契约规则 | `宠物生鲜电商开发项目/.trae/rules/multi-project.md` | 低（新建文件，不影响现有规则） |
| **Step 2** | 创建公共规范母版 | `pet-app-common/docs/shared-rules/cross-project.master.md` | 低（新建文件） |
| **Step 3** | 收敛三端 `cross-project.md` | `pet-app/.trae/rules/cross-project.md` 等三端 | 中（需逐个替换并验证 AI 加载效果） |
| **Step 4** | 清理测试文件 | 删除 `宠物生鲜电商开发项目/.trae/rules/test-parent-rules.md` | 无 |
| **Step 5** | 更新 `pet-app-common/README.md` | 增加 shared-rules 和父级规则说明 | 低 |

### 3.3 Step 3 收敛规则（详细说明）

当前三端 `cross-project.md` 的差异仅为：

| 差异点 | pet-app | pet-app-admin-web | pet-app-backend |
|--------|---------|-------------------|-----------------|
| "当前项目"标识 | 微信小程序前端 | Web 管理端 | 后端服务 |
| 读写权限 | pet-app 读写，其他只读 | admin-web 读写，其他只读 | backend 读写，其他只读 |
| 读取兄弟项目的路径 | 后端 routes、admin-web components | 小程序 components、后端 routes | 小程序 components、admin-web components |

**收敛方式**：将共有部分抽入 `cross-project.master.md`，各项目 `cross-project.md` 只保留差异部分（当前项目标识 + 权限 + 读取路径），并引用母版。

### 3.4 回滚方案

若实施后出现问题（如 AI 规则加载异常）：

1. 删除父级 `.trae/rules/multi-project.md`
2. 将三端 `cross-project.md` 恢复为原始版本（git checkout 或手动还原）
3. `cross-project.master.md` 保留在 `pet-app-common` 供后续参考

## 2. 跨项目变更顺序契约

### 2.1 新增 API（后端 + 前端）

```
Step 1: API 规范文档（pet-app-common/docs/api-specs/）
        定义接口路径、请求/响应字段、错误码
        ↓
Step 2: 后端实现（pet-app-backend/）
        Schema 变更 → Model → Migration → Controller → Route → 验证脚本
        ↓
Step 3: 后端自测
        npm run dev → curl/Postman 验证 → npm run verify:*
        ↓
Step 4: 前端对接（pet-app/ 或 pet-app-admin-web/）
        按 API 规范对接 → 字段类型对齐 → 错误码处理
        ↓
Step 5: 联调验证
        三端联合测试 → 修复对接问题 → 验收
```

### 2.2 数据库 Schema 变更

```
Step 1: 设计变更
        在 pet-app-common/docs/api-specs/ 记录字段变更
        ↓
Step 2: 后端实现
        更新 scripts/schema.sql → 更新 Model → 创建迁移脚本
        ↓
Step 3: 同步与验证
        npm run db:sync → npm run verify:db
        ↓
Step 4: 前端对齐
        通知前端新字段 → 前端按需消费
```

### 2.3 仅前端变更（纯 UI/交互）

```
Step 1: 前端实现（无需后端参与）
        ↓
Step 2: 若涉及新接口，回退到 2.1 流程
```

### 2.4 仅后端变更（纯逻辑/性能优化）

```
Step 1: 后端实现（无需前端参与）
        ↓
Step 2: 若涉及 API 响应字段变更，通知前端
```

## 3. 三端对齐检查清单

每次跨项目变更完成后，逐项检查：

### 3.1 API 规范对齐

- [ ] `pet-app-common/docs/api-specs/` 中的接口文档已更新
- [ ] 后端路由/控制器实现与规范一致
- [ ] 小程序前端 API 调用与规范一致
- [ ] 管理端 API 调用与规范一致
- [ ] 错误码三端使用一致

### 3.2 字段命名对齐

- [ ] 数据库字段使用 snake_case
- [ ] API 路径参数使用 snake_case
- [ ] API 响应字段：旧接口保持 snake_case，新接口使用 camelCase
- [ ] 前端消费时字段名与后端响应一致

### 3.3 时间字段对齐

- [ ] 所有时间字段标注时区（统一使用北京时间 +08:00）
- [ ] 后端返回 ISO 8601 格式时间字符串
- [ ] 前端统一时间格式化函数

### 3.4 新增字段检查

- [ ] 数据库表字段已添加
- [ ] Sequelize Model 已更新
- [ ] 迁移脚本已创建
- [ ] `scripts/schema.sql` 已同步
- [ ] `scripts/verify-db.js` 校验项已更新
- [ ] 前端/管理端已按需消费新字段

## 五、使用指南

### 5.1 如何在新架构下工作

**场景 A：仅修改当前项目（如后端新增一个内部工具函数）**

1. 在 Trae CN 中打开当前项目目录（如 `pet-app-backend/`）作为工作区
2. AI 会加载当前项目的 `.trae/rules/`（含 naming-conventions、docs-conventions、cross-project）
3. 按照项目专属规范开发，无需关注父级规则

**场景 B：跨项目协同开发（如新增 API，需后端实现 + 小程序对接）**

1. 在 Trae CN 中打开父级目录 `宠物生鲜电商开发项目/` 作为工作区
2. AI 会加载父级 `.trae/rules/multi-project.md`（跨项目契约）
3. 按照父级规则中的 §2 变更顺序契约，依次推进：API 规范 → 后端实现 → 前端对接 → 联调
4. 使用 §3 三端对齐检查清单验证完成度

**场景 C：修改公共规范（如更新 cross-project 母版）**

1. 在 Trae CN 中打开 `pet-app-common/` 目录作为工作区
2. 修改 `docs/shared-rules/cross-project.master.md`
3. 按 Step 3 流程同步到三端 `cross-project.md`

### 5.3 常见问题

**Q: 父级规则和子项目规则冲突怎么办？**

A: 父级规则只覆盖"跨项目契约"领域（变更顺序、协同流程、对齐清单）。项目专属规范（命名、文档、技术栈）由子项目规则主导。若出现冲突，以子项目规则为准，并在父级规则中记录例外情况。

**Q: 新增一个子项目（如 pet-app-h5）需要做什么？**

A: 1. 在父级 `multi-project.md` §1 项目结构地图中添加新项目；2. 在 `cross-project.master.md` 中添加新项目差异部分；3. 在新项目 `.trae/rules/` 下创建 cross-project.md、naming-conventions.md、docs-conventions.md。

**Q: 为什么不把 naming-conventions 也上提到父级？**

A: 三端技术栈不同（Node.js vs Vue/JS vs Vue/JS），命名规范有共性也有差异。当前三端 naming-conventions 的分化是合理的（如后端有 Sequelize Model 规范，前端有组件命名规范）。将命名规范上提会导致父级规则膨胀，且无法照顾到项目专属的命名约束。
