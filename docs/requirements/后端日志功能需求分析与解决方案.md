# 后端日志功能需求分析与解决方案

## 一、需求概述

用户提出三项日志功能需求：

| 序号 | 需求描述 |
|------|----------|
| 需求1 | 异步记录并存储进程运行日志，含控制台输出、存储为本地日志文件 |
| 需求2 | `npm run dev` / `npm start` 时自动开始记录，日志持续记录，每超过1小时创建新日志文件 |
| 需求3 | 新终端下通过命令开启日志复制进程（唯一性控制），支持停止和导出/下载 |

---

## 二、需求合理性分析

### 2.1 需求1：异步记录与本地存储

**合理性**：✅ 合理

- 当前项目仅使用 `console.*` 输出到 stdout/stderr，无持久化存储
- 生产环境（Sealos）虽有平台日志采集，但本地开发环境缺乏历史日志追溯能力
- 异步写入可避免阻塞主进程，符合 Node.js 最佳实践

**潜在问题**：
- `.gitignore` 已排除 `*.log`，本地日志文件不会被误提交
- 需注意日志文件大小增长，避免磁盘空间占用失控

### 2.2 需求2：自动记录与小时轮转

**合理性**：✅ 合理，但需调整策略

- 自动记录符合用户预期，无需额外配置
- 1小时轮转间隔在开发环境下较为合理，便于日志管理和追溯

**潜在问题**：
- 当前 `npm run dev` 使用 `node --watch` 热重载，代码变更后进程会重启，需确保日志轮转在重启后正确续接
- 1小时轮转在生产环境可能过于频繁，建议分环境配置

### 2.3 需求3：独立日志复制进程（唯一性控制）

**合理性**：⚠️ 部分合理，部分需优化

**合理部分**：
- 独立进程进行日志复制/导出，不影响主服务运行
- 唯一性控制避免资源浪费和日志重复

**需优化部分**：
- **"在新终端下通过命令开启"**：此方案实现复杂，需进程间通信（IPC），且在 Sealos 容器环境下不适用
- **"复制第2点中的日志"**：若主进程已写入文件，直接读取文件即可，无需额外复制进程
- **建议改为**：提供 CLI 命令读取现有日志文件，或提供 API 接口查询日志

## 三、技术可行性分析

### 3.1 技术栈评估

| 技术 | 当前状态 | 可行性 |
|------|----------|--------|
| Node.js 18+ | ✅ 已使用 | ✅ 完全支持 |
| Winston / Pino | ❌ 未引入 | ✅ 可集成 |
| 文件系统（fs） | ✅ 内置模块 | ✅ 完全支持 |
| 进程管理 | ❌ 未使用 | ✅ 可通过 PM2 或内置模块实现 |

### 3.2 实现难点

| 难点 | 描述 | 解决方案 |
|------|------|----------|
| 热重载日志续接 | `node --watch` 重启后需恢复日志轮转状态 | 使用文件存储轮转状态，或使用 PM2 管理进程 |
| 唯一性控制 | 确保同时只有一个日志复制进程 | 使用锁文件（lockfile）或 Redis 分布式锁 |
| 异步写入性能 | 高频日志写入不阻塞主进程 | 使用 Winston 的 `async` 传输或队列缓冲 |
| 日志文件管理 | 避免日志文件无限增长 | 配置最大文件数/大小，自动清理旧日志 |

### 4.2 核心实现方案

#### 方案A：集成 Winston（推荐）

**优点**：
- 成熟的日志库，支持多种传输方式
- 内置日志轮转（`winston-daily-rotate-file`）
- 支持日志级别、格式化、过滤

**实现步骤**：

1. **安装依赖**
   ```bash
   npm install winston winston-daily-rotate-file
   ```

2. **创建日志配置**（`config/logger.js`）
   - 配置控制台输出（保持原有行为）
   - 配置文件轮转（1小时轮转，保留最近7天）
   - 配置日志级别（开发 `debug` / 生产 `info`）

3. **创建日志工具**（`utils/logger.js`）
   - 封装 Winston logger
   - 提供 `info` / `warn` / `error` / `debug` 方法
   - 兼容现有 `console.*` 调用（可选）

4. **替换现有 console 调用**（渐进式）
   - 在 `server.js`、`services/` 中逐步替换
   - 或通过 `console.log = logger.info` 全局替换

5. **修改启动脚本**（`package.json`）
   ```json
   {
     "scripts": {
       "start": "node server.js",
       "dev": "node --watch server.js",
       "start:prod": "NODE_ENV=production node server.js"
     }
   }
   ```

#### 方案B：自定义文件轮转（轻量）

**优点**：
- 无额外依赖
- 完全可控

**缺点**：
- 需自行实现轮转逻辑、日志级别、格式化

### 4.3 需求3的优化方案

**推荐方案**：CLI 命令 + API 接口

| 功能 | 实现方式 | 说明 |
|------|----------|------|
| 查看日志 | `npm run log:tail` | 实时 tail 日志文件 |
| 查看历史 | `npm run log:view -- --date=20260625` | 查看指定日期日志 |
| 导出日志 | `npm run log:export -- --date=20260625` | 打包导出日志文件 |
| API 查询 | `GET /admin/logs` | 管理端日志查询接口（需鉴权） |

**唯一性控制**：

```bash
# 使用锁文件确保只有一个 tail 进程
# scripts/log-tail.js
const lockfile = './logs/.log-tail.lock';
if (fs.existsSync(lockfile)) {
  console.error('日志查看进程已在运行');
  process.exit(1);
}
fs.writeFileSync(lockfile, process.pid.toString());

# 进程退出时删除锁文件
process.on('exit', () => fs.unlinkSync(lockfile));
```

## 六、配置建议

### 6.1 环境变量配置

```bash
# .env.example
LOG_ENABLED=true                    # 是否启用日志
LOG_LEVEL=debug                     # 日志级别: debug/info/warn/error
LOG_DIR=./logs                      # 日志存储目录
LOG_MAX_SIZE=10m                    # 单文件最大大小
LOG_MAX_FILES=7d                    # 保留天数
LOG_ROTATION_INTERVAL=1h            # 轮转间隔
LOG_CONSOLE=true                    # 是否输出到控制台
LOG_FILE=true                       # 是否写入文件
```

### 6.2 日志文件命名规范

```
logs/
├── app-20260625-09.log             # 主服务日志（按小时轮转）
├── app-20260625-10.log
├── error-20260625-09.log           # 错误日志（可选分离）
└── .log-tail.lock                  # 日志查看进程锁文件
```

## 七、风险评估与应对

| 风险 | 等级 | 应对措施 |
|------|------|----------|
| 日志文件过大 | 中 | 配置 `maxSize` 和 `maxFiles`，自动清理 |
| 异步写入丢失 | 低 | Winston 内置缓存机制，进程退出时 flush |
| 热重载日志中断 | 低 | 使用文件轮转，重启后自动创建新文件 |
| 锁文件残留 | 低 | 启动时检查锁文件对应的进程是否存活 |
| 生产环境性能影响 | 低 | 异步写入 + 队列缓冲，生产环境降低日志级别 |

## 八、结论

### 8.1 需求总结

| 需求 | 合理性 | 可行性 | 推荐方案 |
|------|--------|--------|----------|
| 需求1 | ✅ | ✅ | 集成 Winston，异步写入文件 |
| 需求2 | ✅ | ✅ | 使用 `winston-daily-rotate-file` 实现小时轮转 |
| 需求3 | ⚠️ | ✅ | 改为 CLI 命令 + API，锁文件控制唯一性 |

### 8.2 建议优先级

1. **高优先级**：阶段一（基础日志框架）— 满足核心日志记录需求
2. **中优先级**：阶段二（日志管理工具）— 提供日志查看/导出能力
3. **低优先级**：阶段三（日志 API）— 管理端远程查看日志

### 8.3 注意事项

- 生产环境需确保日志文件不会无限增长
- 敏感信息（如 `JWT_SECRET`、`session_key`）禁止写入日志
- 日志轮转策略需根据实际业务量调整
- 在 Sealos 部署时，需考虑日志文件的持久化存储（使用持久卷）
