## 一、需求背景与目标

### 1.1 背景

在商户管理端（Admin Web）运营过程中，为了提升服务质量和可追溯性，需要明确每一条用户反馈和每一次客服对话的**责任人**。目前系统存在以下不足：

1.  **用户反馈**：虽然后端已记录处理人，但小程序（C 端）和管理端的反馈详情页均未展示处理该反馈的管理员名称，用户无法得知是谁处理了自己的问题。
2.  **客服消息**：当管理员回复用户时，会话中无法直观地看到是哪位管理员正在处理该用户的咨询，导致多人协作时容易混乱，用户体验不佳。

### 1.2 目标

1.  **反馈处理人全端展示**：
    *   **小程序端**：用户在查看自己的反馈详情时，能看到“由管理员【XXX】处理”的信息。
    *   **管理端**：管理员在查看反馈详情时，能清晰看到该反馈的处理人，形成内部记录。
2.  **客服操作人管理端标识**：
    *   **管理端**：在客服会话界面的**消息列表**中，针对**每一条**由管理员发送的消息，标识出发送该消息的管理员姓名，让客服团队内部清楚每条回复的责任人。

## 二、需求分析

### 2.1 需求一：用户反馈处理人显示

#### 2.1.1 现状分析

*   **后端**：
    *   `user_feedback` 表已包含 `processed_by` (admin_id) 和 `processed_at` 字段（合规审计后字段命名为 `created_at`/`updated_at`/`is_deleted`，符合 §8 规范）。
    *   `models/index.js` 已建立 `UserFeedback.belongsTo(AdminUser, { foreignKey: 'processed_by', as: 'processor' })` 关联。
    *   `services/adminFeedbackService.js` 的 `formatAdminDetail` 已通过 `row.processor?.username` 返回 `processed_by_username`（snake_case，经 `adminResponseKeysMiddleware` 自动转 `processedByName`）。
    *   **缺失**：面向小程序的 `GET /feedback/:id` 接口（`services/feedbackService.js` 的 `formatUserFeedback` + `getMyFeedbackDetail`）**未关联查询** AdminUser，未返回 `processed_by_username`。
*   **管理端前端**：
    *   ✅ **已实现**：`src/types/feedback.ts` 的 `FeedbackDetail` 接口已包含 `processedBy` 和 `processedByName` 字段；`src/components/feedback/FeedbackResolveDrawer.vue` 第 192-197 行已通过 `el-descriptions-item` 展示 `detail.processedByName || detail.processedBy || '—'`。
    *   即管理端反馈处理人展示已落地，无需重复改造。
*   **小程序前端**：
    *   详情页 (`src/subpk-feedback/history.vue` 实际为反馈历史**列表页**，通过 `uni.showModal` 弹窗展示详情) **未获取和展示**处理人信息。
    *   `src/services/feedback.js` 的 `normalizeFeedbackItem` 函数**未映射** `processed_by_username` 字段（仅映射 `id/type/content/status/createdAt/reply/imageUrls/orderId`）。
    *   `src/api/feedback.js` 已存在 `getFeedbackDetail(id)` 调用 `GET /feedback/:id`，但当前 `services/feedback.js` 的 `fetchMyFeedbacks` 仅调用列表接口 `getFeedbackList`，未使用详情接口。

#### 2.1.2 需求点

1.  **后端**：确保面向小程序的反馈详情接口返回处理人信息（`processed_by_username` 或 `processed_by` 对象）。
2.  **管理端前端**：在反馈详情展示区域（如抽屉、弹窗）新增一行，醒目标示“处理人：【XXX】”。
3.  **小程序前端**：在反馈详情页的状态区域下方，新增“处理人”信息展示，仅在状态为“已处理”时显示。

### 2.2 需求二：客服消息操作人显示

#### 2.2.1 现状分析

*   **后端**：
    *   `service_message` 表仅记录了 `sender_role` ('user' / 'admin' / 'system')，**未记录**具体是哪个管理员 (`admin_user.admin_id`) 发送的。
    *   **合规审计结论**（依据 §五 例外场景豁免）：`service_message` 表已包含 `created_at` + `updated_at`，**豁免** `is_deleted`（通过业务状态/归档机制管理），符合 §8.5 规范。本次新增 `sender_admin_id` 字段不涉及补齐 `is_deleted`。
    *   `service_conversation` 表**没有**“当前处理人”或“最后操作人”字段（合规审计后已新增 `is_deleted` 字段，软删除改造已完成）。
    *   `models/index.js` 已建立 `ServiceMessage.belongsTo(ServiceConversation)` 与 `ServiceMessage.belongsTo(OrderMain, { as: 'relatedOrder' })`，**未建立** `ServiceMessage.belongsTo(AdminUser)` 关联。
    *   `services/adminServiceConversationService.js` 中的 `sendAdminMessage` 方法**未记录**操作人 ID（当前仅记录 `sender_role: 'admin'`）；`formatServiceMessage` 函数返回字段中**未包含** `sender_name`。
    *   `services/serviceConversationService.js` 中的 `queryConversationMessages` + `formatServiceMessage` 同样**未返回** `sender_name`，由 `adminServiceConversationService.listAdminMessages` 复用，需在共用层或 admin 层补充关联查询。
*   **管理端前端**：
    *   `ChatPanel.vue` 会话头部仅展示用户信息，**无操作人**展示。
    *   `src/types/customerService.ts` 的 `ServiceMessage` 接口**未定义** `senderName` 字段。
    *   **API 响应链路**（已落地，v7.0 P1 变更）：后端 `/admin/*` 路由通过 `utils/adminResponseKeysMiddleware` 中间件将 `res.json` 输出的 `data` 域深转换 snake_case → camelCase；管理端 `src/api/http.ts` 响应拦截器 `toCamelCase()` 再做一次转换。因此后端只需返回 `sender_name`（snake_case），管理端消费 `senderName`（camelCase）。

#### 2.2.2 需求点

1.  **后端**：
    *   **修改 `service_message` 模型**：新增 `sender_admin_id` 字段（当 `sender_role` 为 `admin` 时填入，记录管理员 ID）。
    *   **修改 Service 逻辑**：在 `sendAdminMessage` 中，将 `req.admin.id` 写入新消息的 `sender_admin_id` 字段。
    *   **修改消息查询**：在 `getConversationMessages` (获取消息列表接口) 中，对返回的每条消息，如果 `sender_role` 为 `admin`，则根据其 `sender_admin_id` 关联查询 `admin_user` 表，获取其 `username`，作为 `sender_name` 附加在消息对象中返回。
2.  **管理端前端**：
    *   在 `ChatPanel.vue` 的**消息列表渲染区域**，针对 `sender_role === 'admin'` 的消息气泡，在消息内容旁（如头像右侧、消息气泡下方或时间戳旁）显示 `sender_name`。

## 三、解决方案

### 3.1 技术方案

#### 3.1.1 后端修改方案

1.  **数据库模型 (`models/ServiceMessage.js`)**
    *   *新增字段*：`sender_admin_id` (BIGINT, NULLABLE)。
    *   *说明*：当 `sender_role` 为 'admin' 时，记录发送该消息的管理员 ID；当为 'user'/'system' 时，该字段为 NULL。
    *   *合规审计对齐*：`service_message` 表已包含 `created_at` + `updated_at`，依据 §8.5 例外场景豁免 `is_deleted`（通过业务状态/归档机制管理）。本次仅新增业务字段，不涉及补齐基础字段。

2.  **模型关联 (`models/index.js`)**
    *   *新增关联*：在 `ServiceMessage.belongsTo(OrderMain, { as: 'relatedOrder' })` 之后补充 `ServiceMessage.belongsTo(AdminUser, { foreignKey: 'sender_admin_id', as: 'senderAdmin' })`；并在 `AdminUser.hasMany(ServiceMessage, { foreignKey: 'sender_admin_id', as: 'sentServiceMessages' })` 反向关联。
    *   *说明*：通过 Sequelize 关联查询在 `queryConversationMessages` 中一次性 join AdminUser，避免 N+1 查询。

3.  **数据库迁移 (`scripts/migrate-schema-v49-add-service-message-sender-admin-id.js`)**
    *   *命名规则*：对齐 v44~v48 既有序列，定为 v49；`package.json` 注册 `npm run migrate:v49`。
    *   *迁移内容*：`ALTER TABLE service_message ADD COLUMN sender_admin_id BIGINT NULL DEFAULT NULL COMMENT '管理员发送者 admin_id（sender_role=admin 时填入）' AFTER sender_role;`，并补 `KEY idx_sender_admin_id (sender_admin_id)`；幂等检查 `information_schema.columns` 避免重复添加。
    *   *回滚方案*：`ALTER TABLE service_message DROP COLUMN sender_admin_id;`（可逆，新字段 nullable）。

4.  **Schema 同步 (`scripts/schema.sql` + `scripts/verify-db.js`)**
    *   *schema.sql*：在 `service_message` 建表语句中新增 `sender_admin_id` 字段及对应索引（详见 §3.3 建表语句）。
    *   *verify-db.js*：在 `service_message` 表的 EXPECTED_FIELDS 校验清单中加入 `sender_admin_id: BIGINT`，确保后续环境同步可被自动化校验捕获。

5.  **业务逻辑 (`services/adminServiceConversationService.js` + `services/serviceConversationService.js`)**
    *   *修改 `sendAdminMessage`*：在 `ServiceMessage.create({...})` 调用中增加 `sender_admin_id: adminId`（adminId 由 `adminServiceConversationController` 通过 `req.admin.id` 传入）。
    *   *修改 `queryConversationMessages` / `formatServiceMessage`*：在共用层 `services/serviceConversationService.js` 的 `queryConversationMessages` 中给 `ServiceMessage.findAll` 添加 `include: [{ model: AdminUser, as: 'senderAdmin', required: false, attributes: ['username'] }]`；在 `formatServiceMessage(row)` 中新增 `sender_name: row.sender_role === 'admin' ? (row.senderAdmin?.username || null) : null` 字段（snake_case）。
    *   *命名风格保持 snake_case*：依据 `pet-app-backend/.trae/rules/naming-conventions.md` §3.3 终态规则，后端响应字段统一 snake_case，由 `adminResponseKeysMiddleware` 自动转 camelCase 给管理端，由小程序 `request.js` 拦截器 `deepToCamelCase()` 转换给 C 端。
6.  **小程序反馈接口 (`services/feedbackService.js`)**
    *   *修改 `getMyFeedbackDetail`*：在 `UserFeedback.findOne` 的 `include` 中追加 `{ model: AdminUser, as: 'processor', required: false, attributes: ['username'] }`（关联已存在于 `models/index.js`）。
    *   *修改 `listMyFeedbacks`*：在 `findAndCountAll` 的 `include` 中追加同样的 `AdminUser` 关联，使列表接口 `GET /feedback` 也返回处理人信息（支撑小程序在列表卡片直接展示处理人，无需新增独立详情页）。
    *   *修改 `formatUserFeedback`*：在返回 item 中增加 `processed_by_username: row.processor?.username || null`（snake_case），仅在 `status === 'resolved'`（FEEDBACK_STATUS.resolved）时附加该字段，避免未处理反馈返回冗余字段。
7.  **API 规范文档**
    *   更新 `pet-app-common/docs/api-specs/` 下的客服消息 API 文档（在 `在线客服-消息分页响应修复-方案与任务清单-临时.md` 之上增补附录，或新建 `2026-08-19-API规范-客服消息操作人显示.md`），说明消息对象中新增 `sender_name` 字段；同时备案 `GET /feedback/:id` 响应新增 `processed_by_username`。

#### 3.1.2 前端修改方案

**管理端前端 (`pet-app-admin-web`)**

1.  **类型定义 (`src/types/customerService.ts`)**
    *   在 `ServiceMessage` 接口中新增 `senderName?: string | null`（camelCase）。
    *   *说明*：后端返回的 `sender_name`（snake_case）会经过 `adminResponseKeysMiddleware` 与 `http.ts` 拦截器两层 camelCase 转换，最终前端消费 `senderName`。

2.  **UI 展示 (`src/components/customer-service/ChatPanel.vue`)**
    *   在消息列表的模板中，针对 `v-for` 循环渲染的每条消息，判断 `message.senderRole === 'admin'`。
    *   如果是管理员消息，则在消息气泡旁边（通常是时间戳旁边或消息气泡下方）显示 `message.senderName`。例如：
        ```vue
        <!-- 在消息时间戳旁显示发送者名称 -->
        <span class="chat-panel__time">
          {{ formatChatTime(message.createTime) }}
          <span v-if="message.senderRole === 'admin' && message.senderName" class="chat-panel__sender">
            ({{ message.senderName }})
          </span>
        </span>
        ```
    *   样式上可以使用 `el-tag` 或简单的 `span` 来区分，确保在对话气泡中比较醒目，但又不过于突兀。
    *   *注意*：现有 `ChatPanel.vue` 第 375 行已展示 `chat-panel__time`，可在此处追加 `senderName` span。

3.  **反馈详情页 (`src/components/feedback/FeedbackResolveDrawer.vue`)**
    *   ✅ **无需重复改造**：现状分析已确认第 192-197 行已展示 `detail.processedByName || detail.processedBy || '—'`，仅在 `detail.status === 'resolved'` 时展示（与需求一致）。
    *   类型定义 `src/types/feedback.ts` 第 32-38 行已包含 `processedBy: number | null` 与 `processedByName: string | null` 字段，无需修改。

**小程序前端 (`pet-app`)**

1.  **API 服务 (`src/services/feedback.js` + `src/api/feedback.js`)**
    *   `src/api/feedback.js` 已存在 `getFeedbackDetail(id)` 调用 `GET /feedback/:id`，无需修改。
    *   `src/services/feedback.js` 的 `normalizeFeedbackItem(raw)` 函数中新增字段映射：
        ```javascript
        processedByUsername: raw.processed_by_username ?? raw.processedByUsername ?? null,
        ```
    *   *说明*：后端返回 `processed_by_username`（snake_case），经小程序 `request.js` 拦截器 `deepToCamelCase()` 自动转 `processedByUsername`；三层兼容写法保证旧缓存命中。

2.  **UI 展示 (`src/subpk-feedback/history.vue`)**
    *   *现状澄清*：`history.vue` 实际是反馈历史**列表页**，当前点击列表项通过 `uni.showModal` 弹窗展示详情内容（无独立详情页）；`fetchMyFeedbacks` 仅调用 `feedbackApi.getFeedbackList` 列表接口。
    *   *实现策略*（二选一）：
        - **方案 A（推荐 · 改动最小）**：在 `history.vue` 的列表卡片中直接展示处理人信息（仅当 `item.status === 'resolved'` 且 `item.processedByUsername` 存在时）：
            ```vue
            <text
              v-if="item.status === 'resolved' && item.processedByUsername"
              class="history-processor"
            >处理人：{{ item.processedByUsername }}</text>
            ```
            同时在 `onCardTap` 弹窗内容中也追加处理人信息：
            ```javascript
            if (item.processedByUsername) {
              lines.push(`\n处理人：${item.processedByUsername}`)
            }
            ```
            - 此方案要求**列表接口 `GET /feedback` 也要返回 `processed_by_username`**。需在 §3.1.1 后端修改方案 6 中追加：`formatUserFeedback` 在列表项返回中也添加该字段；或在 `listMyFeedbacks` 的 `findAndCountAll` 中追加 `include: [{ model: AdminUser, as: 'processor', required: false, attributes: ['username'] }]`。
        - **方案 B（侵入式）**：新增独立详情页 `detail.vue`，调用 `getFeedbackDetail(id)` 接口。改动较大，不在本期需求范围内。
    *   本方案采用 **方案 A**：在列表卡片和弹窗中展示处理人，不新增详情页。

3.  **WXSS 样式 (`src/subpk-feedback/history.vue` 内联 `<style scoped>` 段)**

### 3.3 数据库表项描述（依据 `multi-project.md` §7）

#### 3.3.1 `service_message` 表字段信息表（变更后）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| message_id | BIGINT | PK, AUTO_INCREMENT | 消息主键 |
| conversation_id | BIGINT | NOT NULL, FK → service_conversation | 所属会话 ID |
| sender_role | ENUM('user','admin','system') | NOT NULL | 发送者角色 |
| sender_admin_id | BIGINT | NULL, DEFAULT NULL | 管理员发送者 admin_id（仅 `sender_role='admin'` 时填入；其余角色为 NULL） |
| content_type | ENUM('text','image') | NOT NULL | 消息内容类型 |
| content | TEXT | NOT NULL | 消息内容（文本或图片 URL） |
| related_order_id | BIGINT | NULL, FK → order_main | 发送时快照的关联订单 |
| created_at | DATETIME | NOT NULL, DEFAULT CURRENT_TIMESTAMP | 创建时间（北京时间） |
| updated_at | DATETIME | NOT NULL, DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP | 最后更新时间（北京时间） |

> **`is_deleted` 豁免说明**：依据 `multi-project.md` §8.5 例外场景，`service_message` 为会话消息表，通过业务状态/归档机制管理，**豁免** `is_deleted` 字段；本表仍保留 `id` + `created_at` + `updated_at` 三类必备字段，符合规范要求。

#### 3.3.2 `service_message` 表建表语句（变更后）

```sql
CREATE TABLE IF NOT EXISTS `service_message` (
  `message_id` BIGINT NOT NULL AUTO_INCREMENT COMMENT '消息主键',
  `conversation_id` BIGINT NOT NULL COMMENT '所属会话 ID',
  `sender_role` ENUM('user','admin','system') NOT NULL COMMENT '发送者角色',
  `sender_admin_id` BIGINT DEFAULT NULL COMMENT '管理员发送者 admin_id（仅 sender_role=admin 时填入）',
  `content_type` ENUM('text','image') NOT NULL COMMENT '消息内容类型',
  `content` TEXT NOT NULL COMMENT '消息内容（文本或图片 URL）',
  `related_order_id` BIGINT DEFAULT NULL COMMENT '发送时快照的关联订单',
  `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间（北京时间）',
  `updated_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '最后更新时间（北京时间）',
  PRIMARY KEY (`message_id`),
  KEY `idx_conv_time` (`conversation_id`, `created_at`),
  KEY `idx_related_order` (`related_order_id`),
  KEY `idx_sender_admin_id` (`sender_admin_id`),
  CONSTRAINT `fk_service_msg_conv` FOREIGN KEY (`conversation_id`) REFERENCES `service_conversation` (`conversation_id`),
  CONSTRAINT `fk_service_msg_order` FOREIGN KEY (`related_order_id`) REFERENCES `order_main` (`order_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='客服会话消息表（会话消息表，豁免 is_deleted，通过业务状态/归档管理）';
```

> **变更说明**：相比 v1.0 版建表语句，本次新增 `sender_admin_id` 字段（位于 `sender_role` 之后）与 `idx_sender_admin_id` 索引；表 `COMMENT` 显式标注豁免 `is_deleted` 理由，符合 §8.5 规范要求。
