# 餐食模板「存模板」50001 后端排查说明

> **文档用途**：小程序前端联调发现，勾选「设为餐食模板」后保存失败；本文档供 **pet-backend** 排查与自测。  
> **编写日期**：2026-06-14  
> **联调环境**：Sealos Devbox · `https://gnmopuadqqay.sealoshzh.site`  
> **前端仓库**：pet-app（本仓库）

---

## 1. 问题摘要

| 项 | 说明 |
|----|------|
| **现象** | 记一餐 / 编辑餐食页勾选「同时设为餐食模板」并提交后，Toast 提示「服务器内部错误」 |
| **业务码** | `50001` |
| **HTTP** | 500（推断，与全局错误码表一致） |
| **失败接口** | `PUT /api/v1/pets/{pet_id}/daily-records/{record_date}` |
| **触发条件** | 请求体含 `save_as_template: true` 且 `template_name` 非空 |
| **对照结论** | **同一请求体、同一餐食数据**，仅将 `save_as_template` 改为 `false` 即可成功保存 |

**结论（前端侧）**：餐食 PUT 主路径正常；失败集中在后端 **`save_as_template` 写入分支**（同步写入 `pet_meal_template` 相关表时未捕获异常）。

## 2. 复现步骤（小程序端）

1. 微信开发者工具登录已注册账号（联调用户 `user_id=72`）。
2. 进入 **宠物 Tab** → 选择宠物（联调 `pet_id=30`）→ 选择日期（联调 `2026-06-14`）。
3. **场景 A · 编辑餐食**：点击已有餐食 ✎ → 勾选「同时设为餐食模板」→ 填写模板名 → 保存。  
   **场景 B · 记一餐**：点击「+ 记一餐」→ 添加食物 → 勾选模板 → 填写模板名 → 保存。
4. 观察 Network：
   - `GET /meal-templates/name-availability` → **`code: 0`**（名称可用）
   - `PUT /pets/30/daily-records/2026-06-14` → **`code: 50001`**

**反向验证（已通过）**：

- 不勾选模板，编辑餐食 / 记一餐均可正常保存并在 Tab 展示。
- 说明鉴权、`meal_sessions` 全量替换、`session_id` upsert、`daily_*` 顶层字段均正常。

## 4. 接口契约参考（前后端约定）

摘自 `docs/项目开发说明-后端.md` §5.15 / PUT 日记录扩展：

| 字段 | 类型 | 说明 |
|------|------|------|
| `save_as_template` | boolean | 为 `true` 时保存用户级模板（文档写：取 `meal_sessions[0]` 快照） |
| `template_name` | string | 勾选存模板时必填，trim 后 1–16 字 |
| `overwrite_template` | boolean | 同名模板已存在时必须为 `true` 才覆盖 |
| `meal_sessions` | array | 全量替换；带 `session_id` 原地 upsert，无 `session_id` 新建 |

**餐食模板相关错误码（节选，正常应返回这些而非 50001）**：

| code | 含义 |
|------|------|
| 40022 | 模板名称为空 |
| 40023 | 模板名称超过 16 字 |
| 42207 | 模板数量达上限（50） |
| 42208 | 同名模板未传 `overwrite_template=true` |
| 42209 | 模板无有效食物项 |

**50001**：全局未捕获异常 / 服务器内部错误，不应出现在参数合法、表结构正确的正常存模板流程中。

---

## 5. 前端实现说明（供对照，非故障点）

前端在 `src/services/pet.js` 的 `buildDailyRecordPayload` 中组装 PUT 体：

- `meal_sessions`：记一餐时追加新 session；编辑时替换对应项并保留 `session_id`
- `save_as_template` / `template_name` / `overwrite_template`：勾选模板时附带
- `daily_mood` / `daily_weight_kg` / `daily_stool_health`：与 GET 一致，放在 **请求体顶层**（不嵌套 `daily_record`）

联调 Network 中实际 payload 与上述约定一致，**无需前端改字段名或结构**。

## 6. 后端排查建议

### 6.1 优先查看服务端日志

对 §3.1 请求体在 Devbox 重放一次 PUT，抓取 stack trace。常见根因：

1. **`pet_meal_template` / `pet_meal_template_item` 表或 v8 索引未就绪**  
   - 查重接口能工作 ≠ INSERT 路径所有列/生成列/唯一索引均正确  
   - 重点：`migrate:v7`、`migrate:v8`（`active_template_name` 生成列 · 软删后名称可复用）

2. **`save_as_template` 分支代码异常**  
   - 从 `meal_sessions[0]` 构建模板快照时空指针、字段映射错误  
   - 已有 `session_id` 的 session 与新建 session 处理不一致  
   - 事务内餐食已写入、模板 INSERT 失败但未映射为业务码

3. **未映射的数据库错误**  
   - 唯一键冲突、NOT NULL 违反等被全局 handler 吞掉为 `50001`

### 6.2 环境自检命令

在 **pet-backend** 项目根目录执行：

```bash
# 1. 确保餐食模板 Schema 已迁移
npm run migrate:v7
npm run migrate:v8

# 2. 餐食模板 API 自测（文档预期 15/15）
WECHAT_MOCK=true npm run verify:meal-template
```

若自测中 **「记一餐 PUT + save_as_template」** 相关用例失败，与本次联调现象一致。

### 6.3 建议用 curl 最小复现（Devbox）

将 `<token>` 替换为有效 Bearer Token，`pet_id` / `record_date` 按环境调整：

