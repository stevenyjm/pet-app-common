## 二、任务 1.1：基础设施前置决策

### 2.1.1 任务描述

基于需求点 A，完成以下两个关键决策：

1. **是否引入 Redis 序列号生成器基础设施**
   - 决策影响：表 `user_account`、表 `user_login_log`、表 `user_feedback` 的主键编码方案（`user_code`、`login_log_code`、`feedback_code`）均依赖 Redis 序列号。
   - 若引入：表 5 采用方案 C（Redis 序列号），表 1/8/9/9A/子表采用方案 A/B（时间戳+随机）。
   - 若不引入：表 5 需改回方案 A 或 B（DB 计数表），表 1 改回 DB 行锁方案。

2. **Redis 故障降级方案**
   - 选项 A：降级为 DB 计数表 + 行锁（牺牲性能但保证可用性）。
   - 选项 B：拒绝服务（快速失败，保证数据一致性）。
   - 选项 C：混合方案（核心业务降级、非核心业务拒绝服务）。

### 2.1.2 决策依据

| 维度 | 分析内容 |
|------|----------|
| **性能** | Redis 序列号生成器为内存操作，单次耗时 <1ms；DB 行锁方案需 SQL 查询 + 行锁，单次耗时 5-50ms。 |
| **可用性** | Redis 为单点故障，但本项目已在扫码登录、商品缓存、在线状态等场景使用 Redis，具备运维基础。 |
| **一致性** | Redis INCR 为原子操作，天然解决并发问题；DB 行锁方案需自行处理并发竞争。 |
| **复杂度** | Redis 方案需处理连接池、超时、故障转移；DB 方案实现简单但对数据库有压力。 |
| **当前 Redis 使用现状** | 项目已引入 `ioredis`，在扫码登录、商品缓存、在线状态等场景使用，Redis 连接池已配置。 |

## 五、风险与注意事项

### 5.1 基础设施决策风险

| 风险 | 影响 | 应对措施 |
|------|------|----------|
| Redis 未引入导致表 5 主键方案回退 | 需重新设计 DB 计数表方案，增加开发工作量 3-5 人日 | 优先决策 Redis 引入，复用现有基础设施，决策周期控制在 1 天内 |
| Redis 故障降级方案不明确 | 上线后 Redis 故障可能导致用户注册/登录日志功能中断 | 在决策阶段明确降级方案，并在阶段 3 配套实现降级逻辑 |

### 5.2 废除表清理风险

| 风险 | 影响 | 应对措施 |
|------|------|----------|
| 前端清理不彻底 | 小程序残留入口或死链 | 清理后需在小程序端逐一验证"我的"页面、设置页面等 |
| 历史数据未备份 | 废除表中若有重要历史数据将丢失 | DROP TABLE 前需导出数据备份 |
| 迁移脚本未同步 | 新项目初始化时会因找不到已删除表的迁移脚本而报错 | 清理项 E 需同步处理所有迁移脚本 |
| 隐性引用未清理 | 其他模块可能引用已删除的 Model 或服务 | 删除前需全局搜索关键字（`UserEmailVerify`、`emailBindService`、`user_email_verify` 等） |

### 5.3 注意事项

1. **废除表清理与基础设施决策可并行推进**，二者无依赖关系。
2. **表 12 `user_sms_log` 和表 13 `user_notification_setting`** 从未实际使用，清理风险最低，可优先执行。
3. **表 3/4** 涉及前端小程序"我的"页面的邮箱绑定功能，需前后端同步清理，清理完成后需端到端验证。
4. 所有删除操作前，需在测试环境完整验证一遍，确保无遗漏引用。
5. DROP TABLE 操作不可逆，务必确认无历史数据留存需求后再执行。
