## 二、迁移策略：重建表 + 数据迁移

### 2.1 总体策略

采用「重建表」策略，每张表的迁移步骤如下：

```
Step 1: 创建临时新表（按新结构，表名加 _new 后缀）
Step 2: 从旧表迁移数据到新表（生成新主键、映射字段）
Step 3: 校验数据完整性（行数对比、抽样校验）
Step 4: 删除旧表
Step 5: 重命名新表为原表名（RENAME TABLE）
Step 6: 创建索引与约束（新表不含外键约束）
```

### 2.2 user_account 特殊处理（映射桥梁）

由于跨域表仍引用 `user_account.user_id`，user_account 表的迁移需特殊处理：

**方案 A（推荐）：保留 user_id 作为过渡字段**
- 新表 user_account 同时包含 `user_code`（主键）和 `user_id`（过渡字段，保留旧值）
- 跨域表暂不修改，仍引用 user_id
- 待跨域表逐域改造完成后，统一删除 user_account.user_id 字段

**方案 B：新建 user_id_code_mapping 映射表**
- 新表 user_account 仅含 user_code（主键）
- 新建 user_id_code_mapping(user_id, user_code) 映射表
- 跨域表通过 JOIN 映射表获取 user_code
- 待跨域表改造完成后，删除映射表

### 2.3 数据迁移逻辑

| 表 | 数据迁移要点 |
|----|--------------|
| user_account | 生成 user_code（U+yyyyMMdd+4位数字），保留 user_id 作为过渡；created_at→create_time，updated_at→last_modified_time，status→user_status |
| user_profile | user_code 直接复用表1；gender→user_gender；inviter_user_id→inviter_user_code（需查映射表） |
| user_preferences | user_code 直接复用表1；移除 extra_json/legacy 字段；提醒数据迁移到 user_reminder |
| user_reminder | 从 user_preferences.extra_json.reminders 数组解析，逐条插入子表；生成 reminder_code |
| user_login_log | 生成 login_log_code（LL+yyyyMMdd+4位流水号）；user_id→user_code（查映射） |
| user_address | 生成 address_code（ADDR+user_code+3位序号）；user_id→user_code |
| user_browse_log | 生成 browse_log_code（BL+17位毫秒时间戳+4位base36）；user_id→user_code；product_id→product_code（需商品域映射，暂用占位） |
| user_refresh_token | 生成 refresh_token_code（RT+17位毫秒时间戳+4位base36）；user_id→user_code；expires_at→expire_time，revoked_at→revoke_time |
| user_feedback | feedback_code 直接复用原 feedback_no（零迁移成本）；user_id→user_code；order_id→order_code（需订单域映射，暂用占位）；processed_by→processed_by_code（需管理域映射，暂用占位）；type→feedback_type，status→feedback_status，processed_at→processed_time |
| user_broadcast | 从 user_message 中 message_type='system_broadcast' 的历史数据迁移到 user_broadcast |
| user_message | 生成 message_code（MSG+user_code+10位秒级时间戳+4位base36）；user_id→user_code；category→message_category，status→message_status；extra_json 拆分为 icon/tags/cycle + biz_type；biz_id→biz_code；sender_user_id→sender_user_code |

## 四、风险评估与回滚方案

### 4.1 风险评估

| 风险点 | 等级 | 说明 | 缓解措施 |
|--------|------|------|----------|
| 数据丢失 | 高 | 重建表过程中数据迁移不完整 | 迁移前后行数对比 + 抽样校验 + 全量备份 |
| 跨域表关联失效 | 高 | user_account 删除 user_id 后跨域表外键失效 | 方案A：保留 user_id 过渡字段 |
| 主键编码冲突 | 中 | Redis 序列号生成器故障 | 降级为 DB 行锁方案（已实现） |
| extra_json 解析失败 | 中 | user_preferences.extra_json 格式不标准 | 异常记录跳过，迁移后人工修复 |
| product_code/order_code 占位 | 中 | 跨域表未改造，biz_code 字段暂用占位值 | 待跨域表改造后回填真实值 |
| 迁移耗时过长 | 中 | 大表迁移锁表时间过长 | 分批迁移 + 低峰期执行 |

### 4.2 回滚方案

1. **迁移前**：全量备份数据库（`mysqldump`）
2. **迁移中**：每张表迁移后保留旧表备份（`_bak` 后缀），24小时后清理
3. **迁移失败**：
   - 单表失败：回滚该表（`RENAME TABLE user_account TO user_account_failed, user_account_bak TO user_account`）
   - 全局失败：从全量备份恢复（`mysql < backup.sql`）
4. **回滚条件**：
   - 数据行数不一致（差异 > 0）
   - 抽样校验失败（字段映射错误）
   - verify-db.js 校验失败
