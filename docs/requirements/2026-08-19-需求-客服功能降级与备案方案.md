## 1. 文档目的

本文档针对当前已上线的「联系客服」在线 IM 功能进行**降级**与**备案**：

1. **降级**：移除当前客服会话中"关联订单 / 关联商品"的上下文交互能力，将客服消息退化为**纯文字 + 图片**的简单消息形态。
2. **备案**：登记未来三阶段演进路径，明确各阶段范围与边界，避免后续返工：
   - **Level-1**（本期落地）：纯文字 + 图片消息，去除上下文关联 UI 与写入路径。
   - **Level-2**（中期规划）：用户可唤起"预设消息卡片"，卡片内含介绍文案与若干可交互选项（如「咨询订单」「咨询商品」），点击后在弹出的订单列表 / 商品列表中选择目标，并以"选择消息"形式回填到会话中。
   - **Level-3**（后期规划）：在 Level-2 基础上，支持会话内发送**可交互的实体信息卡片**（订单卡片 / 商品卡片），接收方点击卡片可跳转至对应的订单详情或商品详情页。

本文档**仅**进行方案拟定、各阶段开发任务规划与任务清单划分，**不**包含代码变更。Level-1 的代码实现将在本方案评审通过后另行启动。

## 2. 需求背景与降级动因

### 2.1 现状回顾

依据立项文档 [联系客服功能-方案与任务清单.md](./联系客服功能-方案与任务清单.md)，当前客服功能（已上线）具备以下能力：

- 用户与客服之间发送文字 / 图片消息；
- 会话级"活跃上下文"：`service_conversation.active_order_id` / `active_product_id`；
- 消息级"快照关联"：`service_message.related_order_id`；
- C 端聊天页提供「切换咨询订单」入口、订单卡片 / 商品卡片展示；
- 管理端聊天面板提供订单上下文侧栏，可修正关联订单。

### 2.2 降级动因

| # | 动因 | 说明 |
|----|------|------|
| D1 | 上下文写入与维护链路复杂 | 维护 `active_*` 状态、跨表外键约束、消息快照写入，对当前客服量级属于过度设计 |
| D2 | 用户使用频度低 | 实际会话中关联订单 / 商品的交互频次低，纯文字咨询占比高 |
| D3 | 后续能力可由 Level-2/3 渐进复用 | 现"活跃上下文"机制不够灵活，未来更倾向于"消息内嵌卡片"的形态，故先降级再演进 |
| D4 | 降低后续重构成本 | 趁活跃上下文数据量小，先收敛入口，避免后续 Level-2/3 重构时历史脏数据沉淀 |

### 2.3 商户确认结论（待确认项）

| # | 确认项 | 倾向结论 | 方案落点 |
|---|--------|----------|----------|
| Q1 | 是否保留历史消息中的 `related_order_id` 数据 | **保留**，仅停用新写入 | §5.2 / §5.7 |
| Q2 | C 端订单详情页 / 商品详情页的"联系客服"入口是否保留 | **保留入口**，但进入会话时不再带订单 / 商品参数 | §5.4 |
| Q3 | 管理端订单上下文侧栏是否保留 | **移除**侧栏 UI；详情接口字段保留返回（值为 `null`） | §5.5 |
| Q4 | 上下文相关 API 路由是否物理下线 | **不物理下线**，标记为 `Deprecated`，保留 6 个月兼容期 | §5.3 / §5.6 |
| Q5 | `service_conversation.active_order_id` / `active_product_id` 字段是否删除 | **不删除**，保留字段以备 Level-2/3 复用 | §5.2 |

> ⚠️ 本表为倾向结论，需商户在评审阶段最终确认。如商户对 Q2/Q3/Q4 有不同意见，方案相应章节需调整。

## 3. 三级方案对比

### 3.1 总览

| 维度 | Level-1（本期） | Level-2（中期） | Level-3（后期） |
|------|----------------|----------------|----------------|
| 消息形态 | 纯文字 + 图片 | 纯文字 + 图片 + **选择消息** | 纯文字 + 图片 + **可交互卡片消息** |
| 上下文关联 | 🚫 移除 UI 入口，停用新写入 | ✅ 通过预设卡片"选择目标" | ✅ 通过实体卡片承载信息 |
| 用户主动操作 | 仅输入文字 / 选图 | 点击预设按钮 → 选择订单 / 商品 | 点击卡片消息 → 跳转详情 |
| 数据库字段使用 | `related_order_id` 停用写入 | 复用 `related_order_id`，新增 `related_product_id` + `card_type` | 复用并扩展 `content_type` 增加 `card_order` / `card_product` |
| 后端接口 | 标记 `active-*` / `active-context` 为 Deprecated | 新增"预设卡片配置"接口、扩展发送消息接口 | 新增"卡片消息"发送接口、卡片渲染数据接口 |
| 前端组件 | 移除 `OrderPicker` / `ServiceOrderCard` / `ServiceProductCard` / `OrderContextPanel` 的渲染 | 新增 `PresetCardSheet` / `OrderPickerSheet` / `ProductPickerSheet` | 新增 `OrderCardMessage` / `ProductCardMessage` 渲染组件 |
| 落地范围 | 三端联动降级 | C 端新增唤起 + 后端扩展 + 管理端展示选择消息 | 三端渲染卡片 + 跳转链路 |
| 预计任务数 | 详见 §7.1 | 详见 §7.2 | 详见 §7.3 |

### 3.2 边界划分

```
Level-1 范围 ─────────────► 现状 → 纯文字消息
                              │
Level-2 范围 ─────────────► Level-1 + 用户唤起预设卡片选择目标
                              │
Level-3 范围 ─────────────► Level-2 + 卡片消息（可跳转详情）
```

**强约束**：Level-2 / Level-3 必须**在 Level-1 落地并稳定运行后**启动；Level-2 启动前，Level-1 范围内的废弃 API、组件代码须先归档清理。

## 5. Level-1 详细方案

### 5.1 范围与目标

| 维度 | 范围 |
|------|------|
| **本期实现** | Level-1（纯文字 + 图片消息） |
| **本期不做** | Level-2 预设卡片、Level-3 实体卡片 |
| **目标** | 1) 三端移除"关联订单 / 关联商品"的用户可见入口与 UI 渲染；<br>2) 后端停止向 `active_*` 与 `related_order_id` 写入新值；<br>3) 历史数据与字段保留，不破坏既有数据；<br>4) 上下文相关路由标记 `Deprecated`，进入 6 个月兼容观察期；<br>5) 同步更新 API 规范文档与三端开发说明文档。 |

### 5.2 数据库变更策略

**核心原则：Level-1 不进行任何 DDL 变更。**

| 字段 | 现状 | Level-1 策略 | 理由 |
|------|------|--------------|------|
| `service_conversation.active_order_id` | 存在，含 FK → `order_main` | **保留**，停止写入新值（写入路径置 NULL） | 备 Level-2/3 复用，避免迁移成本 |
| `service_conversation.active_product_id` | 存在，含 FK → `product` | **保留**，停止写入新值（写入路径置 NULL） | 同上 |
| `service_message.related_order_id` | 存在，含 FK → `order_main` | **保留**，停止写入新值（发送消息时置 NULL） | 历史消息快照保留，便于审计 |
| `service_message.content_type` | `ENUM('text','image')` | **不变更** | Level-1 仍用现有两种类型 |
| `service_message.sender_admin_id` | 已存在 | **不变更** | 与本降级无关，继续维护 |

**DDL 操作清单**：

- [ ] ❌ 不新增字段
- [ ] ❌ 不删除字段
- [ ] ❌ 不修改字段类型
- [ ] ❌ 不新增 / 删除索引
- [ ] ❌ 不新增 / 删除外键
- [ ] ❌ 不创建迁移脚本

> 📌 **特殊说明**：`service_message` 表已豁免 `is_deleted`，本降级不影响其豁免状态。

### 5.3 后端变更清单

#### 5.3.1 C 端 API 路由（`routes/service.js`）

| 路由 | Level-1 处理方式 |

## 6. Level-2 中期方案规划（备案）

### 6.1 范围

在 Level-1 基础上，**用户主动**唤起一个预设消息卡片：

- 卡片内含一段介绍文本（如"请选择您要咨询的内容类型"）；
- 卡片内含若干可交互选项按钮（如「咨询订单」「咨询商品」）；
- 用户点击选项后，弹出**订单列表 / 商品列表**（来自用户历史订单 / 浏览过的商品 / 收藏的商品）；
- 用户在列表中选择具体目标后，将该选择以**选择消息**形式回填到会话中；
- 选择消息可包含目标 ID 与摘要（如订单号 / 商品名），但**不会**渲染为可跳转的卡片（这是 Level-3 的范畴）。

| `service_conversation` | 不变更（不复用 `active_*` 字段，Level-2 走消息内嵌模式） |

### 6.3 后端变更预告

- 新增"预设卡片配置"接口（`GET /service/preset-cards`），返回可用卡片模板列表；
- 扩展发送消息接口，支持 `content_type='selection'`；
- 新增"用户可选订单列表"接口（`GET /service/orders/selectable`）与"用户可选商品列表"接口（`GET /service/products/selectable`）；
- `formatServiceMessage` 扩展支持 `selection` 类型消息的序列化。
