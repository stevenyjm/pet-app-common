## 一、背景与目标

### 1.1 当前状态（4 层转换，存在冗余）

```
小程序前端代码 (camelCase)
  → 请求拦截器 deepToSnakeCase()         [第1层]
  → 自动追加 useCamelCase:true 参数
  → 参数 deepToSnakeCase → use_camel_case=true [第2层]
  → 后端 camelizeResponse 中间件转换响应 [第3层]
  → 前端响应拦截器 deepToCamelCase()     [第4层，兜底/重复]
→ 小程序前端代码 (camelCase)
```

管理端类似，但管理端不追加 `use_camel_case` 参数，由前端响应拦截器单独转换。

### 1.2 目标终态（仅保留 1 层转换）

```
小程序 / 管理端前端代码 (camelCase)
  → 请求参数直接传 snake_case（与后端接口文档一致，不做转换）
  → 后端直接返回 snake_case（不做转换）
  → 前端响应拦截器统一 deepToCamelCase()  [唯一转换点]
→ 前端代码 (camelCase)
```

**选择理由**：
- 数据库、Model、SQL、后端业务代码使用 snake_case，无需修改，迁移成本为 0
- 前端 JavaScript/TypeScript 使用 camelCase，符合语言习惯
- 只在响应侧做 1 层转换，性能最优、心智负担最低
- 所有请求 URL 不再携带冗余 `use_camel_case=true` 参数

#### 修改点 B（可选，谨慎评估）：移除请求拦截器 `deepToSnakeCase`

> ⚠️ **高风险操作**：需确认所有 `src/api/**` 和 `src/services/**` 中的请求参数命名已改为 snake_case。若仍有前端传 camelCase 参数的代码，移除后将导致后端接收参数名为 camelCase，无法匹配 `req.body.xxx_snake`，引发大面积参数丢失。

**若暂不做此步**（推荐）：保留 `deepToSnakeCase`，仅移除 `useCamelCase` 参数。此时链路为：

```
前端 camelCase → deepToSnakeCase → 后端 snake_case 接收 → snake_case 响应 → deepToCamelCase → 前端 camelCase
```

仍达成「移除 use_camel_case 参数 + 后端中间件」目标，转换层从 4 层 → 2 层。

**修改前（第 57-58 行）：**

```javascript
// 请求拦截：将 camelCase 参数转为 snake_case 发送给后端
const requestData = data ? deepToSnakeCase(data) : data
```

**修改后（若全量 snake_case 化已完成）：**

```javascript
// 请求参数约定使用 snake_case，不再做自动转换
const requestData = data
```

---

#### 修改点 C：响应拦截器 `deepToCamelCase` —— **保留不动**

此转换是终态下唯一需要保留的层，**不修改**：

```javascript
// 响应拦截：将 snake_case 响应数据转为 camelCase
const camelBody = body ? deepToCamelCase(body) : body
resolve(camelBody)
```

### 9.1 紧急回滚（发现线上 Bug 时）

| 受影响端 | 回滚操作 | 预计耗时 |
|---------|---------|---------|
| **小程序前端** | 恢复 `pet-app/src/utils/request.js` 中 `useCamelCase: true` 的追加，重新发布小程序审核 | 5 分钟 + 审核时间 |

| **管理端** | 无需回滚（自身拦截器兜底） | 0 分钟 |

### 9.2 小程序快速临时兼容（不等审核）

若后端已发布、前端旧版用户大量报错，可后端做**热修复兼容**，无需等待小程序审核：

在 `pet-app-backend/middleware/camelizeResponse.js` 中将默认行为从 `false` 改为 `true`，临时让所有响应都转 camelCase（等价于旧版行为）：

```javascript
// 临时回滚兼容：当旧版小程序未带 use_camel_case 时也强制转换
const useCamelCase = req.query.use_camel_case !== undefined
  ? req.query.use_camel_case === 'true'
  : true;  // ← 改这里为 true，恢复过渡期默认行为
```

待小程序新版本覆盖 > 95% 用户后，再切回 `false` 并最终移除中间件。

## 十一、风险与注意事项

### 11.1 小程序版本碎片化

**风险**：旧版小程序（仍带 `use_camel_case=true`）请求后端，此时后端若已移除中间件，`use_camel_case` 查询参数会被忽略，返回 snake_case。旧版小程序响应拦截器 `deepToCamelCase` 仍工作，因此**实际兼容**。但万一旧版有代码直接使用 `res.data.snake_case_field` 而未走拦截器转换（绕过 request.js 封装），会报错。

**缓解**：后端中间件先保留 2-4 周，监控线上日志中 `use_camel_case=true` 的请求比例，低于 1% 再移除。

### 11.2 管理端接口直接访问

**风险**：第三方脚本、Postman 直接调用管理端 API 时，之前若依赖 `use_camel_case=true` 拿 camelCase 响应，移除后返回 snake_case，脚本会失败。

**缓解**：在管理端发布公告，通知 API 使用方统一按 snake_case 对接。

### 11.3 离线脚本依赖

**风险**：`scripts/verify-*.js` 等脚本如果断言响应为 camelCase 字段，会失败。

**缓解**：运行所有 `npm run verify:*` 脚本，修复断言为 snake_case 字段名。
