## 一、需求背景与目标

### 1.1 需求来源

来源于 `todo.txt` 第 224~227 行「预设标签内置」新增需求：

- 将**日常提醒的预设提醒标签**，内置在小程序端中，移除商户管理端下的配置页面
- 将**宠物状态编辑中的预设心情、预设排便状态**，内置在小程序端中，移除商户管理端下的配置

### 1.2 需求目标

将三类业务枚举/选项从「后端数据库动态管理 + 管理端可视化配置」模式，变更为「小程序端静态常量内置」模式：

| 类别 | 当前模式 | 目标模式 |
|------|---------|---------|
| 日常提醒 · 预设提醒标签 | 后端 DB 表 `reminder_tag_dict` + 管理端配置页 + 小程序端 HTTP 拉取 | 小程序端 `constants/` 静态常量内置 |
| 宠物日记录 · 预设心情 | 小程序端已内置常量（`MOOD_OPTIONS`） | 确认并对齐管理端输入交互 |
| 宠物日记录 · 预设排便状态 | 小程序端已内置常量（`STOOL_HEALTH_OPTIONS`） | 确认并对齐管理端输入交互 |

### 1.3 变更收益

1. **减少接口依赖**：小程序初始化/页面加载时无需额外请求后端字典接口，降低首屏延迟
2. **简化运维**：商户无需关心字典配置，选项随版本迭代发布，变更可控
3. **代码一致性**：三端（小程序/管理端/后端枚举校验）使用同一套来源
4. **降低管理端复杂度**：减少一个配置模块，侧栏导航更精简

## 三、方案设计

### 3.1 总体方案

采用「三端分批改造 + 向后兼容窗口」策略：

```
Phase 1：小程序端替换（内置常量，保留接口 fallback）
    ↓
Phase 2：管理端移除（隐藏入口 + 注释路由 + 移除/归档代码）
    ↓
Phase 3：后端下线管理端 CRUD API（保留 C 端 GET 一段过渡期）
    ↓
Phase 4：数据库表归档（逻辑标记 + 文档备案，不做物理删除）
```

### 3.2 预设提醒标签内置方案

#### 3.2.1 小程序端内置常量设计

在 `pet-app/src/constants/` 下新增或扩充提醒标签常量文件：

```javascript
// pet-app/src/constants/reminderTag.js

/** 预设提醒标签分类（与管理端常量 REMINDER_TAG_CATEGORIES 对齐） */
export const REMINDER_TAG_CATEGORIES = [
  '医疗健康',
  '日常护理',
  '饮食喂养',
  '外出活动',
  '美容造型',
  '其他',
] as const

export type ReminderTagCategory = (typeof REMINDER_TAG_CATEGORIES)[number]

/** 预设提醒标签项（与后端 v28 种子数据一致） */
export interface PresetReminderTag {
  name: string
  category: ReminderTagCategory
  sort: number
}

export const PRESET_REMINDER_TAGS: PresetReminderTag[] = [
  { name: '驱虫', category: '医疗健康', sort: 10 },
  { name: '疫苗', category: '医疗健康', sort: 20 },
  { name: '体检', category: '医疗健康', sort: 30 },
  { name: '吃药', category: '医疗健康', sort: 40 },
  { name: '洗澡', category: '日常护理', sort: 10 },
  { name: '剪指甲', category: '日常护理', sort: 20 },
  { name: '刷牙', category: '日常护理', sort: 30 },
  { name: '梳毛', category: '日常护理', sort: 40 },
  { name: '喂食', category: '饮食喂养', sort: 10 },
  { name: '补水', category: '饮食喂养', sort: 20 },
  { name: '遛狗', category: '外出活动', sort: 10 },
  { name: '美容', category: '美容造型', sort: 10 },
  { name: '记录', category: '其他', sort: 10 },
]

/**
 * 获取按分类分组后的预设标签
 * 用于提醒编辑页的分组网格展示
 */
export function getGroupedPresetTags(): Record<ReminderTagCategory, PresetReminderTag[]> {
  const grouped = {} as Record<ReminderTagCategory, PresetReminderTag[]>
  for (const cat of REMINDER_TAG_CATEGORIES) {
    grouped[cat] = []
  }
  for (const tag of PRESET_REMINDER_TAGS) {
    grouped[tag.category].push(tag)
  }
  // 每组内按 sort 升序
  for (const cat of REMINDER_TAG_CATEGORIES) {
    grouped[cat].sort((a, b) => a.sort - b.sort)
  }
  return grouped
}
```

#### 3.2.2 小程序端 fallback 策略

`edit.vue` 改造：
- 优先使用内置常量 `PRESET_REMINDER_TAGS`
- **保留** `getReminderTagDict()` 调用，但改为「可选增强」：若接口返回非空 list，则与内置取并集，避免后端未来若临时扩展时小程序不可用（过渡期可随时关闭）

```
loadPresetTags() {
  // Step 1: 使用内置常量作为基底
  this.presetTags = PRESET_REMINDER_TAGS
  // Step 2: 尝试接口拉取（静默，失败不阻塞）
  getReminderTagDict()
    .then(data => {
      if (data?.list?.length > 0) {
        // 去重合并（可选增强）
        this.presetTags = mergePresetTags(this.presetTags, data.list)
      }
    })
    .catch(() => { /* 静默忽略 */ })
}
```

### 3.3 心情与排便状态改造方案

1. **小程序端常量升级**：同步修改 `pet-app/src/constants/pet.js`，将原 5 项心情、4 项排便状态整体替换为新的 13 项心情、7 项排便状态（与本需求顶部指定一致）。

#### 3.3.3 P0-02 管理端交互选型结论（已评审通过 ✅）

| 维度 | 选项 A：纯下拉 | 选项 B：`<el-select filterable allow-create>` ✅ |
|------|---------------|-----------------------------------------------|
| 旧值回显 | ❌ 历史值（如排便「正常」）无法在下拉中展示，会被清空或报错 | ✅ `allow-create` 使旧值以「用户创建项」形式回显，值无损 |
| 管理员操作灵活性 | ❌ 若需补充应急状态（如「术后观察中」），只能走发版 | ✅ 管理员可临时输入自定义值，不阻塞业务 |
| 枚举一致性风险 | ⚠️ 若有人写代码绕过前端仍可入库脏值，管理端也无法展示 | ✅ 「预设优先 + 自定义兜底」兼顾一致与灵活，与小程序端 Picker 逻辑镜像 |
| 排便零交集风险 | ❌ 7 项新枚举与旧 4 项零交集，历史数据全部不可读 | ✅ 全部历史值可正常展示并再次保存 |

**最终结论（P0-02 通过 ✅）**：心情与排便状态管理端交互统一使用 `<el-select filterable allow-create default-first-option>`，其中：
- `filterable`：支持中文搜索（13 项心情 + 7 项排便搜索友好）
- `allow-create`：关键能力，用于兼容历史旧值与临时自定义
- `default-first-option`：键盘操作时回车即选第一项，效率提升
- **禁止**在选项末尾追加「其他…」或「自定义…」入口，自定义能力由 `allow-create` 原生提供

### 6.2 过渡期与回滚预案

#### 6.2.1 P0-03 过渡期窗口确认（已评审通过 ✅）

本需求涉及 2 处「旧资源保留窗口」，结论如下：

| 资源 | 当前状态 | 保留截止 | 后续动作 | 负责端 |
|------|---------|---------|---------|--------|
| **C 端 `GET /reminder-tag-dict`** | Phase 3 下线管理端 CRUD 后仍保留给旧版小程序 fallback 调用 | **2026-09-20 23:59:59（北京时间）**，共 31 天（30 天整 + 当日剩余） | 2026-09-21 起的下一次后端迭代中，取消挂载 `routes/reminderTagDict.js`，路由返回 410 Gone；同时在 `scripts/schema.sql` 中标注表彻底弃用 | 后端 |
| **管理端路由 `/users/reminder-tag-dict` 源码** | Phase 2 归档 @deprecated | 长期保留（不做物理删除） | 下一「代码清理专项」评估是否物理删除；删除前需再次 grep 三端调用方 | 管理端 |
| **`reminder_tag_dict` 数据库表** | Phase 4 标注 @deprecated 不参与新业务 | 长期保留（不做 DROP TABLE） | 若 90 天（即 2026-11-18 前）无历史读取需求，可启动「物理删除提案」另行评审 | 后端 |

> **为什么 30 天过渡期？**
> - 微信小程序发布审核一般 1~3 个工作日，灰度/全量覆盖用户周期约 7~14 天；
> - 预留 1 个发版周期（2 周）+ 1 个缓冲周期（2 周），确保 99%+ 用户升级到内置常量的版本；
> - 30 天内若发现 fallback 接口空 list 引发异常仍可快速热修。

| 阶段 | 回滚方式 |
|------|---------|
| Phase 1 完成后发现内置标签内容错误 | 快速回滚 `edit.vue` 至「以接口优先」模式；常量可热修 |
| Phase 2 完成后管理端误删字典页需要恢复 | 恢复路由 + 解除 `_deprecated/` 目录归档（代码未物理删除） |
| Phase 3 完成后发现某旧小程序版本完全依赖接口（无内置 fallback） | 在 2026-09-20 过渡期结束前，可随时恢复 C 端接口的响应增强逻辑；恢复管理端路由挂载仅需改 `routes/admin/index.js` 一行 |
| Phase 4 完成后 | 表未物理删除，Model 未删，随时可恢复读能力 |
