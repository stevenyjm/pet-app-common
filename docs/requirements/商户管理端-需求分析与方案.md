## 2. 商户需求确认清单

以下 7 项已与商户确认，**作为本期方案的约束条件**。

| # | 确认项 | 商户意见 | 方案结论 |
|---|--------|----------|----------|
| 1 | 在线用户定义 | 采用 **严格在线** | 需 Redis 会话心跳 + 活跃窗口判定；见 §4.1 |
| 2 | 管理端载体 | **全部放在 PC Web**；一期 **不改动** C 端小程序 | 新建独立 Web 管理项目；小程序零变更；隐藏入口 📋 二期 |
| 3 | 首页封面图 | **仅展示**，无需点击跳转详情 | 商户在 PC 端上传/更换图片即可；C 端只渲染图片 URL |
| 4 | 重大操作确认 | 广播等涉及大量用户的操作需 **弹窗二次确认** | PC 管理端 UI 强制确认 + 后端校验；见 §5.4 |
| 5 | 动态数据删除 | 使用 **软删除**；数据库清洗功能 **一期不做** | 商品/资讯等 `deleted_at` 或 `status`；物理清理 📋 未来 |
| 6 | 隐藏入口登录（二期） | 需 **强校验**，防误入后越权 | 原方案已为服务端强校验；见 §7.2；一期不涉及 |
| 7 | 操作人员 | **单人商户**，无多人并发操作 | 一期单管理员账号即可；RBAC 多角色 📋 未来扩展 |

**结论**：上述确认项与初版技术方案 **无冲突**；主要影响为 **一期范围收窄**（仅 PC Web）、**在线统计实现方式明确**、**首页封面需求简化**。

## 4. 功能需求与可行性

### 4.1 数据统计 · 严格在线用户

#### 商户确认

采用 **严格在线** 定义，而非「最近登录」等近似口径。

#### 技术定义（建议写入验收标准）

| 项 | 定义 |
|----|------|
| 在线判定 | 用户在 **滑动时间窗口 W** 内至少有一次 **有效心跳** |
| 建议窗口 W | **5 分钟**（可配置 `ONLINE_WINDOW_SECONDS=300`） |
| 心跳来源 | C 端小程序在 **已登录** 状态下，前台活跃时每 **60–120 秒** 调用 `POST /presence/heartbeat`（一期需新增 C 端 **仅心跳** 接口，不改变页面与入口） |
| 存储 | **Redis**：`online:user:{userId}` TTL = W；`SCARD online:users` 或 HyperLogLog 统计人数 |
| 管理端展示 | 当前在线人数、近 W 分钟内在线用户列表（分页）；**不承诺**秒级精确到「正在看哪一页」 |

> **说明**：严格在线依赖 C 端心跳上报。商户确认一期不改小程序 **页面与入口**，但增加 **无 UI 的后台心跳请求** 属于基础设施埋点，不改变用户可见功能；若商户连心跳也不希望改动 C 端，则在线人数只能 📋 延后至 C 端配合上线后。 **建议一期允许仅新增心跳 API 调用**（`App.vue` / 请求拦截层，用户无感知）。

#### 其他统计（一期可做，不依赖 Redis）

| 指标 | 数据来源 |
|------|----------|
| 注册用户数 / 今日新增 | `user_account.create_time` |
| 今日/本周订单数、GMV | `order_main` 聚合 |
| 待发货 / 待售后数量 | `order_status=20`、`after_sales` 待审核 |
| 数据导出 | CSV/Excel 流式下载，单次上限建议 1 万行 |

## 5. 非功能需求

### 5.1 一期范围：仅 PC Web

| 包含 | 不包含（二期） |
|------|----------------|
| PC 浏览器访问的管理后台 | 小程序隐藏入口、管理分包 |
| 新建 `/api/v1/admin/*` 管理 API | C 端 Tab/页面结构变更 |
| Admin 账号登录 | 小程序内商户轻量操作 |

### 5.2 单人商户

- 一期仅 **1 个** `admin_user` 账号（账号密码 + 可选绑定微信 openid 备二期用）。
- **不实现**：多管理员、角色分工、并发编辑锁、操作人区分（审计日志可预留 `admin_user_id` 字段默认为 1）。

### 5.3 鉴权方案

| 层级 | 方案 |
|------|------|
| 管理 API | `Authorization: Bearer <adminAccessToken>` |
| 签发 | `POST /admin/auth/login`（账号 + 密码，bcrypt） |
| 有效期 | accessToken 4h；refreshToken 7d（可配置） |
| 兼容 | 保留 `X-Admin-Key` 供脚本/`verify:*` 自测 |
| C 端隔离 | 普通 User JWT **不能** 调用 `/admin/*` |

**禁止**：在浏览器或小程序内嵌 `ADMIN_API_KEY`。

### 5.4 重大操作二次确认（商户确认）

以下操作在 PC 管理端必须 **弹窗二次确认**，且后端校验 `confirm_token` 或请求体显式 `confirmed: true`：

| 操作 | 确认文案要点 |
|------|--------------|
| 全体用户消息广播 | 展示预估接收人数，「此操作将向 **N** 位用户发送消息，不可撤回」 |
| 指定批量用户广播 | 展示 user_id 数量 |
| 软删除商品/资讯（影响 C 端展示） | 商品名称 + 「下架后用户不可见」 |
| 修改用户协议/隐私政策 | 「将影响所有用户可见内容」 |

**UI 要求**：确认框需 **单独点击「确认发送/确认删除」**；输入框二次校验（如广播时输入 `发送` 或接收人数）📋 可选增强。

### 5.5 软删除与数据清洗

| 一期 | 未来 |
|------|------|
| 软删除字段 + 列表过滤 | 物理清洗、归档、回收站彻底删除 |
| 无「清空已删数据」按钮 | 需单独评审与备份流程 |

> 完整任务拆分、排期与验收见 **[商户管理端-二期任务清单.md](./商户管理端-二期任务清单.md)**。

#### 二期隐藏入口鉴权说明（回应确认项 #6）

原示例方案 **已是强校验**，不仅依赖 UI 隐藏：

1. 隐藏入口仅负责 **路由发现**，不构成授权。  
2. 管理分包内必须 **微信登录** → 后端比对 `admin_user` 白名单（openid 或预绑定）。  
3. 比对失败：**403 + 立即返回 C 端首页**，不缓存 admin token。  
4. Admin JWT 与 C 端 User JWT **分类型签发**，payload 含 `role: admin`。  
5. 所有 `/admin/*` 在服务端校验，**无法**通过篡改前端路由绕过。

一期不涉及上述流程；二期按此标准实现即可满足商户「强校验」要求。

## 11. 结论

1. 商户确认的 7 项细节 **已全部纳入** 本方案；与初版分析 **一致且无冲突**。  
2. **一期已基本交付**：`pet-app-admin-web`（Vue 3 + TypeScript，M0~M5 Web 功能）+ 管理 API（M0~M4 后端）+ Redis 在线统计 + C 端无感心跳与封面 URL 读取（代码已合入）。  
3. **一期唯一功能缺口**：微信原路退款（BE-405）；**联调验收与生产上线** 尚待完成。  
4. 小程序隐藏入口、多管理员、数据库清洗、批量发货等 **明确列入二期**，任务见 [商户管理端-二期任务清单.md](./商户管理端-二期任务清单.md)。  
5. 广播等重大操作 **必须二次确认**，软删除 **一期生效**，物理清洗 **不做**。  
6. 隐藏入口二期方案 **已含服务端强校验**，满足商户防误入要求。
