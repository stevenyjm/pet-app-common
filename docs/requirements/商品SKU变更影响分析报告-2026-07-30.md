## 三、根因分析

### 3.1 双库存源数据流

当前系统存在**两套独立的库存数据源**，业务链路使用混乱：

```text
┌─────────────────────────────────────────────────────────────────┐
│                    product_sku.stock（库存源 A）                │
│  - 管理员通过 updateSku 修改                                    │
│  - 购物车 add/update 校验使用                                   │
│  - isProductInvalid 判定使用（sku.stock <= 0 → invalid）        │
│  - C端商品详情回退使用                                          │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│              inventory_real_time.available_qty（库存源 B）      │
│  - 下单前校验使用（orderController.createOrder）                │
│  - 下单预占（reserveStock）：available_qty -, locked_qty +      │
│  - 取消释放（releaseStock）：available_qty +, locked_qty -      │
│  - 出库扣减（deductStockWithFIFO）：locked_qty -                │
│  - C端商品详情优先使用                                          │
└─────────────────────────────────────────────────────────────────┘

⚠️ 两源之间无同步机制
```

### 3.3 期望链路 vs 实际链路

**期望链路（管理员改库存）**：

```text
管理员改库存 → 更新 inventory_real_time → 写入 inventory_flow 流水
            → 同步刷新 product_sku.stock（或废弃该字段）
            → 失效缓存 → C端/购物车看到最新库存
```

**实际链路（管理员改库存）**：

```text
管理员改库存 → 只更新 product_sku.stock
            → inventory_real_time 不变 ❌
            → inventory_flow 无记录 ❌
            → 失效缓存（已修复）→ C端优先读 inventory_real_time 看不到变化 ❌
```

## 四、不符合预期 / 错误现象汇总

### 4.1 🔴 P0 问题（严重，影响核心业务正确性）

#### 问题 1：双库存源不一致导致超卖或库存展示错乱

**现象**：

1. 管理员把 `product_sku.stock` 从 100 改为 0 → 购物车立即标记"库存不足"，但 `inventory_real_time.available_qty` 仍是 100，用户在商品详情页仍看到"有货"并可下单
2. 管理员把 `product_sku.stock` 从 0 改为 100 → 购物车允许加入，但下单时 `reserveStock` 可能因 `inventory_real_time` 记录不存在而抛"库存不存在"404
3. 下单预占后 `inventory_real_time.available_qty` 减少，但 `product_sku.stock` 不变 → 购物车校验通过的库存数与实际可下单数不一致，**可能超卖**

**根因**：见 §3.1 双库存源数据流

**影响范围**：购物车、C端商品详情、下单流程

#### 问题 2：管理员改库存不写流水

**现象**：

- `updateSku()` 修改 stock 时直接 `sku.update({ stock: payload.stock })`，未调用 `inventoryService.adjustStock()`
- `inventory_flow` 表缺失管理员手动调整记录
- 财务对账、库存盘点数据不完整
- 审计日志缺失，无法追溯库存调整历史

**代码证据**：[adminProductService.js#L528](file:///c:/Users/22188/Desktop/宠物生鲜电商开发项目/pet-app-backend/services/adminProductService.js#L528)

**影响范围**：库存审计、财务对账、盘点

### 4.2 🟡 P1 问题（重要，影响用户体验或数据完整性）

#### 问题 3：停售 SKU 不取消待支付订单

**现象**：

- `updateSku` 改 status=0 或 `deleteSku` 时：
  - 购物车中该 SKU 会标记 invalid
  - **但已存在的待支付订单不取消、不通知用户**，用户仍可完成支付
- 后果：用户支付了一个已停售的商品，管理员需要手动处理退款

**代码证据**：[adminProductService.js#L584-612](file:///c:/Users/22188/Desktop/宠物生鲜电商开发项目/pet-app-backend/services/adminProductService.js#L584-612)（deleteSku 仅切换 card_display_sku_id，不处理待支付订单）

#### 问题 4：价格变更无用户通知机制

**现象**：

- 管理员改 SKU 价格时返回 `pending_order_count` 给管理端，仅弹提示
- **不通知用户**，待支付订单用户不知情
- 用户可能按旧价支付后看到新价更低而投诉，或新价更高而觉得被欺诈

**影响范围**：用户体验、客诉风险

#### 问题 5：updateSku 缺事务保护

**现象**：

- `updateSku`（[L508-582](file:///c:/Users/22188/Desktop/宠物生鲜电商开发项目/pet-app-backend/services/adminProductService.js#L508-582)）涉及多步写操作：
  1. 更新 SKU 字段
  2. 切换 card_display_sku_id
  3. 更新 product.original_price
  4. 失效缓存
- **未使用事务**，中间任何一步失败会导致数据不一致
- 例如：SKU 已停售但 card_display_sku_id 未切换 → 商品卡片显示一个已停售的规格

**影响范围**：数据一致性

#### 问题 6：isProductInvalid 未检查 is_hidden

**现象**：

- 商品被 `deleteProduct()`（hide）后，`product.is_hidden=true`，但 `product.status` 可能仍是 1
- `isProductInvalid` 仅检查 `product.status !== 1`，**不检查 `product.is_hidden`**
- 后果：商品被 hide 后，购物车中商品可能仍显示"在售"

**代码证据**：[productHelpers.js#L253-257](file:///c:/Users/22188/Desktop/宠物生鲜电商开发项目/pet-app-backend/utils/productHelpers.js#L253-257)

### 4.3 🟢 P2 问题（优化，提升系统健壮性）

#### 问题 7：批次库存与 SKU 库存脱节

**现象**：

- `deductStockWithFIFO` 操作 `batch_info.quantity` 和 `inventory_real_time`
- 管理员改 `product_sku.stock` 不影响 `batch_info`
- 后果：批次库存汇总数 ≠ `product_sku.stock`，盘点数据不一致

#### 问题 8：SKU 删除不检查在售订单

**现象**：

- `deleteSku` 仅检查"商品必须至少拥有一个规格"，不检查是否有未完成订单关联该 SKU
- 历史订单的 sku_snapshot 已冻结，展示无问题
- 但 `outboundService.createOutbound` 在支付回调时通过 `detail.sku_id` 查询 SKU，若 SKU 已"删除"（status=0 但记录还在），FIFO 扣减仍可工作
- **风险点**：若未来增加物理删除逻辑，会破坏出库流程

#### 问题 9：管理员改库存未校验预占库存

**现象**：

- `updateSku()` 修改 stock 时不检查 `inventory_real_time.locked_qty`（已预占数量）
- 管理员可以把 `product_sku.stock` 改为 0，但 `inventory_real_time.locked_qty` 中的预占数量仍可正常支付出库
- 这本身不影响业务正确性，但管理员看到的 stock 数与实际可售数脱节，容易误判

## 五、修复方案

### 5.1 方案选型

| 问题 | 方案 A | 方案 B | 最终选择 |
|------|-------|-------|---------|
| 双库存源 | 废弃 `product_sku.stock`，统一用 `inventory_real_time` | 双向同步两个数据源 | **方案 A**：单一数据源更可靠，避免同步复杂性 |
| 改库存不写流水 | 在 `updateSku` 中调用 `adjustStock` | 单独提供库存调整 API | **方案 A**：复用现有 service，最小改动 |
| 停售不取消订单 | 自动取消待支付订单 | 推送消息让用户自行决定 | **方案 B**：避免强制取消引发客诉，让用户知情 |
| updateSku 无事务 | 包裹 `sequelize.transaction` | 改用乐观锁 | **方案 A**：事务更直观 |
| is_hidden 未检查 | 在 `isProductInvalid` 中补充判定 | 在 `buildProductWhere` 中过滤 | **两者并行**：列表过滤 + 失效判定双重保障 |
