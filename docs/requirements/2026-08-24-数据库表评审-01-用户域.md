#### 字段介绍

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| user_id | BIGINT | PK, AUTO_INCREMENT | 主键 |
| openid | VARCHAR(64) | NOT NULL, UNIQUE | 微信 openid |
| unionid | VARCHAR(64) | NULL | 微信 unionid |
| session_key | VARCHAR(128) | NOT NULL | 微信 session_key |
| status | TINYINT | NOT NULL, DEFAULT 1 | 1-正常 0-封禁 |
| created_at | DATETIME | NOT NULL, DEFAULT CURRENT_TIMESTAMP | 创建时间 |

| last_login_time | DATETIME | NULL | 最后登录时间 |
| is_deleted | TINYINT | NOT NULL, DEFAULT 0 | 逻辑删除：0-未删除，1-已删除 |

#### 建表语句

```sql
CREATE TABLE IF NOT EXISTS `user_account` (
  `user_id` BIGINT NOT NULL AUTO_INCREMENT,
  `openid` VARCHAR(64) NOT NULL,
  `unionid` VARCHAR(64) DEFAULT NULL,
  `session_key` VARCHAR(128) NOT NULL,
  `status` TINYINT NOT NULL DEFAULT 1 COMMENT '1-正常 0-封禁',
  `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间（北京时间）',
  `updated_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '最后更新时间（北京时间）',
  `last_login_time` DATETIME DEFAULT NULL,
  `is_deleted` TINYINT NOT NULL DEFAULT 0 COMMENT '逻辑删除：0-未删除，1-已逻辑删除',
  PRIMARY KEY (`user_id`),
  UNIQUE KEY `uk_openid` (`openid`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

#### 备注说明

- `user_id` 为逻辑主键（`BIGINT AUTO_INCREMENT`），违反 D1 业务主键规则
- `status` 字段名易混淆（联表查询时无法区分表源），违反 D2 字段表源前缀规则
- `created_at` / `updated_at` 命名不符 D3 时间字段命名（应为 `create_time` / `last_modified_time`）
- 时间字段使用 `DEFAULT CURRENT_TIMESTAMP` / `ON UPDATE CURRENT_TIMESTAMP`，违反 D3 维护方式规则（应后端推送）
- 无表级 `COMMENT`
- `openid` 等部分字段缺失 `COMMENT`

### 第三部分：用户评审决策

> **填写说明**：请对以下变更项逐项决策。决策列可选：`✅ 采纳` / `❌ 不采纳` / `⚠️ 部分采纳` / `🔄 用户自定义`。若选 `🔄 用户自定义`，请在"最终值"列填写您的方案。

#### 决策对照表

| 变更项 | 旧值 | 建议值 | 决策 | 最终值 |
|--------|------|--------|------|--------|
| 主键 | user_id BIGINT AUTO_INCREMENT | user_code VARCHAR(16) | ✅ 采纳 | user_code VARCHAR(16) |
| user_code 编码格式 | - | U00000001（前缀U+8位数字） | 🔄 用户自定义 | U + yyyyMMdd + 4 位数字（不使用全0值），如 `U202608250001`，当日下第几个用户 |
| user_code 字段长度 | - | VARCHAR(16) | ✅ 采纳 | VARCHAR(16) |
| user_code 并发安全方案 | - | （待用户决策） | 🔄 用户自定义 | Redis 序列号生成器 `seq:user_code:{yyyyMMdd}` + 当日过期；与表5/表11 序列号生成器共用基础设施；Redis 故障时降级为 DB 计数表 + 行锁 |

| 字段表源前缀 | status | user_status | ✅ 采纳 | user_status |
| is_deleted | DEFAULT 0 | DEFAULT 0 | ✅ 采纳 | DEFAULT 0（保留） |
| COMMENT 补充 | 部分缺失 | 全部补充 | ✅ 采纳 | 全部补充 |

#### 决策说明

**1. 业务主键编码方案（用户自定义：U + yyyyMMdd + 4 位数字）**

- 格式：`U` + `yyyyMMdd`（8 位日期） + 4 位数字（不使用全 0 值）
- 示例：`U202608250001`（共 13 位）
- 长度：13 位，VARCHAR(16) 余量 3 位
- **与 §8.2 规范差异说明**：§8.2 规范定义为 `U00000001`（前缀 U + 8 位数字，不带日期）；用户自定义为 `U + yyyyMMdd + 4 位数字`（含日期），**以用户决策为准**。
- **选型理由**：
  - 编码自带日期，运维审计可读性好（一眼看出注册时间）。
  - 与表5 `login_log_code`（LL + yyyyMMdd + 4 位流水号）、表11 `feedback_code`（FB + yyyyMMdd + 4 位流水号）风格一致，全平台"前缀 + 日期 + 流水号"编码风格统一。
  - 单日 4 位数字上限 9999（不使用全 0 值，实际有效范围 0001-9999），用户注册量远低于此量级。
- **实施注意**：
  - Redis 序列号 `seq:user_code:{yyyyMMdd}` + 当日过期；与表5/表11 序列号生成器共用基础设施。
  - Redis 故障降级方案：DB 计数表 + 行锁（`SELECT ... FOR UPDATE`）。
  - 不使用全 0 值（`U202608250000` 非法），首条为 `U202608250001`。

**2. 时间字段备注（北京时间/格式）**

为 `create_time`、`last_modified_time`、`last_login_time` 三个时间字段统一追加备注"北京时间 UTC+8，格式 yyyy-MM-dd HH:mm:ss"。

**3. 字段表源前缀（status → user_status）**

- 原 `status` → `user_status`（避免与 SQL 保留字及联表查询时与订单状态、消息状态等混淆）。
- 依据 §8.4 字段表源前缀规则（易混淆字段加前缀）。

**4. is_deleted 保留**

- 业务实体表，逻辑删除走 `UPDATE ... SET is_deleted = 1`，查询默认带 `is_deleted = 0` 过滤。
- 不对 `is_deleted` 单独建索引（§8.3.7）。

**5. 后续待办与确认点（落地实施前需用户决策）**

1. **Redis 序列号生成器复用决策**（跨表联动）：表1 `user_code`、表5 `login_log_code`、表11 `feedback_code` 均采用"前缀 + 日期 + 4 位流水号"格式，需在落地实施时明确是否引入 Redis 序列号生成器基础设施，三表共用同一序列号生成器。
2. **Redis 故障降级方案**：Redis 不可用时，用户注册流程是降级为 DB 计数表 + 行锁，还是拒绝注册？这关系到用户注册可用性，需用户决策。
3. **存量数据迁移**：现有 `user_id BIGINT AUTO_INCREMENT` 历史数据如何映射为新的 `user_code`？建议按 `user_id` 升序、按注册日期分组生成 `U{yyyyMMdd}{0001/0002/...}` 编码，需配套数据迁移脚本与回填方案。
4. **API 兼容方案**：现有 API 是否需要双写过渡期（同时返回 `user_id` 和 `user_code`）？需评估前后端兼容成本。
5. **is_deleted 单列索引移除**：既有表若有 `idx_is_deleted` 单列索引，需在迁移期移除（§8.3.7）。

#### 最终建表语句

```sql
CREATE TABLE IF NOT EXISTS `user_account` (
  `user_code` VARCHAR(16) NOT NULL COMMENT '用户编码（业务主键，格式：U + yyyyMMdd + 4 位数字，不使用全0值，如 U202608250001，当日下第几个用户）',
  `openid` VARCHAR(64) NOT NULL COMMENT '微信 openid',
  `unionid` VARCHAR(64) DEFAULT NULL COMMENT '微信 unionid',
  `session_key` VARCHAR(128) NOT NULL COMMENT '微信 session_key',
  `user_status` TINYINT NOT NULL DEFAULT 1 COMMENT '账号状态：1-正常，0-封禁',
  `last_login_time` DATETIME DEFAULT NULL COMMENT '最后登录时间（北京时间 UTC+8，格式 yyyy-MM-dd HH:mm:ss）',
  `is_deleted` TINYINT NOT NULL DEFAULT 0 COMMENT '逻辑删除：0-未删除，1-已删除（查询默认带 is_deleted=0 过滤）',
  `create_time` DATETIME NOT NULL COMMENT '创建时间（北京时间 UTC+8，格式 yyyy-MM-dd HH:mm:ss，后端推送）',
  `last_modified_time` DATETIME NOT NULL COMMENT '最后修改时间（北京时间 UTC+8，格式 yyyy-MM-dd HH:mm:ss，后端推送）',
  PRIMARY KEY (`user_code`),
```

#### 决策说明

**1. 业务主键策略（user_code 直接作主键，1:1 关系）**

- `user_profile` 与 `user_account` 是 1:1 关系，直接用 `user_code` 作主键，无需独立业务编码。
- 与表1 `user_account.user_code` 共用同一编码（U + yyyyMMdd + 4 位数字），由 user_account 创建时生成，user_profile 同步写入。
- 与表10 `user_preferences` 主键策略一致（1:1 关系，user_code 直接作主键）。

**2. 时间字段备注（北京时间/格式）**

为 `invited_at`、`create_time`、`last_modified_time` 三个时间字段统一追加备注"北京时间 UTC+8，格式 yyyy-MM-dd HH:mm:ss"。

**3. 字段表源前缀（gender → user_gender）**

- 原 `gender` → `user_gender`（联表查询时与 `pet_gender` 区分）。
- 依据 §8.4 字段表源前缀规则（易混淆字段加前缀）。

**4. 唯一索引 uk_user_id 移除**

- 原唯一索引 `uk_user_id (user_id)` 移除——`user_code` 已是主键（即唯一），无需额外唯一索引。
- 保留 `uk_invite_code`、`uk_email` 两个唯一索引（业务唯一性约束）。

**5. 外键引用与 CONSTRAINT 移除**

- `user_code`：引用 `user_account.user_code`，后端校验引用完整性。
- `inviter_user_code`：引用 `user_account.user_code`（邀请人），后端校验。
- 移除 2 处 `CONSTRAINT` 外键约束（`fk_profile_user`、`fk_profile_inviter`）。

**6. is_deleted 保留**

- 业务实体表，逻辑删除走 `UPDATE ... SET is_deleted = 1`，查询默认带 `is_deleted = 0` 过滤。
- 不对 `is_deleted` 单独建索引（§8.3.7）。

**7. 后续待办与确认点（落地实施前需用户决策）**

1. **存量数据迁移**：现有 `profile_id BIGINT AUTO_INCREMENT` + `user_id` 历史数据如何映射为新的 `user_code`？需与表1 `user_account` 迁移同步进行，配套数据迁移脚本与回填方案。
2. **API 兼容方案**：现有 API 是否需要双写过渡期（同时返回 `user_id` 和 `user_code`）？需评估前后端兼容成本。
3. **invite_code 生成规则**：当前 COMMENT 已注明"由后端生成的随机字符串，仅含数字和大小写字母"，长度 VARCHAR(16)，需在落地实施时明确生成算法（如 `crypto.randomBytes` 转 base36 截取）与冲突重试机制。
4. **is_deleted 单列索引移除**：既有表若有 `idx_is_deleted` 单列索引，需在迁移期移除（§8.3.7）。

#### 决策说明

（填写决策理由、login_log_code 编码方案等补充说明）

**1. 业务主键 `login_log_code` 编码方案（方案 C）**

- 格式：`LL` + `yyyyMMdd` + 4 位流水号
- 示例：`LL202608250001`（共 14 位）
- 选型理由：与 `order_code`（`yyyyMMdd` + 4 位流水号）风格保持一致，统一全表业务主键编码风格，简洁可读，运维一眼可识别登录日期与当日序号。
- 字段长度：保留 VARCHAR(32)，实际编码 14 位，预留约 18 位余量；未来若需扩展为 6/8 位流水号或追加用户标识后缀，无需变更字段类型。
- 实施注意（并发安全）：
  - 单日 4 位流水号上限 9999，超出时回退为追加日期后次日序号或扩展至 6 位（需评估）。
  - 并发场景下 4 位流水号生成需配套**序列号生成器**（候选：Redis INCR 序列号键 `seq:login_log:{yyyyMMdd}` + 当日过期；或 DB 独立计数表 + 行锁）。
  - 主键唯一索引冲突时业务层重试 1-2 次；若 Redis 序列号不可用需有降级方案（如改用方案 A 时间戳+随机作为兜底）。
  - 服务重启/Redis 故障转移期间需保证序列号连续性，避免重复。

**2. 时间字段备注（北京时间/格式）**

为 `login_time`、`logout_time`、`create_time`、`last_modified_time` 统一追加备注"北京时间 UTC+8，格式 yyyy-MM-dd HH:mm:ss"，明确时间字段的时区与展示格式，避免后续读端（前端、报表、审计）歧义。

**3. `ip_address` 字段长度保留 VARCHAR(64)**

- 覆盖范围：IPv4 单地址（15 字符）、IPv6 单地址（最多 39 字符）、IPv6+端口/zone（约 45-47 字符）、多级代理 XFF 首段（含 2-3 个 IPv4，约 33 字符）。
- 64 字符比 IPv6 实际最大长度 39 多出 25 字符余量，应对未来扩展（zone id、端口等）。
- 不存原始多级 XFF 全量字符串（避免超长）；按 `emailBindService.getClientIp` 实现取首个客户端 IP。

#### 决策说明

（填写决策理由、address_code 编码方案等补充说明）

**1. 业务主键 `address_code` 编码方案（方案 A）**

- 格式：`ADDR` + `user_code`（U+8 位，如 `U00000001`） + 3 位用户内序号
- 示例：`ADDRU00000001001`（共 15 位）
- 选型理由：
  - 编码自带"用户标识 + 用户内序号"，运维审计一眼看出归属，与订单收货地址快照对账时定位用户一目了然。
  - 该表为业务实体表（CRUD 全生命周期）、低频写入、单用户少量记录（业务上限 20 条），适合 DB 行锁方案，无需 Redis 序列号生成器。
  - 3 位序号（001-999）远超业务上限 20 条，余量充足。
- 字段长度：保留 VARCHAR(32)，实际编码 15 位，预留 17 位余量；未来若需扩展（如追加门店维度前缀），无需变更字段类型。
- 实施注意（序号生成与回收策略）：
  - **序号不回收，永久递增**：即使逻辑删除（`is_deleted=1`）某地址，序号也不复用，避免删除后重建导致主键冲突或快照对账歧义。
  - **用户内序号生成**：后端创建地址时执行 `SELECT COALESCE(MAX(user_seq), 0) + 1 FROM user_address WHERE user_code = ? AND is_deleted = 0 FOR UPDATE`（事务内行锁），解析出序号后拼装 `address_code`。
  - **跨用户并发无需协调**：各用户独立序号空间，跨用户并发创建无锁竞争。
  - **单用户并发**：理论上同一用户不会并发创建地址，DB 行锁兜底即可。
  - **不补加 `user_address_seq` 字段**：用户查询收货地址非高频业务，序号嵌入 `address_code` 内即可，无需单独建字段与联合唯一索引 `uk_user_seq`。
  - **单用户地址数硬上限 20 条**：后端业务层校验单用户地址数 ≤20，超出时返回业务错误码（避免序号膨胀、控制存储成本）。

**2. 时间字段备注（北京时间/格式）**

为 `create_time`、`last_modified_time` 统一追加备注"北京时间 UTC+8，格式 yyyy-MM-dd HH:mm:ss"，明确时间字段的时区与展示格式，避免后续读端（前端、报表、审计）歧义。

**3. `is_deleted` 保留**

业务实体表（CRUD 全生命周期），保留 `is_deleted` 字段；逻辑删除走 `UPDATE ... SET is_deleted = 1`，无 `DELETE FROM`；查询默认带 `is_deleted = 0` 过滤。

**1. 业务主键 `browse_log_code` 编码方案（方案 A）**

- 格式：`BL` + `yyyyMMddHHmmssSSS`（17 位毫秒时间戳） + 4 位 base36 随机（大小写字母 + 数字）
- 示例：`BL20260825143012a3F9`（共 22 位）

  - **写入路径优化**：浏览埋点接口高频写入，建议异步落库（消息队列或批量插入），减少 DB 压力；编码生成在异步 worker 中完成。

本表为用户行为记录表（记录用户对商品的浏览及加购/下单行为），与 `user_refresh_token` 会话类表性质不同，需支持逻辑删除。原"流水表豁免"主张已取消，补充 `is_deleted TINYINT NOT NULL DEFAULT 0` 字段：

### 第三部分：用户评审决策

#### 决策对照表

| 变更项 | 旧值 | 建议值 | 决策 | 最终值 |

| COMMENT 补充 | 多数字段缺失 | 全部补充 | 同意 | 全部补充 |

#### 决策说明

（填写决策理由、refresh_token_code 编码方案等补充说明）

**1. 业务主键 `refresh_token_code` 编码方案（方案 A）**

- 格式：`RT` + `yyyyMMddHHmmssSSS`（17 位毫秒时间戳） + 4 位 base36 随机（大小写字母 + 数字）
- 示例：`RT20260825143012a3F9`（共 22 位）
- 选型理由：
  - 已有 `token_hash` 作为业务唯一标识（`uk_token_hash` 唯一索引），业务查询走 `token_hash`，`refresh_token_code` 主要作行标识，业务可读性价值低，无需 Redis 序列号或用户码前缀。
  - 登录/刷新 token 是高频写入 + 极高频读取（每次 API 调用验证 token），方案 A 无协调器、绝对并发安全，写入路径最短。
  - 不依赖 Redis 序列号生成器，**登录可用性不受 Redis 故障影响**——会话类表对 Redis 故障容忍度低（Redis 故障期间登录不能挂），方案 A 更稳妥。
  - 与表7 `BL` 风格一致，都是高频写入 + 流水/会话类表。
  - `RT` 前缀 + 17 位毫秒时间戳，运维可读性好，可一眼看出 token 签发时间。
- 字段长度：保留 VARCHAR(32)，实际编码 22 位，预留 10 位余量；未来若需扩展（追加用户标识后缀），无需变更字段类型。
- 实施注意（生成与冲突处理）：
  - **随机生成函数**：推荐 `crypto.randomBytes(3).toString('base64').slice(0, 4)` 或等价 base36 生成（4 位约 167 万组合）。
  - **冲突兜底**：主键唯一索引冲突时业务层重试 1-2 次；单毫秒内冲突概率极低，重试基本不会失败。
  - **与表5 `LL`（方案 C 流水号 + Redis 序列号）风格的差异合理**：表5（登录流水）单日量级中等，4 位流水号足够；表8（会话类表）对 Redis 故障容忍度更低，方案 A 无 Redis 依赖更稳妥。

**2. 时间字段备注（北京时间/格式）**

为 `expire_time`、`revoke_time`、`create_time`、`last_modified_time` 统一追加备注"北京时间 UTC+8，格式 yyyy-MM-dd HH:mm:ss"，明确时间字段的时区与展示格式，避免后续读端（鉴权中间件、审计、报表）歧义。

**3. 业务时间字段命名统一**

- `expires_at` → `expire_time`
- `revoked_at` → `revoke_time`
- 统一 `_time` 后缀，与 `create_time` / `last_modified_time` 风格一致；命名变更需在 API 规范与后端代码同步。

**4. `is_deleted` 豁免**

Token 表，通过 `revoke_time` 撤销，删除走物理清理（合规豁免）；表级 `COMMENT` 注明豁免理由。

**5. 外键引用与 CONSTRAINT 移除**

- `user_code` 引用 `user_account.user_code`（VARCHAR(16)）。
- 1 处 `CONSTRAINT` 外键移除（`fk_refresh_token_user`），引用完整性由后端在创建 token 时校验 `user_code` 存在性。

**6. 索引保留**

- `uk_token_hash` 唯一索引：业务核心，token 验证主路径，保留。
- `idx_user_code` 普通索引：按用户查询所有 token（多设备管理、撤销某用户所有 token），保留。

**7. 后续待办与确认点（落地实施前需用户决策）**

1. **物理清理策略**：本表豁免 `is_deleted`，通过 `revoke_time` 撤销，删除走物理清理。落地时需配套定时任务清理已过期/已撤销 token（避免表无限膨胀）。
   - 建议清理规则：`WHERE revoke_time IS NOT NULL OR expire_time < NOW() - INTERVAL 30 DAY`
   - 建议清理频率：每日凌晨低峰期执行
   - **待用户决策：保留期长度**（建议 30 天，便于审计追溯）

2. **多设备登录管理**：单用户可能同时存在多个有效 token（多设备登录），建议后端创建 token 时检查该用户有效 token 数量，超限时撤销最旧的。
   - **待用户决策：单用户最大并发有效 token 数**（建议 5 个，覆盖手机/平板/PC/网页多端）

3. **`token_hash` 字段长度**：VARCHAR(128) 当前够用（SHA-256 哈希后 64 字符，预留约 64 字符余量），落地时无需调整；后续若改用 SHA-512 或加盐哈希也无需迁移。

4. **存量数据迁移**：现有 `id BIGINT AUTO_INCREMENT` 历史数据如何映射为新的 `refresh_token_code`？
   - 建议方案：按 `id` 升序批量生成 `RT + 原 created_at 时间戳 + 4 位序号` 形式，但需保留 `token_hash` 与原 `id` 的映射关系以兼容历史会话。
   - **待用户决策：是否在迁移期保留双写（同时写入旧 id 与新 refresh_token_code）以平滑过渡**

5. **编码生成与写入路径**：登录/刷新 token 是高频操作，编码生成应在 token 签发流程内**同步完成**（不能异步），因为 refresh_token 需立即返回给客户端。与表7 浏览流水（可异步落库）不同。

6. **Redis 序列号生成器复用决策**：表5 `login_log_code` 已选方案 C（依赖 Redis 序列号生成器）；表8 选方案 A（不依赖 Redis）。两个方案在用户域并存，**需在落地实施时明确：是否引入 Redis 序列号生成器基础设施？**
   - 若引入：表5 用方案 C 落地，表8 仍走方案 A（不依赖）
   - 若不引入：表5 需改回方案 A 或方案 B（DB 计数表）

#### 最终建表语句

```sql

  `refresh_token_code` VARCHAR(32) NOT NULL COMMENT '刷新令牌编码（业务主键）：格式 RT + yyyyMMddHHmmssSSS（17位毫秒时间戳） + 4位 base36 随机，如 RT20260825143012a3F9（共 22 位，冲突重试 1-2 次）',
```

#### 决策说明

**1. 表拆分方案（方案 A 简化版：2 张表）**

原 `user_message` 表拆分为 2 张表：

| 表 | 定位 | 含 user_code | 已读/删除交互 |
|----|------|-------------|--------------|
| user_broadcast | 广播消息主表（面向全体用户） | ❌ 不含 | ❌ 不提供 |
| user_message | 用户消息表（非广播类） | ✅ 含 | ✅ 保留 |

**拆分理由**：
- 广播消息原为每个目标用户创建一条记录（10000 用户 = 10000 条记录），存储浪费严重。
- 拆分后广播主表仅 1 条记录/广播，写入性能大幅提升。
- 广播消息不提供已读/未读状态与删除入口，无需 user_code 字段。

**业务规则补充**：
- 广播消息对用户不提供已读/未读状态（不参与未读数量统计）。
- 广播消息不提供删除入口（用户无法删除广播消息）。
- 广播消息仅展示，点击可跳转（若有 action_path 则跳转，当前暂不需要）。

**2. 表 9A user_broadcast 业务主键编码（BC + 秒级时间戳 + 4 位随机）**

- 格式：`BC` + `yyyyMMddHHmmss`（14 位秒级时间戳） + 4 位 base36 随机
- 示例：`BC202608251430a3F9`（共 20 位）
- 选型理由：
  - 广播消息低频写入（管理端手动触发），方案 A（时间戳+随机）足够。
  - 与表7 BL、表8 RT 风格一致（都是时间戳+随机）。
  - 无需 Redis 序列号生成器，广播发送可用性不受 Redis 故障影响。
- 冲突兜底：主键唯一索引冲突时重试 1-2 次。

**3. 表 9A user_broadcast 字段精简**

| 移除字段 | 理由 |
|----------|------|
| biz_type | 广播消息只关联 broadcast_job 一种实体，biz_type 固定值冗余 |
| biz_code（更名） | 更名为 broadcast_job_code，语义更明确 |
| tags | 广播消息分类通过 priority+icon 实现，tags 价值不大 |
| user_code | 全体广播，不针对特定用户 |
| message_status | 不提供已读/删除交互 |
| action_path | 暂不需要 |
| cycle | 非提醒消息 |
| message_category | 固定为系统广播，无需分类字段 |
| message_type | 固定为 system_broadcast，无需字段 |

**4. 表 9B user_message 业务主键编码（方案 B + 4 位随机）**

- 格式：`MSG` + `user_code`（U+8位，共9位） + `MMddHHmmss`（10位秒级时间戳） + 4 位 base36 随机
- 示例：`MSGU0000000108251430a3F9`（共 26 位）
- 选型理由：
  - 编码自带用户标识，便于运维审计定位。
  - 消息表中频写入，4 位 base36 随机兜底充分。
  - 不依赖 Redis 序列号生成器。
- 字段长度：VARCHAR(32)，实际 26 位，预留 6 位余量。

**5. 表 9B user_message biz_type 取值调整**

移除 `broadcast_job` 取值（广播消息走 user_broadcast 表），保留 5 个取值 + null：

| biz_type | 关联业务表 | biz_code | 使用场景 |
|----------|-----------|----------|----------|
| order | order_main | order_code | 订单状态变更通知 |
| after_sales | after_sales_main | after_sales_code | 售后申请创建、退款完成 |
| feedback | user_feedback | feedback_code | 用户反馈处理完成 |
| service_conversation | service_conversation | conversation_code | 客服回复 |
| reminder | user_reminder | reminder_code | 用户提醒（替代原 extra_json.reminder_id） |
| null | - | null | 无关联业务实体 |

**6. 表 9B user_message extra_json 处理（方案 A 优化版）**

- 移除 `extra_json TEXT`，扁平化为 3 个字段：icon VARCHAR(32)、tags VARCHAR(255)、cycle VARCHAR(16)。
- `reminder_id` 由 `biz_type='reminder'` + `biz_code=reminder_code` 承载。
- `source_job_id` 不再需要（广播消息走 user_broadcast 表，通过 broadcast_job_code 关联）。

**7. 订单消息分表决策（短期不分表）**

- 短期不分表，采用替代优化方案：定期归档 + 索引优化 + 消息合并展示。
- 分表演进路径：阶段1（当前单表）→ 阶段2（数据量达千万级按 message_category 分表）→ 阶段3（数据量达亿级按 user_code 哈希分表）。

**8. 时间字段备注**

- 表 9A：expire_time、create_time、last_modified_time 标注北京时间 UTC+8。
- 表 9B：read_time、expire_time、create_time、last_modified_time 标注北京时间 UTC+8。

**9. is_deleted 处理**

- 表 9A：保留 is_deleted（系统级逻辑删除，管理员操作，非用户删除）。
- 表 9B：取消豁免，补充 is_deleted 与 message_status 并存（参考 §8.3.3）。

**10. 后续待办与确认点（落地实施前需用户决策）**

1. **adminBroadcastService 改造**：从批量创建 user_message 记录改为创建 1 条 user_broadcast 记录。
2. **messageService.createMessage 改造**：判断 message_type，若='system_broadcast' → createBroadcast；否则 → createUserMessage。
3. **管理端反查接口改造**：从 `JSON_EXTRACT(extra_json, '$.source_job_id')` 改为 `WHERE broadcast_job_code=?`（走 idx_broadcast_job_code 索引）。
4. **小程序消息中心改造**："系统"Tab 查询改为 UNION user_broadcast + user_message。
5. **message_type 枚举清单**：建议在 API 规范中补充完整清单（按 message_category 分组）。

#### 决策说明

**1. 主键策略（user_code 直接作主键）**

- `user_preferences` 与 `user_account` 为 1:1 关系，直接用 `user_code` 作主键，无需 `preference_id` 独立逻辑主键。
- 依据 §8.2 主键规则（强制业务主键，禁止 BIGINT AUTO_INCREMENT 逻辑主键）。
- 原 `uk_user_id` 唯一索引移除（主键即唯一，无需额外唯一索引）。

**2. 时间字段备注（北京时间/格式）**

为 `create_time`、`last_modified_time` 统一追加备注"北京时间 UTC+8，格式 yyyy-MM-dd HH:mm:ss"。

**3. `pet_daily_reminder_enabled` 与 `pet_reminder_time` 移除**

- 经代码核查，日常提醒业务已由用户自定义提醒（`extra_json.reminders` 数组）承接：
  - `pet_daily_reminder_enabled` / `pet_reminder_time` 在业务语义上已被 `extra_json.reminders` 取代。
  - 定时任务（`cron:user-reminders`）已切换到扫描 `extra_json.reminders`，不再读 `pet_reminder_time`。
  - API 侧为兼容旧客户端仍"过渡期双写"（从 reminders 反推并双写 legacy 字段）。
- 拆分 `user_reminder` 子表后，两字段迁移到子表（子表的 `enabled` / `time` 字段承载），主表移除冗余字段。
- 过渡期双写改为 API 层适配（后端从 `user_reminder` 子表查询 daily 提醒，反推为旧字段返回给旧客户端），数据库不再存储冗余字段。

**4. `extra_json` 处理（方案 B：拆分 user_reminder 子表）**

- 经代码核查，`extra_json` 不是"简单扩展字段"，而是**用户自定义提醒业务的核心存储字段**，存储结构：
  ```json
  {
    "schema_version": 2,
    "reminders": [
      { "id": "rm_abc123", "enabled": true, "status": "active", "cycle": "daily",
        "time": "20:00", "once_date": null, "weekday": null, "month_day": null,
        "content": "该记录毛孩子的今日状态啦", "tags": [],
        "last_fired_at": null, "created_at": "...", "updated_at": "..." }
    ]
  }
  ```
- 采用方案 B（拆分 `user_reminder` 子表），理由：
  - 提醒数据是结构化实体（有 id、enabled、status、cycle、time 等 13 个字段），适合独立表。
  - 子表可支持索引（如按 `cycle` + `time` 查询待触发的提醒），提升 cron 扫描性能。
  - 符合 §8.8 避免 TEXT/JSON 规范。
  - 与表9 `user_message` 的 `extra_json` 处理逻辑一致（结构化业务数据应拆子表或扁平化）。
- `user_reminder` 子表需另行评审（待办项 1）。

**5. 外键引用与 CONSTRAINT 移除**

- `user_code` 引用 `user_account.user_code`（VARCHAR(16)）。
- 1 处 `CONSTRAINT` 外键移除（`fk_user_preferences_user`），引用完整性由后端校验。

**6. 索引调整**

- 移除 `idx_reminder_schedule (pet_daily_reminder_enabled, pet_reminder_time)`：两字段已迁移到 `user_reminder` 子表，主表无需此索引。
- 移除 `uk_user_id`：`user_code` 已是主键，无需额外唯一索引。

1. **`user_reminder` 子表评审**（核心待办）：需新增 `user_reminder` 表的评审，字段基于 `extra_json.reminders` 数组项结构（id、enabled、status、cycle、time、once_date、weekday、month_day、content、tags、last_fired_at、created_at、updated_at），配套主键设计（业务主键格式）、索引设计（如 `idx_user_cycle_time` 用于 cron 扫描）、is_deleted 处理。**该子表是否纳入本次评审范围，还是作为后续评审项？**

   - **待用户决策**：是否保留 `user_preferences` 表作为"偏好占位表"（未来扩展其他偏好字段如通知开关、语言、主题等）？还是直接废除该表，待有具体偏好字段时再新建？

#### 决策对照表

#### 决策说明

**1. 业务主键编码方案 A（RM + user_code + MMddHHmm + 4 位 base36 随机）**

- 格式：`RM` + `user_code`（U+8 位，共 9 位） + `MMddHHmm`（8 位秒级时间戳） + 4 位 base36 随机（大小写字母+数字）
- 示例：`RMU0000000108251430a3F9`（共 24 位）
- 长度：24 位，VARCHAR(32) 充足余量
- **选型理由**：
  - 用户级提醒是低频写入（单用户最多 5 条提醒，配置后偶尔修改），无需 Redis 序列号生成器
  - 方案 A 无协调器依赖，写入路径最短，并发安全
  - 单用户提醒上限 5 条，分钟级时间戳 + 4 位 base36 随机（约 167 万组合），冲突概率极低
  - 编码自带用户标识，便于审计定位
- **生成函数**：`crypto.randomBytes` 转 base36，截取 4 位
- **冲突兜底**：主键唯一索引冲突时重试 1-2 次
- **与表9 `user_message` 对接**：定时任务触发提醒后写入 `user_message` 表，`biz_type='reminder'`，`biz_code=reminder_code`（与表9已决策的 biz_type 扩展方案对接）

**2. 时间字段备注（北京时间/格式）**

为 `create_time`、`last_modified_time`、`last_fired_time` 三个时间字段统一追加备注"北京时间 UTC+8，格式 yyyy-MM-dd HH:mm:ss"。

**3. is_deleted 保留（业务实体表）**

- 本表为业务实体表（CRUD 全生命周期），保留 `is_deleted` 字段。
- 删除操作走 `UPDATE ... SET is_deleted = 1`，无物理删除。
- 查询默认带 `is_deleted = 0` 过滤。
- 不对 `is_deleted` 单独建索引（TINYINT 选择性低，依据 §8.6）。

**4. 外键引用与 CONSTRAINT**

- `user_code` 引用 `user_account.user_code`（VARCHAR(16)）。
- 独立子表，无 DB 外键约束（依据 §8.5 禁止 CONSTRAINT 约束规则）。
- 引用完整性由后端校验（创建/更新提醒时校验 user_code 存在性）。

**5. 后续待办与确认点（落地实施前需用户决策）**

1. **单用户提醒上限**：当前业务规则为 5 条，需在 `user_reminder` 表的后端创建接口中校验（`SELECT COUNT(*) FROM user_reminder WHERE user_code=? AND is_deleted=0`），超限返回业务错误码。

   - `id` 字段（如 `rm_abc123`）需映射为新的 `reminder_code`（按方案 A 生成）。
   - `created_at` / `updated_at` ISO8601 需转换为 `yyyy-MM-dd HH:mm:ss` 格式写入 `create_time` / `last_modified_time`。
   - `last_fired_at` ISO8601 需转换为 `yyyy-MM-dd HH:mm:ss` 格式写入 `last_fired_time`。

3. **过渡期双写改造**：[userPreferenceService.js#L33-L44](file:///c:/Users/22188/Desktop/宠物生鲜电商开发项目/pet-app-backend/services/userPreferenceService.js#L33-L44) 的 `persistRemindersExtra` 与 [reminderHelpers.js#L258-L281](file:///c:/Users/22188/Desktop/宠物生鲜电商开发项目/pet-app-backend/utils/reminderHelpers.js#L258-L281) 的 `syncLegacyFieldsFromReminders` 需改造为读写 `user_reminder` 子表。

### 第三部分：用户评审决策

#### 决策对照表

| 变更项 | 旧值 | 建议值 | 决策 | 最终值 |
|--------|------|--------|------|--------|
| 主键 | feedback_id BIGINT AUTO_INCREMENT | feedback_code VARCHAR(32) | 同意 | feedback_code VARCHAR(32) |

| 时间字段维护方式 | DB 自动维护 | 后端推送 | 同意 | 后端主动推送 create_time / last_modified_time |
| 时间字段备注 | - | 追加北京时间/格式说明 | 同意 | 北京时间 UTC+8，格式 yyyy-MM-dd HH:mm:ss |
| 字段表源前缀 | type / status | feedback_type / feedback_status | 同意 | feedback_type / feedback_status（§8.4 易混淆字段加前缀） |

| COMMENT 补充 | 部分缺失 | 全部补充 | 同意 | 全部补充 |

#### 决策说明

**1. 业务主键编码方案 A（复用原 feedback_no 格式：FB + yyyyMMdd + 4 位流水号）**

- 格式：`FB` + `yyyyMMdd` + 4 位流水号
- 示例：`FB202608250001`（共 14 位）
- 长度：14 位，VARCHAR(32) 充足余量
- **选型理由**：
  - **零迁移成本**：现有 `feedback_no` 数据可直接作为 `feedback_code`，无需重新生成编码，这是方案 B/C 无法比拟的优势。
  - 与 `order_code`（`yyyyMMdd` + 4 位流水号）风格一致，全平台编码风格统一。
  - 单日 9999 上限足够：用户反馈是低频操作，远低于登录/浏览量级。
  - 被表9 `user_message` 引用兼容：`biz_type='feedback'` + `biz_code=feedback_code`，复用原格式不影响对接。
- **实施注意**：
  - Redis 序列号 `seq:feedback:{yyyyMMdd}` + 当日过期；与表5 `login_log_code` 序列号生成器可共用基础设施。
  - 现有 `feedback_no` 数据直接作为 `feedback_code`（重命名字段，值不变）。
  - 移除 `uk_feedback_no` 唯一索引（主键即唯一）。
  - `feedback_code` 字段长度 VARCHAR(32)（实际 14 位，余量 18 位）。

**2. 时间字段备注（北京时间/格式）**

为 `create_time`、`last_modified_time`、`processed_time` 三个时间字段统一追加备注"北京时间 UTC+8，格式 yyyy-MM-dd HH:mm:ss"。

**3. 字段表源前缀（feedback_type / feedback_status）**

- 原 `type` → `feedback_type`（避免与 SQL 保留字及联表查询混淆）。
- 原 `status` → `feedback_status`（避免与表9 `message_status`、订单状态等混淆）。
- 依据 §8.4 字段表源前缀规则（易混淆字段加前缀）。

**4. 外键引用与 CONSTRAINT 移除**

- 3 处外键引用改造：
  - `user_id` → `user_code`（VARCHAR(16)，引用 `user_account.user_code`）。
  - `order_id` → `order_code`（VARCHAR(20)，引用 `order_main.order_code`）。
  - `processed_by` → `processed_by_code`（VARCHAR(16)，引用 `admin_user.admin_code`）。
- 3 处 `CONSTRAINT` 外键移除（`fk_feedback_user` / `fk_feedback_order` / `fk_feedback_admin`），引用完整性由后端校验。
- **跨表依赖待办**：`admin_user.admin_code` 字段长度待管理域表评审确定后同步调整；`order_main.order_code` 已定为 VARCHAR(20)。

**5. 唯一索引 uk_feedback_no 移除**

- 原 `uk_feedback_no` 唯一索引移除：`feedback_code` 已是主键（即唯一），无需额外唯一索引。

**6. image_urls 处理（保留 JSON 主张豁免）**

- 用户决策：保留 `image_urls JSON` 字段，沿用旧表方案，主张豁免 §8.8 避免 TEXT/JSON 规范。
- **豁免理由**：
  - 截图 URL 数组结构简单（最多 6 张），扁平化或拆子表成本高于收益。
  - 数组项仅含 URL 字符串，无复杂嵌套结构，JSON 解析成本低。
  - 与 §8.8 豁免候选中的"审计/流水表动态详情字段"类似——结构由业务决定，扁平化成本高。
- **实施注意**：
  - 后端创建/更新反馈时，`image_urls` 字段需校验数组长度 ≤ 6。
  - 查询时直接读取 JSON 字段，前端按数组渲染。

**7. 后续待办与确认点（落地实施前需用户决策）**

1. **admin_code 字段长度**：`processed_by_code` 引用 `admin_user.admin_code`，字段长度 VARCHAR(16) 暂定，待管理域表评审确定后同步调整。
2. **Redis 序列号生成器复用决策**（与表5 决策点联动）：表5 `login_log_code` 与表11 `feedback_code` 都选方案 C/A（4 位流水号），需在落地实施时明确是否引入 Redis 序列号生成器基础设施。
3. **存量数据迁移**：现有 `feedback_no` 数据直接作为 `feedback_code`（值不变，仅重命名字段），迁移成本最低；`image_urls` 数据无需迁移（保留 JSON 格式不变）。
