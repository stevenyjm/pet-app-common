## 1. 需求背景

用户希望在编辑每日状态时，能够更便捷地设置宠物的"最近状态"（`latest_*` 字段），减少重复操作。具体需求如下：

| 需求项 | 说明 |
|--------|------|
| 同步至最近状态 | 保存今日日记录状态时，可选择将状态同步到宠物档案的最近状态字段 |
| 来源预填充 | 编辑今日日记录状态时，可从最近状态或昨日状态预填充表单 |
| 页面跳转控制 | 保存后可选择停留在日记录页面或跳转至宠物信息页面 |

## 2. 需求分析

### 2.1 现有数据模型

**宠物档案表 `pet`**（已有字段）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `latest_mood` | VARCHAR(32) | 最近心情 |
| `latest_mood_update_time` | DATETIME | 最近心情更新时间 |
| `latest_weight_kg` | DECIMAL(6,2) | 最近体重（kg） |
| `latest_weight_update_time` | DATETIME | 最近体重更新时间 |
| `latest_stool_health` | VARCHAR(32) | 最近排便健康 |
| `latest_stool_update_time` | DATETIME | 最近排便健康更新时间 |
| `latest_physical_state` | VARCHAR(6) | 最近身体状态描述（限6字） |
| `latest_physical_state_update_time` | DATETIME | 最近身体状态更新时间 |

**日记录表 `daily_record`**（已有字段）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `daily_mood` | VARCHAR(32) | 当日心情 |
| `daily_weight_kg` | DECIMAL(6,2) | 当日体重（kg） |
| `daily_stool_health` | VARCHAR(32) | 当日排便健康 |

### 2.2 状态流转关系

```
最近状态（pet.latest_*）← 同步 ← 今日日记录（daily_record.daily_*）
                                       ↑
                                       │ 预填充来源
                                       │
                    ┌──────────────────┴──────────────────┐
                    ↓                                     ↓
              最近状态（pet.latest_*）              昨日状态（昨日 daily_record）
```

### 2.3 用户场景

| 场景 | 用户操作 | 期望行为 |
|------|----------|----------|
| 每日记录 | 用户在日记录页面编辑今日状态 | 可选择从最近状态/昨日状态预填充 |
| 快速更新档案 | 用户编辑完今日状态后保存 | 可选择同步至最近状态，更新宠物档案 |
| 查看档案 | 用户保存后希望查看宠物档案 | 可选择跳转至宠物信息页面 |
| 继续记录 | 用户保存后希望继续记录其他内容 | 可选择停留在日记录页面 |

## 3. API 接口变更

### 3.1 保存日记录并同步最近状态

**PUT** `/pets/{petId}/daily-records/{recordDate}`

#### 请求体新增字段

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `sync_to_latest` | Boolean | 否 | 是否同步至最近状态，默认 false |

#### 请求示例

```json
{
  "daily_mood": "开心",
  "daily_weight_kg": 18.5,
  "daily_stool_health": "正常",
  "sync_to_latest": true
}
```

#### 响应体

当 `sync_to_latest` 为 true 时，响应体除返回日记录外，还需返回更新后的宠物对象：

| 字段 | 类型 | 说明 |
|------|------|------|
| `pet` | Object | 更新后的宠物对象，包含所有 `latest_*` 字段 |

#### 响应示例

```json
{
  "record_date": "2026-07-11",
  "daily_mood": "开心",
  "daily_weight_kg": 18.5,
  "daily_stool_health": "正常",
  "pet": {
    "pet_id": 1,
    "name": "豆豆",
    "latest_mood": "开心",
    "latest_mood_update_time": "2026-07-11T14:30:00",
    "latest_weight_kg": 18.5,
    "latest_weight_update_time": "2026-07-11T14:30:00",
    "latest_stool_health": "正常",
    "latest_stool_update_time": "2026-07-11T14:30:00"
  }
}
```

### 3.2 获取昨日日记录（新增接口）

**GET** `/pets/{petId}/daily-records/{recordDate}/yesterday`

#### 请求参数

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `petId` | String | 是 | 宠物ID |
| `recordDate` | String | 是 | 当前日期（YYYY-MM-DD），服务端自动计算昨日日期 |

#### 响应体

返回昨日的日记录数据（结构同 GET `/pets/{petId}/daily-records/{recordDate}`）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `daily_mood` | String | 昨日心情 |
| `daily_weight_kg` | Number | 昨日体重 |
| `daily_stool_health` | String | 昨日排便状态 |

#### 响应示例

```json
{
  "record_date": "2026-07-10",
  "daily_mood": "一般",
  "daily_weight_kg": 18.3,
  "daily_stool_health": "正常"
}
```

#### 4.2.2 返回逻辑设计

**设计原则**：同页面内模式切换优先于页面跳转，保持用户上下文连续性。

**返回逻辑矩阵**：

| 当前模式 | 触发操作 | 行为 | 理由 |
|----------|----------|------|------|
| 只读模式 | 点击返回按钮 | 返回上一页（通常是日记录页面） | 符合用户预期的导航行为 |
| 编辑模式 | 点击返回按钮 | 切换回只读模式（有脏数据时提示确认） | 同页面内状态切换，不改变页面栈 |
| 编辑模式 | 点击保存档案按钮 | 保存成功后切换回只读模式 | 保存完成后自然回到查看状态 |

**编辑模式下的返回确认逻辑**：

| 场景 | 行为 |
|------|------|
| 无脏数据（未修改） | 直接切换回只读模式 | 无需确认 |
| 有脏数据（已修改） | 弹出确认对话框「您已修改宠物档案，确定要放弃修改吗？」 | 防止误操作丢失数据 |
| 确认放弃 | 切换回只读模式，恢复原始数据 | 保持数据一致性 |
| 取消放弃 | 留在编辑模式，继续编辑 | 用户可继续操作 |

**脚本逻辑调整**：

| 新增方法 | 说明 |
|----------|------|
| `enterEditMode()` | 进入编辑模式，重置表单为当前详情数据 |
| `exitEditMode()` | 退出编辑模式，切换回只读模式 |

| 修改方法 | 修改内容 |
|----------|----------|
| `goBack()` | 编辑模式下有脏数据时提示确认；无脏数据时切换回只读模式；只读模式下正常返回 |
| `performSave()` | 保存成功后保持现有逻辑（切换回只读模式） |

## 5. 业务规则

### 5.1 预填充规则

| 规则 | 说明 |
|------|------|
| 优先级 | 用户手动输入 > 预填充值 |
| 空值处理 | 预填充来源字段为空时，对应表单字段保持为空 |
| 体重转换 | 预填充体重时保持数字类型，显示时转为字符串 |

### 5.2 同步规则

| 规则 | 说明 |
|------|------|
| 同步时机 | 仅在保存日记录成功后执行同步 |
| 同步范围 | 仅同步有值的字段（空值不覆盖现有最近状态） |
| 更新时间 | 服务端自动设置对应 `*_update_time` 为当前时间 |
| 物理状态 | 同步时不包含 `latest_physical_state`（该字段仅在宠物信息页编辑） |

### 5.3 页面跳转规则

| 规则 | 说明 |
|------|------|
| 跳转条件 | 仅当 `syncToLatest` 为 true 且保存成功时，才可选择跳转至宠物信息页 |
| 跳转目标 | `/subpk-pet/info` 页面，携带 `petId` 参数 |
| 页面栈 | 跳转时使用 `uni.navigateTo`，保留日记录页面在栈中 |

### 8.2 替代能力：自动拉取最近一次记录填充

最近状态降级后，以"自动拉取最近一次记录填充"替代：用户新增餐食/运动记录时（页面与表单刚加载完成时），自动从该宠物最近一次同类型记录（跨日期）拉取内容填充表单，并在上方展示提醒条"已自动为您拉取该宠物最近一次记录"，停留 5 秒后收回。仅新增模式触发，编辑模式不触发。详见主文档 §5.9.2。

### 8.3 降级动因

1. **双份状态语义冗余**：`latest_*` 与 `daily_*`（每日状态）语义重叠，维护两套字段易产生不一致
2. **同步链路复杂**：`syncPetLatestSnapshot` 跨 `latest_record_date` 比较写入、C 端 `sync_to_latest` 开关、管理端同步逻辑三处入口，逻辑分散
3. **真实需求是"快速填充"而非"档案缓存"**：用户编辑今日状态时希望复用最近一次数据，本质是"预填充"需求，可通过"自动拉取最近一次记录填充"更直接满足
