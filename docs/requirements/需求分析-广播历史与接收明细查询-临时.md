# 需求分析：广播历史与接收明细查询

> **文档类型**：临时需求分析文档
> **文档版本**：v1.0
> **日期**：2026-06-25
> **关联项目**：`pet-app-admin-web`（PC 商户管理 Web）+ `pet-app-backend`（REST API）

---

## 1. 需求背景

当前系统已在 Web 管理端实现「消息广播」能力（`FE-U03` · `/message/broadcast`），支持：
- 向**全体用户**发送系统消息；
- 向**指定用户**（通过 user_id 列表）发送系统消息；
- 异步任务执行 + 进度轮询（`admin_message_job`）。

现运营方提出新需求：
1. **查看历史广播消息列表** —— 回顾过往发布的广播记录；
2. **查看广播接收用户明细** —— 了解某条广播具体发送到了哪些用户。

## 2. 现有系统能力分析

### 2.1 数据层（后端已具备）

| 表 / 实体 | 现状 | 与本需求关联 |
|-----------|------|--------------|
| `admin_message_job` | ✅ 已存在，记录每次广播任务 | **核心数据源**：`job_id`、`title`、`content`、`target_type`、`target_value`、`status`、`sent_count`、`total_count`、`created_by`、`create_time`、`finish_time` |
| `user_message` | ✅ 已存在，记录用户收到的消息 | **核心数据源**：`category=1`（系统消息）、`message_type=system_broadcast`，含 `user_id`、`title`、`content`、`create_time`、`extra_json`。**需改造写入逻辑**，将 `job_id` 注入 `extra_json` |
| `admin_user` | ✅ 已存在 | 用于关联 `created_by` → 操作人名称 |
| `user_account` | ✅ 已存在 | 用于在接收明细中展示用户昵称 / 手机号等 |

> 结论：**数据基础基本完备**，仅需在广播写入时将 `job_id` 注入 `user_message.extra_json`，无需新增数据库表或字段。

### 2.2 接口层（后端现状）

| 接口 | 状态 | 说明 |
|------|------|------|
| `POST /admin/messages/broadcast` | ✅ | 创建广播任务 |
| `GET /admin/messages/broadcast/preview` | ✅ | 预览接收人数 |
| `GET /admin/messages/jobs/{id}` | ✅ | 查询单个任务状态/进度 |
| `GET /admin/messages/jobs` | ❌ | **缺失**：广播历史列表 |
| `GET /admin/messages/jobs/{id}/recipients` | ❌ | **缺失**：某广播的接收用户明细 |

### 2.3 Web 前端现状

- `Broadcast.vue`：仅支持「发送广播 + 查看当前任务进度」，无历史列表入口。
- 路由 `/message/broadcast`：单一表单页。

## 3. 需求合理性分析

| 维度 | 评估 | 说明 |
|------|------|------|
| **业务合理性** | ✅ 高 | 运营工具必须具备**审计追溯能力**。当前发送广播后除即时轮询卡片外无留痕入口，无法满足「事后核查」与「合规审计」要求。 |
| **用户场景** | ✅ 明确 | 场景 A：运营人员想确认上周发的促销广播是否成功；场景 B：客服收到用户投诉「未收到通知」，需要核实该用户是否在广播范围内。 |
| **与现有架构一致性** | ✅ 高 | 完全复用现有 `admin_message_job` + `user_message` 数据模型，不引入新概念。 |
| **复杂度** | 🟡 中低 | 本质是**列表查询 + 详情查询**，无复杂业务逻辑，但接收明细在用户数极大时（`target_type=all`）存在性能考量。 |

**综合判断**：需求合理、必要且与现有系统架构兼容，建议纳入开发计划。

## 4. 可行性分析

### 4.1 技术可行性

- **广播历史列表**：对 `admin_message_job` 按 `create_time` 倒序分页查询，技术成熟。
- **接收用户明细**：对 `user_message` 按 `message_type='system_broadcast'` + 扩展字段关联 `job_id` 进行精确分页查询。

> ⚠️ **关键发现**：当前 `user_message` 表在写入广播消息时，未显式记录 `job_id`。
> 后端文档 §5.23 描述为："异步执行批量写入 `user_message`（`category=1` 系统消息，`message_type=system_broadcast`）；幂等键 `broadcast:{job_id}:{user_id}`"。
> 这意味着 `job_id` 仅存在于 Redis 幂等键中，**MySQL `user_message` 行内没有 `job_id` 字段**。

**解决方案对比**：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **A · 扩展 user_message 表结构** | 在 `user_message` 新增 `source_job_id` 列，广播写入时填充 | 查询高效、索引友好、语义清晰 | 需后端 Schema 变更 + 历史数据无法回填 |
| **B · 纯文本匹配（不推荐）** | 通过 `message_type='system_broadcast'` + `title` + `content` + 时间窗口近似匹配 | 无 Schema 变更 | 不精确，重发相同内容会混淆；无法支持全体广播的精确追溯 |
| **C · 复用 extra_json 扩展字段（已确认采用）** | 在 `user_message.extra_json` 中写入 `"source_job_id": job_id` | 轻量级、无 Schema 变更、利用现有字段、可扩展性强 | 需确认数据库支持 JSON 函数；历史数据无法回填 |

**✅ 已确认采用方案 C**：

根据后端文档 §5.17 的设计，`user_message` 表已具备 `extra_json` 字段用于存储扩展载荷，且本项目使用 MySQL 8.0+ 版本，完全支持 `JSON_EXTRACT()` 函数。因此方案 C 是最优选择：

- **写入逻辑改造**：在 `services/adminBroadcastService.js` 广播批量写入 `user_message` 时，将 `job_id` 注入 `extra_json`：
  ```javascript
  extra_json: JSON.stringify({ source_job_id: jobId })
  ```
- **查询逻辑实现**：接收明细查询通过 `JSON_EXTRACT(extra_json, '$.source_job_id') = ?` 精确过滤，性能足够支撑分页查询。
- **向后兼容**：`extra_json` 为 TEXT/JSON 类型，不影响现有数据，历史广播虽无法追溯接收明细，但不影响新广播功能。

### 4.2 性能可行性

| 场景 | 预估数据量 | 评估 |
|------|-----------|------|
| 广播历史列表 | 运营级别，月级/百级 | 常规分页，无性能问题 |
| 接收用户明细（指定用户） | 单次最多数千 | 常规分页，无性能问题 |
| 接收用户明细（全体用户） | 可能数万~数十万 | **需限制**：① 必须分页（`page_size` 上限如 100）；② 禁止无差别导出全量；③ 可仅展示「发送成功数 + 抽样/搜索」而非完整列表 |

> 若商户规模极大，可考虑「全体广播不展示完整接收列表，仅展示统计摘要 + 按用户搜索」。此点需在需求确认阶段与产品沟通。

## 5. 建议的解决方案

### 5.1 功能范围

| 功能 | 优先级 | 说明 |
|------|--------|------|
| **广播历史列表** | P0 | 分页展示过往广播任务，含标题、目标类型、状态、发送数/总数、发送时间、操作人 |
| **历史广播详情抽屉/弹窗** | P0 | 查看单条广播的完整内容（标题、正文、目标描述、状态、时间） |
| **接收用户明细查询** | P0 | 在详情中分页展示该广播接收了哪些用户（用户 ID、昵称、接收时间） |
| **按标题/时间筛选** | P1 | 历史列表支持关键词搜索、时间范围筛选 |
| **按用户搜索接收记录** | P1 | 在接收明细中按用户 ID / 昵称搜索 |
| **重新发送/复制广播** | P2 | 基于历史广播快速创建新广播（预填标题和内容） |

### 5.2 页面交互建议

- **列表页**：复用项目现有 `ElTable` + `ElPagination` 标准列表范式（参考 `/users`、`/orders` 等页面）。
- **详情/明细**：采用 `ElDrawer` 侧栏（参考 `PetCertAuditDrawer`、`FeedbackResolveDrawer`），左侧展示广播摘要，右侧 Tab 切换「内容预览」与「接收用户列表」。
- **全体广播的接收明细**：若数据量极大，建议默认隐藏明细列表，仅展示统计数字；提供「查看明细」按钮展开分页表格，并加入用户搜索框。

## 7. 关键风险与建议

| 风险点 | 影响 | 建议措施 |
|--------|------|----------|
| `user_message` 未存储 `job_id`，无法精确关联 | 高 | 后端必须先完成广播写入逻辑改造（BE-BH-01），将 `job_id` 注入 `extra_json`，否则接收明细功能无法实现 |
| `JSON_EXTRACT` 查询性能 | 中 | `extra_json` 字段无法直接建索引，但 `message_type` + `create_time` 可部分补偿；建议测试全量查询性能，必要时在全体广播场景下仅展示摘要或强制搜索 |
| 全体广播接收用户量极大 | 中 | 接口层面强制分页上限；前端列表不默认加载全部，提供搜索后才查；或全体广播明细仅展示「成功数 + 失败数」摘要 |
| 历史数据无 `job_id` 回填 | 低 | 历史广播无法追溯接收明细，属于可接受范围；改造后新增的广播即可支持 |
| 与现有审计日志的边界 | 低 | `admin_audit_log` 已记录 `message_broadcast` 动作，本次需求是在业务层补充明细查询，与审计日志互不冲突 |

---

## 8. 结论

1. **需求合理且必要**：消息广播作为运营工具，缺少历史追溯能力会形成审计盲区。
2. **技术可行**：后端已具备 `admin_message_job` + `user_message` 数据基础，仅需补充关联字段与查询接口。
3. **建议优先级**：作为运营工具的增强，建议列为 **P1（高优先级）**，在现有 M3 广播能力之上快速迭代。
4. **开发顺序**：
   - **第一步**：后端确认 `user_message` 关联方案（`extra_json` vs 新增列）并完成写入改造；
   - **第二步**：后端提供 `GET /admin/messages/jobs` 与 `GET /admin/messages/jobs/{id}/recipients`；
   - **第三步**：前端并行开发列表页、详情抽屉与 API 对接。
