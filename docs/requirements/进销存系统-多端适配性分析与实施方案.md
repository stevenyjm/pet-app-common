## 1. 项目现状分析

### 1.1 现有架构

```
C 端微信小程序 (pet-app)          PC 商户管理 Web (pet-app-admin-web)
         │                                    │
         │  Bearer User JWT                   │  Bearer Admin JWT
         └──────────────┬─────────────────────┘
                        ▼
              pet-app-backend (/api/v1)
                        │
            MySQL (pet_app, 54 表) + Sealos S3 + Redis（可选）
```

### 1.2 现有核心数据模型

| 模型 | 关键字段 | 当前库存管理方式 |
|------|----------|------------------|
| `product_sku` | `stock`、`price`、`spec_json`、`nutrition_json` | 单字段库存值，无批次/效期 |
| `order_main` | `order_status`、`pay_time`、`cold_chain` | 订单状态流转，无批次关联 |
| `order_detail` | `sku_id`、`buy_quantity`、`buy_price` | 记录SKU和数量，无批次信息 |
| `cart` | `sku_id`、`quantity` | 仅记录SKU和数量 |
| `product` | `cold_chain`、`extra_json` | 商品主数据，无批次管理开关 |

### 1.3 当前业务流程

```
用户下单 → 扣减 product_sku.stock → 支付 → 发货 → 完成
```

**核心问题**：当前库存管理仅为简单的数量扣减，缺乏：
- 批次管理与效期管控
- FIFO出库策略
- 库存流水追溯
- 临期预警机制

## 3. 多端实施方案

### 3.1 分期策略

基于项目当前 **单人商户、单仓库** 的 MVP 阶段特性，建议采用 **三期渐进式** 实施方案：

| 阶段 | 范围 | 目标 |
|------|------|------|
| **一期（基础库存）** | 后端核心表 + 基础 API + Admin 基础页面 | 实现库存实时管理、批次记录、基础出库流程 |
| **二期（效期管控）** | 效期预警 + FIFO策略 + 追溯功能 | 实现效期管控、临期预警、双向追溯 |
| **三期（业财联动）** | 采购管理 + 成本核算 + 财务单据 | 实现采购入库、成本核算、业财一体化 |

## 4. 关键适配点

### 4.1 库存管理模式切换

| 模式 | 说明 | 适用阶段 |
|------|------|----------|
| **简单模式** | 沿用 `product_sku.stock`，新增库存实时表作为聚合视图 | 一期过渡 |
| **批次模式** | 基于批次管理库存，`product_sku.stock` 作为汇总值 | 二期及以后 |

**切换策略**：一期采用双写模式（同时更新 `product_sku.stock` 和库存实时表），二期完全切换为批次管理。

### 4.2 订单与出库的关联

**当前实现分析**：

现有支付回调逻辑位于 [paymentService.js](file:///C:/Users/22188/Desktop/宠物生鲜电商开发项目/pet-app-backend/services/paymentService.js#L52-L103) 的 `completePayment` 函数中：

```
支付成功 → 更新订单状态为 ship → 记录支付日志
```

当前库存扣减逻辑位于 [orderService.js](file:///C:/Users/22188/Desktop/宠物生鲜电商开发项目/pet-app-backend/services/orderService.js#L69-L81) 的 `restoreOrderStock` 函数中，仅在订单取消时恢复库存，下单时的库存扣减通过 [productCacheService.js](file:///C:/Users/22188/Desktop/宠物生鲜电商开发项目/pet-app-backend/services/productCacheService.js#L137-L167) 的 `deductSkuStock` 实现。

**改造后流程**：
```
订单支付 → completePayment 回调 → 创建出库单 → FIFO批次分配 → 扣减库存实时表 → 更新订单状态为 ship → 记录支付日志
```

**关键改动点**：
- 在 `completePayment` 函数中，更新订单状态之前，调用新增的出库服务创建出库单
- 出库服务负责查询批次、执行FIFO策略、扣减库存、记录流水
- 订单取消时调用新增的库存恢复服务（替代现有 `restoreOrderStock`）

### 4.3 库存预占机制

> **设计决策**：库存预占时机为「提交订单时」而非「加入购物车时」，避免 abandoned cart 场景下库存被无效占用。
> 
> **库存粒度**：库存操作粒度为「SKU + 仓库 + 库位」，`location_id` 为可选字段，未指定库位时视为仓库级库存。

| 环节 | 操作 | 说明 |
|------|------|------|
| 提交订单 | 预占库存 | `locked_qty += quantity`，`available_qty -= quantity`，需指定 `sku_id`、`warehouse_id`、`location_id` |
| 支付成功 | 扣减库存 | 创建出库单，`locked_qty -= quantity`，记录流水，关联 `batch_id` |
| 订单取消/过期 | 释放预占 | `locked_qty -= quantity`，`available_qty += quantity`，按原预占条件释放 |

**释放机制**：
- 订单超时（`expire_at`）自动释放预占
- 订单取消手动释放预占
- 定时任务扫描过期未支付订单释放预占

**预占优先级**：
1. 优先匹配指定库位的库存
2. 未指定库位时，按可用量从高到低选择库位
3. 跨库位预占时，记录预占明细便于后续出库分配

### 4.4 缓存策略适配

**现有缓存机制**：

[productCacheService.js](file:///C:/Users/22188/Desktop/宠物生鲜电商开发项目/pet-app-backend/services/productCacheService.js) 使用 Redis Hash 缓存 SKU 信息，包含 `stock` 字段，通过 Lua 脚本 `DEDUCT_STOCK_SCRIPT` 实现原子扣减。

**改造策略**：

| 阶段 | 缓存策略 | 说明 |
|------|----------|------|
| 一期 | 双写模式 | 同时更新 Redis 缓存和库存实时表，保持 `product_sku.stock` 与缓存同步；缓存 Key 增加 `warehouse_id` 维度 |
| 二期 | 以库存实时表为准 | 缓存从库存实时表加载，Redis 仅作为热点缓存；缓存 Key 增加 `location_id` 维度 |

**缓存 Key 设计**：

| 阶段 | Key 格式 | 说明 |
|------|----------|------|
| 一期 | `sku:{skuId}:warehouse:{warehouseId}` | 仓库级库存缓存 |
| 二期 | `sku:{skuId}:warehouse:{warehouseId}:location:{locationId}` | 库位级库存缓存 |

**缓存失效策略**：
- 库存变动时调用 `invalidateInventoryCache(skuId, warehouseId, locationId)` 失效对应缓存
- 库存实时表更新后自动刷新 Redis 缓存
- 新增 `syncInventoryCache(skuId, warehouseId, locationId)` 函数同步库存实时表到缓存

### 4.7 并发控制策略

**库存预占与扣减场景**：

| 场景 | 并发控制策略 | 说明 |
|------|--------------|------|
| 库存预占 | 乐观锁 + 版本号 | `inventory_real_time.version` 字段，更新时校验版本号 |
| 库存扣减 | 乐观锁 + 版本号 | 扣减失败时返回冲突错误，前端重试 |
| 批次分配 | `SELECT FOR UPDATE` | 出库时锁定批次记录，防止并发分配同一批次 |

**乐观锁实现示例**：
```sql
UPDATE inventory_real_time 
SET available_qty = available_qty - 1, 
    locked_qty = locked_qty + 1, 
    version = version + 1
WHERE sku_id = ? AND warehouse_id = ? AND version = ? AND available_qty >= 1
```

## 5. 风险与注意事项

| 风险点 | 说明 | 应对措施 |
|--------|------|----------|
| **数据一致性** | 库存实时表与流水表需保持绝对一致 | 采用事务保证原子性操作 |
| **性能影响** | 高频库存操作可能影响系统性能 | 引入 Redis 缓存库存热点数据 |
| **历史数据迁移** | 现有商品数据需补全批次管理字段 | 制定数据迁移计划，分批处理 |
| **下单流程改动** | 修改下单校验逻辑可能影响现有功能 | 先实现库存预占，再切换为批次管理 |
| **Admin 界面改动** | 新增多个管理页面工作量大 | 按分期策略逐步实现 |
| **并发冲突** | 高并发下单可能导致库存超卖 | 乐观锁 + 版本号控制，失败重试机制 |
| **批次数据冗余** | 批次信息在多处存储可能不一致 | `batch_info` 为唯一数据源，其他表通过外键关联 |

3. **技术细节**：补充了数据库索引设计、并发控制策略、事务边界设计、软删除策略
4. **追溯链路**：通过 `order_detail` 表新增 `batch_id`、`outbound_id` 字段，确保反向追溯数据链路完整
5. **设计一致性**：将 `purchase_order.batch_info` JSON字段改为独立的 `purchase_item` 明细表，与 `batch_info` 表通过外键关联，消除设计矛盾
