# 在线客服「带订单号 open」40053 · 后端排查与修复方案

> **文档用途**：小程序联调 OD-08 / SC-09 / QA-901 时发现，从订单详情进入在线客服失败；本文档供 **pet-app-backend** 定位根因并实施修复。  
> **编写日期**：2026-06-15  
> **联调环境**：Sealos · `https://gnmopuadqqay.sealoshzh.site`  
> **前端仓库**：pet-app（本仓库）  
> **缺陷编号建议**：`DEF-CS-001`

---

## 1. 问题摘要

| 项 | 说明 |
|----|------|
| **现象** | 订单详情页点击「客服」，进入 `pages/service/chat` 后页面显示「订单不属于当前用户」 |
| **业务码** | `40053` |
| **HTTP** | 400 |
| **失败接口** | `POST /api/v1/service/conversations/open` |
| **触发条件** | 请求体含 `order_id`，且值为 C 端订单 API 返回的 12 位商户订单号（`out_trade_no`） |
| **对照结论** | 同一 Token 下 `GET /orders/{out_trade_no}` 成功；无参 `open` 成功；**仅带 `order_id` 的 `open` 失败** |

**结论（联调侧）**：订单归属与客服会话创建均正常；失败集中在客服模块 **未正确解析 C 端传入的 `out_trade_no` 格式订单号**，导致 `active_order_id` 绑定失败并误报 `40053`。

## 5. 根因分析

### 5.1 数据模型与 API 约定

| 概念 | 存储 / 约定 |
|------|-------------|
| 内部主键 | `order_main.order_id`（BIGINT 自增，如 `18`） |
| 商户订单号 | `order_main.out_trade_no`（VARCHAR UK，12 位 `YYYYMMDD` + 4 位序号，如 `202606150018`） |
| C 端对外 `id` | 文档约定返回 **`out_trade_no` 字符串**（见 `项目开发说明-后端.md` §5.7） |
| 客服活跃订单 | `service_conversation.active_order_id` 存 **内部 BIGINT FK** |

### 5.2 订单模块已支持双格式解析

订单模块在 v0.9.0 已修复路径参数解析（changelog：**修复 `out_trade_no` 路径解析**）：

> **`order_id` 路径参数**支持内部 `order_id`（短数字）**或** `out_trade_no`（12 位）。

因此 `GET /orders/202606150018` 能正确命中 `out_trade_no = '202606150018'` 且校验 `user_id = 79`。

### 5.3 客服模块未复用同一解析逻辑（推断）

客服接口 body 字段虽命名为 `order_id`，但 C 端实际传入的是 **`out_trade_no` 字符串**（与订单详情 `id` 一致）。若客服 Service 层：

1. 将 `"202606150018"` **直接当作** `order_main.order_id`（BIGINT）查询；或  
2. 未走与订单模块相同的 `resolveOrderIdentifier` 逻辑；

则可能出现：

- 查不到对应 `out_trade_no` 的真实订单，却命中了 **另一条** `order_id` 数值碰巧等于 `202606150018` 的记录（极低概率）；或  
- 解析/归属校验基于错误记录 → 返回 **40053**（订单存在但 `user_id` 不匹配）。

无论具体分支如何，**与订单 API 行为不一致**即为缺陷：C 端无法获得内部数字 ID，只能传 `out_trade_no`。

### 5.4 前端侧说明（非故障点）

前端链路符合设计，**无需修改**：

| 步骤 | 实现 |
|------|------|
| 订单详情点客服 | `navigateToServiceChat({ orderId: this.order?.id })` |
| 客服页 onLoad | `entryOrderId = options.orderId` |
| 初始化 | `openServiceChat({ orderId: this.entryOrderId })` → `POST …/open` body `{ order_id }` |

`normalizeOrder` 中 `id` 取自 `raw.id ?? raw.order_id ?? raw.order_no`，与后端订单 API 返回一致。

## 6. 修复方案（后端实现）

### 6.1 原则

1. **复用订单模块已有的订单号解析**，禁止在客服模块重复实现另一套规则。  
2. body / 路径中的 `order_id` **语义与订单 API 对齐**：接受内部 ID **或** `out_trade_no`。  
3. 解析成功后写入 `active_order_id` 的必须是 **`order_main.order_id`（BIGINT）**。  
4. 对外响应 `active_order.order_no` 继续返回 `out_trade_no` 字符串。

### 6.2 建议抽取公共方法

在 **pet-app-backend** 中抽取（或复用已有）工具函数，例如：

```js
/**
 * 将 C 端/Admin 传入的订单标识解析为 order_main 行。
 * @param {string|number} identifier - 内部 order_id 或 out_trade_no
 * @returns {Promise<{ order_id: number, out_trade_no: string, user_id: number, ... } | null>}
 */
async function resolveOrderByIdentifier(identifier) {
  const raw = String(identifier ?? '').trim()
  if (!raw) return null

  // 12 位 YYYYMMDD + 4 位序号 → 按 out_trade_no 查（与订单路由一致）
  if (/^\d{12}$/.test(raw)) {
    return orderRepository.findByOutTradeNo(raw)
  }

  // 纯数字且长度较短 → 按内部 order_id 查
  if (/^\d+$/.test(raw)) {
    return orderRepository.findById(Number(raw))
  }

  return null
}
```

> **实现提示**：若订单模块已有 `resolveOrderId` / `parseOrderParam` 等函数，**直接 import 复用**，勿复制粘贴第二份，避免再次漂移。

### 6.3 归属校验统一封装

```js
/**
 * @throws {BusinessError} 40405 订单不存在 · 40053 不属于当前用户
 */
async function assertOrderOwnedByUser(identifier, userId) {
  const order = await resolveOrderByIdentifier(identifier)
  if (!order) {
    throw new BusinessError(40405, '订单不存在') // 或客服场景沿用 40053，见 §6.6
  }
  if (Number(order.user_id) !== Number(userId)) {
    throw new BusinessError(40053, '订单不属于当前用户')
  }
  return order // 含内部 order_id
}
```

### 6.4 需修改的接口与逻辑

| 接口 | 修改点 |
|------|--------|
| **`POST /service/conversations/open`** | body 含 `order_id` 时：先 `assertOrderOwnedByUser(order_id, req.userId)`，再将返回的 **内部** `order.order_id` 写入 `active_order_id` |
| **`PUT /service/conversations/{id}/active-order`** | 同上 |
| **`PUT /admin/service/conversations/{id}/active-order`** | 解析 identifier 后，校验订单 **`user_id` 等于该会话的 `user_id`**（商户改绑） |
| **`serializeConversation` / `active_order` 摘要** | `active_order_id` 用 BIGINT；`active_order.order_no` 输出 `out_trade_no` |

**`open` 伪代码**：

```js
async function openConversation(userId, { order_id, product_id } = {}) {
  const conv = await findOrCreateConversation(userId, merchantId)

  if (order_id != null && order_id !== '') {
    const order = await assertOrderOwnedByUser(order_id, userId)
    conv.active_order_id = order.order_id          // 内部 BIGINT
    conv.active_product_id = null                  // 订单优先，清空商品上下文（若现有逻辑如此）
  } else if (product_id != null && product_id !== '') {
    // 商品解析逻辑不变
  }
  // 无参：保留已有 active_*（现有行为）

  await conv.save()
  return serializeConversation(conv)
}
```

### 6.5 错误码约定

| 场景 | 建议 code | 说明 |
|------|-----------|------|
| 订单标识无法解析 / 不存在 | **40405** 或 **40053** | 与订单 API 对齐优先 **40405**；若需保持客服现有契约可继续 **40053**，但 message 应区分「不存在」与「不属于」 |
| 订单存在但 `user_id` 不匹配 | **40053** | 保持不变 |
| 会话无权访问 | **40052** | 不变 |

推荐：**不存在 → 40405**，**存在非本人 → 40053**，便于前端与订单模块共用文案（`ORDER_ERROR_MESSAGES[40405]`）。

### 6.6 数据库与索引

确认已有（通常已存在）：

- `order_main.out_trade_no` **UNIQUE**
- `service_conversation.active_order_id` FK → `order_main.order_id`

无需新迁移；纯 Service 层逻辑修复。

### 6.7 自测与 verify 脚本扩展

在 **`npm run verify:service`** 中补充（或修正）用例：

| # | 用例 | 预期 |
|---|------|------|
| 1 | 用户 A 下单，取响应 `id`（out_trade_no），`POST open` body `{ order_id: out_trade_no }` | `code: 0`；`active_order_id` 为内部 ID；`active_order.order_no === out_trade_no` |
| 2 | 同上，body `{ order_id: internalOrderId }`（短数字） | `code: 0`；结果与 1 一致 |
| 3 | 用户 B Token + 用户 A 的 out_trade_no | `40053`（或 `40405`） |
